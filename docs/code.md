# The code

Code in this repository has no comments. A lint rule fails on any comment. What a comment would say goes into a name, a type, or a smaller function. What a name cannot carry, such as why a module is shaped the way it is, lives here. [The spec](spec.md) owns the design. This file owns the reasons in the code that the spec does not name.

## Gates

- `eslint.config.js` holds the lint rules. Inline disable comments are off (`noInlineConfig`), so a rule changes only there, in review.
- `fleet/no-comments` is a local rule in `eslint.config.js`. It allows one comment that the toolchain reads: a triple-slash `<reference lib="..." />` directive, which `e2e/board/board.test.ts` needs for the DOM types of the code it runs in the browser.
- `.dependency-cruiser.cjs` holds the module boundaries. `cardd`, the extension, and the board share only the wire protocol. End-to-end tests drive real processes, so they import only the protocol.
- `ci.yml` puts each pull request's runs in one concurrency group, so a new push cancels the run it supersedes. Each push to `main` gets a group of its own, keyed by its run id. With one group for `main`, a merge cancelled the run of the merge before it, both in progress and while it waited, so that commit never got a full result.
- The end-to-end jobs install their tools through `.github/actions/install-direnv` and `.github/actions/install-chromium`, and no job calls `apt-get` for a package that a release download or the runner image already supplies. On 2026-11-11 the authoritative name servers of `ubuntu.com` stopped answering the Azure resolver that GitHub runners use, so `azure.archive.ubuntu.com`, `archive.ubuntu.com`, and `security.ubuntu.com` did not resolve for more than an hour. Only the jobs that used apt failed: `direnv` came from apt, and `playwright install --with-deps` ran `apt-get update` and then installed the fonts that the image lacks. `install-direnv` downloads the release binary and checks it against a pinned checksum. `install-chromium` caches the browser under `~/.cache/ms-playwright`, asks Playwright which system packages are missing (`install-deps --dry-run`), and calls apt only for those. It does not run `apt-get update` first, because the image's package lists are enough. When the first archive host in `/etc/apt/apt-mirrors.txt` does not resolve, it points apt at mirrors outside `ubuntu.com`. Those mirrors serve the same signed packages. Apt retries with backoff. Each retry refreshes the package lists and asks Playwright again which packages are missing, so the install and the final proof use the same lists. A failed install names the packages and says whether the archive resolves. A final dry run proves that Chromium has every package. The fonts stay, because the board tests measure text layout. The `board-e2e` and `extension-e2e` filters include `ci.yml` and the actions, so a change to how those jobs install their tools runs those jobs.
- `packages/cardd/scripts/check-migrations.ts` applies every migration to an empty database, checks the result, and compares it with the committed `schema.sql`. With `MIGRATIONS_BASE` set to a git ref, it also fails when a migration that exists at that ref was changed, renamed, or removed. `--write` updates `schema.sql`.

## End-to-end deadlines

`npm run test:e2e` runs tests through `e2e/run.ts`. Each test has five minutes. The whole runner has two hours, including teardown. A full unsharded run took almost thirty minutes when the suite had 402 tests. With 608 tests it takes about an hour, and about seventy minutes on a loaded host, so the earlier sixty minutes killed a run that had no failing test. The tests run one at a time and their own time is nearly all of the run, so the deadline grows with the suite. Node's test timeout does not stop a file that finished its tests but still has open handles. The outer deadline kills only the process group it started and returns failure. SIGINT, SIGTERM, and SIGHUP are forwarded to that group, and the runner exits with failure. A file that fails with "Interrupted while running" and "Promise resolution is still pending but the event loop has already resolved" was not hung: that is Node's report of a SIGINT or SIGTERM that reached the test runner, often from a pattern kill elsewhere on the host. CI also bounds each end-to-end job to thirty minutes, including installation and build.

Every board test file calls `boundBoardFile` from `e2e/support/board.ts`, which ends the file after ten minutes even if its tests finished with open handles. Board fixtures register cleanup through `startBoardServer` and `openBoardPage` as each resource is acquired. A seed failure before the page exists must still stop its server. The kanban and links fixtures use normal timers: they do not assert timed-check behavior, and an accelerated timed check competes with fixture database writes.

## Protocol

`packages/protocol` is the wire protocol between `cardd`, the extension, and the board. Each schema is the one source of its type and its validator. `parse` throws one readable error that names the first problem.

## cardd

### Command line

```
cardd serve --db <file> [--listen <host:port>] [--board <built board folder>] [--hostname <name>]... [--hosts <json>] [--public-host <host> --access-team <team domain> --access-aud <tag> --access-email <email>]
cardd lane add <name> --db <file> --home <path> [--parent <lane>]
cardd lane list --db <file>
cardd lane home <name> <path> --db <file>
cardd lane remove <name> --db <file>
cardd lane plan <name> --db <file> [--plan <json>]
cardd project list --db <file>
cardd project add <name> --db <file> --delivery <mode> [--clone <host>=<path>]... [--yolo] [--repo <owner/name>] [--hosts <json>]
cardd project clone <name> <host>=<path> --db <file>
cardd project unclone <name> <host> --db <file>
cardd project remove <name> --db <file>
cardd project yolo <name> on|off --db <file>
cardd project delivery <name> <mode> --db <file>
cardd card delivery <number> <mode> --db <file>
```

`serve --hosts` takes JSON, and [setup.md](setup.md) owns its form. The four `--public-host` and `--access-*` flags turn on the public board link, and [setup.md](setup.md) owns that too (A public link through Cloudflare Access). They are set together or `serve` refuses to start. `project add` without `--repo` reads the project's GitHub repository from the `origin` remote of a clone. It runs `git` through the transport that `--hosts` names for the clone's host, and on the `cardd` host itself for a host that `--hosts` does not list, so a clone on another host needs `--hosts` or `--repo`. It prints `<name>: repo <owner>/<name>` or `repo not set` and what to do, because a clone it cannot read is not an error. `serve` fills in any that are missing at each start. `lane add` and `project add` refuse a name that exists, with a message that names `lane list` or `project list`, so the database's constraint never shows.

`registry.ts` holds the commands that read and change the registry beyond `add`. `lane list` and `project list` print one plain line for each row. `lane home` sets a lane's informational home and refuses a relative path. `lane remove` deletes a lane that never worked: its row, its mate's session, deliveries, and maintenance records (the reloads and stows that main asked of it), its lane card, and its schedules, in one transaction. It refuses a lane that is a parent, whose mate is not `exited`, that has an open card, or that has entries or incidents, because entries are append-only and a card with entries cannot be deleted. Removing a lane that ever worked a card would need its cards to outlive it, as `cards.historical_project` does for a project, which is a schema change that nobody has asked for.

Every command except `serve` opens the database with `openDatabase(path, false)`, which refuses when the database has a schema (`user_version` above 0) older than the checkout's last migration, and names both numbers. Opening applies pending migrations, so a CLI run from a checkout newer than the running `cardd` would migrate the live database under it. `--migrate` lifts the refusal. `serve` always migrates, which is the supported way (section 7 of [setup.md](setup.md)).

`project clone` sets one host's clone of a registered project to a new path, so a clone can move. Attempts already begun keep their worktrees where they are: close finds them through the clone's worktree list, not through a stored path.

`project remove` refuses open cards, then moves the closed cards' project names into `cards.historical_project` and clears their registry references before deleting the project. Card reads coalesce the current and historical names, so their public history stays unchanged and foreign keys stay valid. Clone registration lives in the project row, so deleting it removes every refresh and dispatch target without touching files.

`project delivery` sets the delivery mode that new ship cards of a project take: `no-mistakes`, `direct-PR`, or `local-only`. It changes no card: a card records its mode when it is created, and that record is what dispatch tells the worker. `card delivery` changes the recorded mode of one open ship card. It refuses a card that is closed, is not a ship card, or has a live worker, because that worker was told its mode in its task and a changed record would let it go on with a stale one. To change the mode of a card with a live worker, a mate dispatches again with `delivery=<mode>` and `replace=true`, which starts the worker over with the new mode. Setting the mode a card already has changes nothing. Each change is a note on the card.

`lane add` prints the mate's token. The first lane, added with no `--parent`, is the root. `one_root_lane` allows no second root, and `mainLane()` is the only reader of that row. A second mate is added with `--parent`. `CARDD_TIMING_SCALE=0.01` speeds up every timer, for tests. `CARDD_CLOCK_FILE=<file>` makes the timed checks, such as the scheduled wakes and a lane stop's end, read their time from that file, an ISO 8601 time, instead of the clock, so a test moves time by writing the file. Entries keep real time. `project yolo` sets the captain's standing merge authority for a project. The captain can set it through this command line or tell main to set or clear it with `project_yolo(project, on)`. The tool is offered only to main. The `project.yolo` operation validates its arguments, refuses workers and second mates, and reuses the registry's `setYolo`. Main never changes it on its own initiative or on a second mate's request. Destructive, irreversible, or security-sensitive merges still need the captain's words with yolo on.

### Storage

- `store.ts` reads and writes `cards.db`. A mate's session ID is its lane name. Rows leave the database as JSON that SQLite builds, and are checked against the protocol schemas, so the types match the wire. A card from before names existed is known by its number.
- A session's token is the HMAC of its role and ID under the database's key. The same session always gets the same token, and no mate can share a token with a worker.
- `db.ts` applies every new migration in one transaction, so a failed migration leaves the database as it was. Foreign keys are off while migrations run, as SQLite's procedure for rebuilding a table requires: dropping a parent table counts each child row as a violation that its replacement never clears. Instead, every key is checked after each migration, and a violation names its rows. Every foreign key in the schema is one column.
- Each entry that the card's status reads raises the card's revision, and so does any change to the card's row, such as `last_activity` when a session starts or ends a turn. The revision is for readers that cache a card's thread (the board's facts). An action never compares it: a board action or a pane answer names the hold entry the captain saw, so unrelated entries and card updates cannot refuse it.
- The cards table stores no status, phase, or time of change. `store.ts` replays a card's entries through `status.ts` each time it reads the card.

### Status and holds

- `status.ts` is pure. A card's status is one function of its communication entries: the worker's reports, holds, the captain's answers, comments, and the close. Mostly the last report decides. An open hold wins. Nothing else feeds it: not GitHub, not the timed check's findings, not job results, not commands. No operation sets a status, and none is stored.
- A hold that waits on the captain makes the card Needs you. A hold that waits on a mate makes it With mate. A hold with a future date is Waiting until then. A closed card has no hold.
- A `paused` report shows the card as Paused until its date. A `blocked`, `failed`, or `stopped` report shows the card as With mate with red attention, except a `stopped` that follows `done` or `merged`, which is never written (see Closing). Any later report, steer, or answer replaces both. Pause, finish, and idle-watch are decided once in `status.ts`, not read from the latest report row: `pausedNow`, `isFinished`, and `idleNow`. The timed check and incident recovery read those. A steer that resumes the worker clears the pause, so the idle watch starts then, not when the old pause date passes. `pausedNow` does not depend on the status: a pause while Merging leaves the card Merging on the board, and recovery still sees the pause. `isFinished` is the worker's done or merged handoff, until a steer or a later handoff report takes it back. `finishedOpen` is the wider fact for the close reminder and the bundle: a merge report still counts after either, because a merge is not taken back.
- A card shows one state, and `standingFrom` in `status.ts` is the only place that decides it: `status`, `attention`, and `until`. `until` is the date a Paused or Waiting card's wait ends, the report's or the hold's, and null when the card has no date, as a standing card that is Waiting has none. Attention shows only while the card has no open hold, so a hold with a future date reads Waiting with its date whatever the worker last reported, and when the date passes the card reads by its holder as above, with no attention. The board, the `board` tool, and the worker's own `standing` op read that state and never decide one of their own.
- A captain's approval of the merge question, or yolo on a ship card's `done`, makes the card Merging. The worker's next `done` leaves it Merging, and the mate's close makes it Done or Dropped.
- `change.ts` holds the guards of spec section 7.4: a Done or Dropped card refuses reports, holds, and steers, and a lane card refuses all of them. `statusWith` reads the status a report will give, with the entries a caller writes next counted.
- `waits.ts`: a dated hold says what it waits on and what work remains. `hold` with `until` refuses a call that does not give exactly one of `job`, `schedule`, `worker` (a card whose worker is live: its attempt runs and its Pi is connected), `watcher` (free text that fleet cannot check), `outside` (an outside date or event), or `said` (the captain's words for later, checked like a merge approval's: `source` is `chat` when the extension found them in the session file, otherwise `record`, which `cardd` looks for in the captain's entries). A mate may name only a job, schedule, or worker of its own lane (main may name any lane). One of another lane is refused with the words for one that does not exist, so the refusal gives away no label, time, or liveness. The same check runs each time the hold is read, against the lane that wrote it (`Hold.author`), because a schedule id is given out again once its schedule is removed: a hold whose id now belongs to another lane's schedule reads as gone, in the words for a schedule that was removed. It also refuses a call without `remaining`: an array of card numbers, `[]` for none, each an open card of the mate's reach other than the held card. The statement is stored in the hold entry's `wait` and `remaining` fields, so no migration is needed. `status.ts` reads them with `parseWait` and `parseCards`, which treat anything else as no statement. `datedWait` turns a hold that is Waiting into a `DatedWait` for the board and the reminder: `watch` is `running` (a job that runs, a schedule that exists, or a worker that is live), `unchecked`, `outside`, `later`, `gone` (the job, schedule, or worker is gone, or the worker's Pi is not connected: it never connected, exited, or was lost), or `none` (no statement: every dated hold from before this existed). `gone` and `none` are an idle park (`idlePark`). A `watcher` text is never idle, because fleet cannot see it. `since` is when the hold opened, so dating it again keeps its age. The `board` and `card` tools show a dated wait on a job, schedule, or worker of another lane, and a remaining step that is a card of another lane, to a reader that cannot reach it (not main, not that lane) as the kind and the state only (`a job in another lane (running)`, `c-N (another lane)`), and a list for a mate follows the same rule. The hold entry shows only the kind in its `wait` field in the same case, in the `card` tool and in the push to its mate. The `card` tool also leaves out a decision list that was sent to another lane's mate, for a reader that is not main, because main's list names objects of every lane and is kept on the oldest card in it. The web board stays whole. A date that the captain types on the board or in the pane counts as his later, with his typed words as `said` (see Later, in the Pane section).
- `holds.ts`: a card has at most one hold, with every question of its gate bundled in it. The card's own mate owns it. It waits on the mate, then main, then the captain, and climbs one level at a time. Only main marks a hold as the captain's. Main's own cards skip main. Holding the same hold again writes nothing. A hold after a release is the next occurrence of the same hold.
- Only the captain's exact words release what waits on the captain. Merge approval is such a release. Own words on a merge question request changes: only the Approve option approves.
- A steer withdraws the merge question while the PR is reworked, because approving a PR that is about to change would approve the wrong head. The worker's next `done` asks again, as the same hold.
- The captain's comment takes the hold back from him. A comment written on the board goes to main only, never to a second mate or a worker, and it carries the card's lane when the card is not in main's lane. Main relays it as it sees fit. A hold that went back to a second mate's lane waits there until main does.

### Talking

- `comments.ts`: a comment is the one way to talk to an agent. A worker's card hears its mate. A second mate's lane card, or any card in its lane, hears main when main speaks, and main hears the second mate when it answers. Main never steers another lane's worker. A comment cannot answer a worker's decision that waits on the captain.
- `board.ts`: `/api/board` and `/api/card/N` give the board its data. Each card carries `activity`: the state of the session that works on it (a worker's, or a mate's for a lane card) and when cardd last heard from it. A change of that state reaches the board over the live socket. `cardd` sends `changed` to board tabs at most once per second, except right after a board action. `/api/board` is rebuilt only when the database changed or the last build is over a second old. A card that is Waiting on a dated hold carries `datedWait` (`waits.ts`), which the board shows as a line on the card and a Waiting row in its detail, marked when it is an idle park. An open work card also carries `pulse` (see Neglect, below).
- The board's thread (`thread.ts`) gives each entry a direction from its author, its `for` and `holder` fields, and the card's lane. Rows between two mates are quiet log rows. A board answer that main recorded again with the captain's words is not shown twice, and a quote of the captain's earlier words in another entry folds to a marker. A `replyTo="r-N"` entry shows a link to its question. Replies to a captain comment nest under it and keep their sender and recipient labels. The board's reply e2e uses real cardd comments and answers, with no direct database writes.
- `ops.ts`: a report reaches the mate when its status hands off, or when it is the first report after a comment that reached the worker (spec section 10.3). Each operation runs in one transaction. A `paused` report with no `until`, or one that is not in the future, is refused with a message that tells the worker to report `blocked`. One more than 24 hours away is refused too, and the worker is told to ask its mate for a dated hold. `paused` is a wait on a time or an outside event. A wait on the mate's action is `blocked`, which reaches the mate and stays on its decision list. A paused report is routed like any other: the first one after a comment, and one with a `replyTo`, still reach the mate. The extension fills in no default date, so a worker cannot pause without choosing one.
- `replies.ts`: a mate can ask for a reply to one comment, on its worker's card or, as main, on a card in a second mate's lane. The comment entry is the record: it carries `owes`, the recipient, and the reply's id is `r-<entry id>`, so the record exists in the same transaction as the comment, before any push. The open replies are derived from the card's entries, like its hold. Only an entry from the recipient that names the id in `replyTo` answers it: a worker's report, or the second mate's comment or hold, which goes to the asker. Only the asker withdraws it. The timed check resends it after two minutes, then every five minutes while its recipient is up, until it is answered or withdrawn. A dated hold pauses the reminders. The captain's board comment opens one too: it carries `owes`, the lane of main for the card, and the answer is main's comment or hold with that `replyTo`, which notifies no one and is marked `for: captain`. It uses the same repeating reply reminders to main. Replies on a closed card are not nudged and not shown.
- `plans.ts`, `schedule.ts`, and `wakes.ts` are a mate's scheduled wakes (spec section 19 describes run cards for a standing card: this is the lighter form that wakes the mate and starts nothing). The plan is on the lane card in two columns: `plan_next` is what the captain set, and `plan` is what the mate loaded at its start, with the time it took effect. The `lane.plan` op, which the extension calls once when it starts, moves the next plan into the active one and returns it, so activation is the mate's own restart and the call is safe to repeat. Only the active plan fires.
- `schedule.ts` is pure. Time is compared as local wall-clock minutes (`YYYY-MM-DDTHH:MM`) in the plan's zone, never as instants, so a time that DST skips fires when the clock reaches it and a time that DST repeats compares true twice. For each wake it finds the latest slot at or before now, looking back at most a week. The slot is due when it is not before the minute the plan took effect. A wake is never made up for more than its latest slot.
- `wakes.ts` writes the wake in the timed check. A slot's key is its minute and its purpose, and the wake entry carries the keys it covers in `fields.slots`, so what is issued is read from the card's own entries: a restart of `cardd` finds it, with no second table. Slots due together are one wake. The wake is a comment by `schedule` with `owes` the lane, `for: mate`, and `from` the lane's parent, so reply tracking in `replies.ts` treats it like main's `reply=true` comment, with two differences: main can withdraw the reply, but the mate's answer notifies no one; its text is the whole wake line. Open replies never suppress later scheduled wakes. A script wake (`wake` op) is a plain comment by `script` that owes nothing.
- `echo.ts`: when a parent commented on a card and the mate has not acted on it since, the mate's next action also reaches the parent. It is sent once, because the next action ends the wait.
- `authority.ts`: the mate's extension checks chat words against its own session file. For any other source, the words must be in a captain entry: a board comment, an option click, or an earlier answer. A project's yolo flag lets its mate have the worker merge a green PR without asking. A done PR in such a project goes straight to Merging.

### Attempts, delivery, and the server

- Delivery modes: a ship card records its mode in `cards.delivery`. `card.new` takes the project's registered mode, and maps `no-mistakes-prod-only` to `no-mistakes`, its most rigorous leg, as Firstmate's `fm-project-mode.sh` does for mechanical callers. `attempt.begin` records an override that the mate passes, and writes the card's mode into the task message as its `Delivery:` line, so the worker reads the mode from the card. A task that names another mode is refused. A worker that already runs keeps its mode: a new mode needs a new attempt. `cardd project delivery` changes the default for later cards only, and `cardd card delivery` changes one card that has no live worker (see Command line).
- A local-only card has no PR. Its worker starts from the clone's local base branch, without a fetch, because local-only work lands there and never on origin. Its `done` carries where its branch lands instead of a PR lookup, and raises the same merge question about the branch. A branch with no commit off the local base branch and no uncommitted file in its worktree is an operation, such as an ad change: its `done` raises no merge question, withdraws a merge hold already open, and the mate closes it directly. The comparison is against the local base only, so a branch fast-forwarded to `origin/<base>` still counts as having commits (`empty-branch.ts`). The timed check and close never look up a PR for it.
- `attempts.ts`: an attempt is one run of a card by one worker. Its ID is the retry key for dispatch. A dispatch retry on the same host finds the same attempt, with the same token and no second task message. A new attempt gets its task message in the same transaction, so a retry can neither lose it nor repeat it.
- A worker names its own branch, as Firstmate's workers do (`fm-task-branch.sh`). A new attempt's worktree starts on a placeholder branch named for the attempt, such as `c-83-a1`, with `attempts.branch_named` at 0. The worker's first action is the `branch(name)` tool: the name is `<type>/<slug>` (`branchNameProblem` in `@fleet/protocol` owns the rule), the extension refuses a name taken in the clone or on origin and renames the branch it is on, and the `branch.name` op records it in `attempts.branch`, refusing a name that is another live attempt's in the same project. If the record is refused, the rename is undone. A branch is named once: naming the same name again confirms it, and another name is refused. Every consumer that needs a card's branch (close's landed check, the archive, the local-only fast-forward, a resumed dispatch, and `board(card=N)`) reads `attempts.branch`, so none of them guesses a name. Attempts made before this, including those on `fm/c-N` branches, have `branch_named` at 1 and keep the branch they have. A scout makes no branch, so it never names one.
- `deliveries.ts`: at a connect, every delivery that is queued, in flight, or taken in but missing from the session file is pushed. While the session stays up, only a queued delivery is pushed. A delivery already in the session file but not taken in waits for the chase. Each push carries its card's short name, which the message shows after the card number. No entry quotes the comment it answers, so when a second mate steers its worker right after main's comment, the worker gets the steer alone, never main's words to its mate.
- A comment from a mate or the captain is a Pi steer unless the sender set `later=true`; other entries stay follow-ups. A `now` argument from an older caller is ignored, since steer is the default. A worker report other than `working` or `note` is refused while a comment to it is unread, and the error names the comment. A comment is unread while its delivery is `pending`, `pushed`, `resent`, or `pushed-again`: no finished model response of the worker has held it. A comment that a hello listed as in the session file is not unread, because the file holds it. Whether a settled run took it in is a separate fact, and the gate does not ask it. A comment that was queued while the worker was down, or lost before the file existed, is not in the file, so it stays unread until it is sent and a finished model response holds it. The gate never waits for the run to settle, so a worker that read a comment can hand off in the same run. A resend makes the comment unread again.
- A delivery has one state: `pending`, `pushed`, `resent`, `pushed-again`, `read`, `filed`, `acknowledged`, or `confirmed`. `pending` waits for its first push. `pushed` has been sent and no finished model response has held it. `resent` waits to be pushed again. `pushed-again` has been sent again and no finished model response has held it. `read` was held by a finished model response and is not taken in. `filed` is in the session file and not taken in. `acknowledged` was taken in by a settled run and is not yet in the file. `confirmed` was taken in and is in the file. The extension's `read` moves `pushed` and `pushed-again` to `read` and changes no other state. A hello that lists the entry confirms an `acknowledged` one and files any other, and it never takes one in, so a queued entry that the file lacks stays `pending` and is pushed. A `read` entry that the file lacks is sent again at the connect and stays `read`. Only the extension's `ack` takes it in, when that run settles with no abort and no error. Neither Pi adding the message nor a finished tool-use response takes it in: a run aborted or failed after such a response leaves the entry `read`, and the chase resends it. A message can sit in the session file and still not be taken in, when the captain aborts the turn or the provider fails, and Pi drops a queued follow-up on Escape. A `cardd` that is older than the extension only records the acknowledgement later, and drops the connection at a `read` it does not know until the update brings it onto the same commit. The chase never resends or reports a session whose run is still going: a queued follow-up or steer waits for the next model call, so a worker in one long turn has not taken it in yet, and its fate is known only at settle. A hung run is the stall check's business. The idle-worker check ignores a worker with an entry in flight (`pending`, `pushed`, `resent`, `pushed-again`, or `read`) and does not ignore a `filed` one.
- The extension holds every pushed entry until Pi has loaded all extensions (its `resources_discover` event). A push that arrives earlier would start the model's first request before other extensions, such as pi-fff, have registered their tools, and the tool list would change between requests and break the prompt cache prefix. `e2e/extension/prefix-stable-tools.test.ts` covers it.
- The chase resends every two minutes a delivery that is `pushed`, `pushed-again`, `read`, or `filed`, so one that is not taken in, while the receiver is up. Each resend uses the same entry, marked `again`, including entries already in the session file. Main hears after three resends, then every 15 minutes. Main's own entries keep resending without a self-escalation. The extension deduplicates repeated delivery within a turn, not forever. This tracks intake, independently of reply obligations.
- `server.ts`: one websocket per session, plus `POST /call` with a bearer token for scripts. The first message must be hello with the token. Every later message checks that the session is still live, so an ended or replaced attempt loses access at once. A hello from a known session whose attempt ended is refused with 4001, and `cardd` logs why once for that session until it restarts. At start no session is connected: live sessions reconnect and become idle, or running when their hello says a run is going, so a reconnect never makes a running worker eligible for the chase. The extension's link remembers the latest activity it was asked to send and sends it right after welcome, so a run that ends between hello and welcome still leaves the session idle.
- `web.ts`: the board has no login. Without a public host, only the Tailscale network reaches `cardd` (spec section 21.4): every board request must name an allowed Host, which closes DNS rebinding, and its Origin, when present, must be allowed. With a public host, a request for it needs Cloudflare Access's token instead (The public host, below).

### The public host

`access.ts` and `Web.channel` in `web.ts` decide what a request is before any route sees it. Without the four flags, every request is a tailnet request and nothing here runs. With them, each request is one of three things:

- Public: its Host is the public host exactly, with no port. Its Origin, when present, must be `https://<public host>`, and a write or a websocket upgrade must carry one. It needs a valid `Cf-Access-Jwt-Assertion` header. Only the board's own routes answer it: the pages, `/api/board`, `/api/card/N`, `/api/version`, `POST /api/action`, and the `/live` socket. `/call`, `/session`, and `/api/health` do not, even to the owner.
- Refused: its Host is anything else, but it carries a header that begins with `cf-`, a `Cdn-Loop` header, or an Origin whose host name is the public host, under any scheme or port. Cloudflare adds those headers to every request that it forwards, so such a request came through the tunnel with a rewritten Host. The markers only refuse: they never make a request public, so a valid token does not rescue it. This is the rule that stops a tailnet-looking request from becoming a way round the token check.
- Tailnet: everything else, handled exactly as before.

A process on the host that runs the tunnel can still send a request with the tailnet Host and none of the markers. It gets the tailnet's access, which any process on that host already has: the board with no login, and `/call` with a token.

The token is checked with `jose`: RS256 only (`none` and `HS*` are refused before a key is looked up), the signature against the team's certs endpoint, `iss` equal to `https://<team domain>`, `aud` holding the AUD tag, `exp` required, `nbf` and `exp` honored with five seconds of skew, and `email` equal to the owner, ignoring case. The keys are kept for ten minutes. An unknown key id fetches them again at most once every thirty seconds, and so does a failed fetch, because `Access` refuses without fetching for that long after a failure. A request whose keys cannot be had is refused, never let through. `CARDD_TIMING_SCALE` scales both times. A refusal gives a 403 with no reason and no board content. The reason goes to the log, once a minute for each reason. A reason is a name from a fixed set: a fixed sentence from `access.ts` or `Web.channel`, a `jose` error code, or a `jose` error code with the claim that failed. It never holds text from the request, so tokens that differ only in their text log once and keep nothing. A failed fetch of the keys logs its cause once for each cooldown. The token is read from the header only, never from the `CF_Authorization` cookie, so a cookie that Cloudflare would have turned into a header at the edge buys nothing at cardd. A websocket that was opened with a valid token stays open after the token expires. It carries only the word `changed`, and the data behind it still needs a valid token.

The test certs endpoint is served over TLS with a certificate that `openssl` makes for the test, and cardd trusts it through `NODE_EXTRA_CA_CERTS`. That keeps the production code free of any switch that fetches keys over plain HTTP.

### The timed check

- `check.ts` polls `cards.db` every 15 seconds. Each tick loads the open cards once and shares them between the rules. Finding identity includes the obligation, its occurrence when needed, and the current due tier. It emits the current tier once, never a backlog of missed tiers. Reminders pause while the receiving mate is down. See [Persistent wakes](wake-plan.md) for all cadences. An idle worker is a quiet session whose card is `idleNow`: working or in review, and not `pausedNow`.
- Workers report `pr` explicitly when done and `merged=true` after merging. `cardd` never queries GitHub for discovery, checks, or merge confirmation. A done report without a PR reaches its mate without a merge question. Close trusts the worker's merge report. Authority still comes from the captain or yolo, not the report.
- Finished open cards repeat to their own mate every two hours. Escalating unresolved work is the second mate's decision.
- `timing.ts` owns the thresholds and test scale. A job is `running`, `lost`, `finished`, or `abandoned`. `@fleet/protocol` holds that state and the one rule table that moves it, and `cardd` is the only writer. A job is running only when that state is `running`. Three missed heartbeats move a running job on a live attempt to `lost`. Its mate is reminded until the job is rerun or dropped. `job.drop` sets `dropped_at` on a lost job, for its worker or a mate of its lane, and the job stays lost. `dropped_at` is valid only on `lost`. Dropping twice is safe, and a job that is not lost is left as it is. A lost job that is not dropped runs again when its heartbeat returns: `job.alive` sets it back to running and sends its worker a `job-result` entry marked `revived`. A late result still finishes a lost job, dropped or not, and clears `dropped_at`. Ending an attempt, including close, abandons each running job of that attempt, so the row does not stay `running` after the attempt has ended. The extension syncs its tracked jobs from `cardd` before it delivers any job result, and keeps the result pending if the sync fails. The hub keeps one grace object for job loss: the time of the first check, and the stall deadline. The timed check skips lost-job detection for the first three heartbeat periods after `cardd` starts, so a restart does not lose jobs that have not yet reported. After a late check tick (the event loop stalled), job loss is skipped for three heartbeats too, so live jobs can report again.
- `bundle.ts` builds the one decision list for each mate: with-mate and merging cards, holds waiting on it, and for main every captain-held card, marked as the captain's. The holder of the hold picks the mate, not the card's lane. It is sent when its oldest card has waited 30 minutes and the last list went out 30 minutes ago, so a card resolved or held between lists never starts a second clock. A dated hold is a line in the list: it names what it waits on, until when, and how old the hold is. A watched wait, an outside date, and the captain's later are listed as information in their own group, and they ride along with every list. They never start a list on the 30 minute cadence. After a day, a watcher, an outside date, and the captain's later are parked, and the pulse sends them to main instead (see Neglect, below). When a mate has only such waits, it gets one information list (`information: N dated waits, nothing needs action`) once a day, `informing` in `timing.ts`, counted from the oldest wait or from the last list that was due for them, whichever is later. A list on the 30 minute cadence that carries the watched group along does not count: its `watched` field is 0. The `watched` count in each list entry's `fields` is how the check reads that back after a restart, with no table of its own. An idle park (see `waits.ts`) is an item to act on, in the first group, so the date never hides it, and the check treats its card as acting. Its receiver is the holder's mate, as for any hold. A dated pause keeps a working card off the list, because a paused card is silent, until it has lasted a day (see Neglect, below). It quiets only a card that is otherwise Working or In review: a card with an open hold, or a Merging card, stays on the list for its own reason.

### Health and logs

- Every `cardd serve` log line starts with an ISO timestamp (`log.ts`).
- `health.ts` watches the event loop two ways. `monitorEventLoopDelay` feeds the five-minute summary. A 100 ms timer measures how late it fires, and a line `warning: event loop lag <ms> ms, p99 <ms> ms, max <ms> ms` is logged when it is over 1 second. That timer also sets the latest lag that `/api/health` reports, so every incident counts, not only a record one.
- A check tick over 500 ms logs `warning: check took <ms> ms, over 500 ms (slowest part: <name>)`.
- Every five minutes it logs `health: loop p50 ... p99 ... max ...; longest tick <ms> (<part>); accepted <n>; sockets <n>; sessions <n>; rss <MB>`, then starts a new window.
- `GET /api/health` answers `Health` from `@fleet/protocol` with no card loading and no auth: `commit`, `now` and `windowStart` (epoch ms), `loopP50Ms`, `loopP99Ms`, `loopMaxMs` (since `windowStart`, the last five-minute summary), `lastLagMs` and `lastLagAt` (the last lag over 1 second, `null` until one happens, never reset), `lastTickMs`, `longestTickMs` (this window), `sockets` (open connections), `sessions` (live session sockets), and `rssBytes`.
- Policy: alert and shed load, never exit on lag. `cardd` has no exit or restart on lag.
- `e2e/cardd/health.test.ts` freezes a real `cardd` with SIGSTOP and SIGCONT, then reads the health and the log.

### Runtime incidents

- A runtime incident is one failure episode of one actor, a worker or a mate: a model turn that ended in an error, a worker that never connected, or a worker connection that was lost. `incidents.ts` owns them. They are not report entries, so they never change a card's status and never take back a `done` or a pause. The record keeps the actor's intent from the card when the incident opens. That intent is a checked set: working, paused, completed, closed, queued, with-mate, needs-you, waiting, and merging for rows saved before active Merging became working intent. `incidents.state` is the same kind of checked set. Both are parsed when a row is read. `nextIncident` in `incident-lifecycle.ts` is the only transition table, and every state write goes through it. Recovery is offered only for a working snapshot, or a saved merging snapshot, while the card's current intent is also working. The eligibility notice and every recovery step a message names check the current intent as well as the snapshot, so a later pause, hold, or completion is never offered recovery. Closing the card is a `card-closed` event: it supersedes every live incident of that card. Active Merging is working intent, including post-merge verification that a parent requested after the worker's done or merged report. An explicit merged report is a completed handoff until that new work is requested. A PR's merged state alone does not finish that verification. A future worker pause remains a pause even when the card's stage stays Merging. Recovery reads `pausedNow` and `isFinished` (see Status and holds).
- The error comes from Pi's own failed assistant message, read at `agent_settled` by `failure.ts`, so no second model turn is needed to learn the cause. Reading it at the settle and not at each message keeps a failure that Pi's own retry or a queued follow-up cured in the same run from being reported. A failed turn also skips the handoff nudge and the `stopped` report, since both would need another model call that would fail the same way. A failure the extension cannot send at once is kept and sent at the next connect. The extension keeps no record of what it reported. Each settled run that ended without an error, and each successful compaction, asks `cardd` to clear, and `cardd` answers from its own incident. A clear that could not be sent is kept the same way and sent at the next connect, before every kept failure of either kind, since an actor has one live incident across both phases and a failure sent first would join the incident that the clear then closes. A success also drops a kept failure of its kind, since that episode ended before `cardd` heard of it. What is kept lives in a process-wide cell, not in the reload-local `Failures`, because the process id and the incident survive a reload and so must what the extension still owes `cardd`.
- A failed compaction (`session_compact_failed`, not an abort) is a `compaction` incident with its original error, told once like a turn failure. The backoff's failure count and next retry live in the same process-wide cell as the patch that reads them, so a reload does not clear the backoff and does not retry a failed compaction at once. Only a successful `session_compact` verifies its recovery, after the recovery check reached the process; a retry or a replacement makes the extension compact once, without a model turn. A turn that succeeds does not clear a compaction incident, and a compaction does not clear a turn incident. A `stale-module` error, a missing import from an old loaded bundle, offers only `replace`, which keeps the same session and card. Fleet decides recovery from the error text alone and does not rely on any router fallback.
- Recovery never creates a card, a conversation, or an attempt: every incident and recovery entry is on the actor's own card. The one card fleet makes is the captain card for main's own failure, since main has no card, and it is not a recovery.
- `sanitize` hides bearer tokens, key-shaped strings, and long opaque words, and cuts the text, before it is stored or told. `classify` is a pure match on that text: `stale-module`, `router-cooldown`, `vendor-quota`, `auth`, `transient`, or `unknown`. Unknown stays unknown. A local router cooldown is never called a vendor quota, and the router's own timers are not used as a vendor reset. Only a `Retry-After` in the error is trusted as a reset time.
- An actor has at most one live incident (`one_live_incident`). Repeated errors of the episode add to its count and tell nobody. The direct parent hears once when it opens: a worker's mate, a second mate's main. Main has no parent, so its incident is a card for the captain with a hold on the captain, which the board shows with no agent involved. The timed check ties the `worker-never-connected` and `worker-not-connected` findings to an incident, so those findings carry its id and stay the one message. A worker that is paused or finished gets no incident from the watchdog. A second mate whose connection is lost, not closed cleanly, for longer than the not-connected grace gets an incident for main, unless that mate is in a stop that has not ended. `lane.stopping` starts the stop, and it ends at `stopping_until` (four minutes, on the same scale as the other graces) or at the mate's next connect, whichever comes first. A loss that is still open after the stop ends is reported, so an abandoned stop cannot hide a later crash. A mate that reconnects in the same process clears a lost or startup incident, so a network blip leaves no open incident. A live incident also holds back the idle finding and the `missed` chase for that actor, since the same failure caused them.
- A session's `process` is a random id generated once for the OS process and sent in `hello`. An in-process reload keeps it. A new OS process raises `generation` and supersedes an open or blocked incident, since a failure of the new process is a new episode. A recovering incident stays, so a replacement can finish. A cardd restart keeps the process id, so it keeps the incident and tells nothing again. A reload or a relaunch completes a reload that was already in progress because that extension's first hello says it just started (`started`), not because the process id changed. A reconnect of the same link does not. The link sends `started` in each hello until `cardd` answers one with welcome, so a connection that drops before the answer does not lose it.
- `card.restart` (the `restart_card` tool) is for the direct parent only. It carries the card, the incident, the generation it read, a mode, and a key, and optionally `avoid` and `model`, whose rules are under Lanes and homes (Dispatch's `model`). In one transaction it refuses a foreign parent, a stale generation, a mode the class does not allow or whose budget is spent, and a time before the incident's eligible time. An ordinary restart of a working card or a card with its mate replaces the process as before. A card that is paused, finished, waiting, or held for the captain is replaced only when its worker's session is disconnected (`lost`, `exited`, or never connected). The plan then says `reconnect`: the restart writes one note, resumes nothing, and leaves the card's status as it was. A connected worker of such a card is refused, because there is nothing to reconnect, and a repeated key still answers with the same plan. It rechecks the current card's execution intent before starting recovery, and the eligibility notice uses that same current intent, so a later pause or completion is protected too. Existing incidents whose saved intent is `merging` need no data rewrite: they may recover only while the current execution intent is working. A second recovery with another key while one runs is refused, and the same key answers with the same plan, so a retried call after a crash never starts a second one. Budgets are two retries and one replacement for each episode. A retry waits 30 s, then 2 min, never less than the `Retry-After`. A vendor quota with no known reset and bad credentials are blocked at once: restarting is not a repair.
- Recovery sends a health check, never a task. `retry` delivers it to the live process. `replace` records it and delivers it only when the new process connects, so the old process can never answer it. The recovery is verified when the check's turn settled without an error (the same acknowledgement that marks the delivery taken in) and the actor then made a `report`, `comment`, or `board` call after the check reached it. A process that merely started does not verify. A failed check turn, or no verification within the window, spends the attempt, is told once, and ends in `blocked` when no mode is left. The extension takes a recovery check as an end of run that needs no handoff, so it never nudges a paused worker into work.
- Times that a person or a vendor sets, the eligible time and the `Retry-After`, read the controllable wall clock. The verification window uses the real clock.
- `incident-escalation.ts`: a live incident of a worker in a second mate's lane goes to main when no recovery is left. Main hears it once, as one `runtime-failure-unrecoverable` finding in a single line that names the card, its lane, the incident, the failure, and why. It is written when the owning mate's first reminder is due, one `repeat` after the incident opened, and only while the incident's saved intent is working (or the old `merging`). It waits for main to be up. It is retired when the incident ends or the card closes or pauses, and a pause does not let it be written a second time: the entry already written for the incident keeps a resume from sending another. A recovery that is running holds back a finding not yet sent and keeps one already sent. The owning mate's reminders are unchanged. A worker in main's own lane is not escalated, since main is its mate.
- "No recovery left" is exactly one of two things. The incident is `blocked`: its class allows no mode (`auth`), or the retry budget and the replacement budget it allows are spent. Or the direct parent asked for a restart that avoids the provider of the card's explicit model, and `card.restart` refused it. The request must name an open incident of that card at its current generation, while the card is working. A refused avoid counts even while a retry is pending, and even when the same request is also too early or names a mode the class does not allow, since the avoid is checked before those: the mate tried to leave the failing provider and could not. The message to main then says that a retry is still pending and when it becomes eligible. A pending eligible retry holds back escalation only while no recovery has been refused. Any other refused restart is not a refusal that counts: waiting or a better request still reaches a recovery.
- The explicit-model refusal is the one that cannot be derived from the incident, so it is kept. `keepingRefusals` wraps every op. For an incident restart of an open incident, `card.restart` checks the direct parent, that the incident belongs to the card, the generation, and the card's current execution intent before it refuses the avoid. A request that fails one of these gets that error and records nothing. `AvoidRefused` carries the incident that the request named. A refusal of the request's own new `model` carries none, since the mate fixes that by naming another model, so it records no note and does not reach main. When `card.restart` throws it, a `restart-refused` check note goes on the card for that incident, in its own transaction, since the refused call rolled back. It records one note for each incident, and nothing for a restart that names no incident.

### Closing

`closing.ts`: close decides Done or Dropped from the record (guard 7, spec section 20.5), the way Firstmate's teardown did. A local-only card lands only when its landing is authorized: the card is Merging, by yolo or by the captain's approval. Then `close.begin` asks the host to land it. Done means landed. A merged PR landed everything. Otherwise the worker's latest handoff must be done. A task or comment routed to the worker takes that completion back, including a replacement attempt's task. Coordination routed to a mate or the captain does not: it asks no new work of the worker. A `stopped` report is not a handoff of its own: `doneStands` (`status.ts`) is true when the worker's last report that says anything about the work (not a `note`) is `done` or `merged` and nothing was routed to the worker since, and then the `report` operation drops a `stopped` report without writing it, so a stop after done changes no status and never blocks close. Done then `working`, `paused`, or `in-review` is not that case: a later `stopped` is written as before. The entry record is replayed for close and finished-card reminders, so a restart needs no separate completion state. A ship card must have no unmerged PR, and the host confirms that no attempt has a commit off the base branch or an uncommitted file. Dropped is never a fallback: the mate asks for it with `landed=false`, and a merged PR refuses it. A captain card has no worker, so it closes as Done once the captain acted. The record is checked again after the host confirms.

A scout closes Done only when the close names what happens next (`next-step.ts`). Two scouts, c-1357 and its revision c-1368, closed as "nothing built": the go-ahead to build had been in the mate's head and not on any card, so no reminder carried it. `close.begin` and `close.finish` take an optional `next` with exactly one of `build` (a ship card, open or Done, never Dropped), `decision` (an open card whose hold waits on the captain, so the card has the `needs-you` status and is on his list), or `drop` (the reason). The card must exist in the closing mate's reach, as for a dated hold's `remaining` step. A card with no hold, a hold that is still dated, or a hold that waits only on main is not on the captain's list, so it is refused: the mate makes the decision's card, holds it, and a second mate's hold waits for main to escalate it before the close names it. `closable` runs the check for both operations, after the work's own check, so `close.begin` refuses before the extension stops a worker or archives anything, and `close.finish` refuses a caller that never asked `close.begin`. `next` is refused for every other close: a ship or captain card, and any close that ends Dropped, so `landed=false` works as it did. The scout's cleanup entry records it in `fields.next` and starts its body with one line (`Next: c-N carries the build.`, `Next: the captain decides on c-N.`, or `Next: nothing is built, because <reason>.`), the line that the board shows collapsed. The rule runs when a scout closes and stores nothing on the card, so a scout that was open before it existed is held to it too, with no migration. An extension that still has the older `close` tool has no `next` to send: it can close a scout only with `landed=false` until its lane restarts on the new code. A newer extension talking to an older `cardd` sends `next` and `cardd` ignores it. When a second mate closes its own card, main hears. When main closes it, the card's mate hears. Close also supersedes the card's live incidents (see Runtime incidents).

## Extension

### Entry and arguments

- `index.ts`: dispatch starts each worker with `--fleet-url`, `--fleet-token`, and `--fleet-role`. `FLEET_URL`, `FLEET_TOKEN`, and `FLEET_ROLE` work too. A worker whose mate has a `bws` block also gets `--fleet-bws` (`FLEET_BWS` works too), described under Secrets from bws. A Pi in a lane home needs none of them: the home's `config/lane.json` makes it that lane's mate. Without either, the extension does nothing.
- `fleet-args.ts`: each value follows `=` in its flag, because Pi reads a separate value that begins with `-` as an option, and 1 `cardd` token in 64 begins with `-`. `launch.ts` turns the separate value of each option it takes, such as `--url <value>`, into `--url=<value>` for the same reason. It refuses `--token` before it reads anything else, so no token value is ever in its argument list or in a message.
- `.pi/extensions/fleet.ts` loads the fleet extensions only in a lane home. A worker in a worktree of this repository has no `config/lane.json`, so it loads nothing from there and needs no installed packages. Dispatch gives workers the extension with `-e`.
- Activity at each run and tool call keeps `last_activity` fresh for the stall check (spec section 12.2).

### Sessions

- `link.ts` holds the session's one websocket. It sends hello with the fleet entry IDs found in the session file, reconnects with backoff, and matches calls with their results. A close with code 4002 means a newer connection took the session. The link stops, the same as for 4001, so the old connection does not connect again and take the session back. A message from `cardd` that fails the protocol schema closes the socket with 4003 and the schema error as the reason, which reconnects with backoff, and the session says so once until it connects again. `cardd` logs that reason once for the session until the session sends anything else. A session that runs in a herdr pane also reloads itself, as `update_fleet` does: `MaintenanceQueue.reloadForStaleCode` relaunches Pi on the same conversation at its next safe point (its turn is over and no message waits), so that it loads the code on disk, which is the code that `cardd` runs. A result that fails its schema asks for the same reload. A reconnect does not cancel the request, because a welcome that parses does not show that the message or result that failed can be read: only the replacement process drops it. The relaunch passes `--fleet-stale-reload=<ms>`, and a process started with it does not reload again for 10 minutes, so a checkout that is behind `cardd` costs one relaunch each 10 minutes and not a loop. Jobs are not a reason to wait, because their results are queued in `cardd` and arrive when the session connects. A session that runs outside a herdr pane only says so. An exception in a websocket listener would end Pi, so a `cardd` on other code would crash-loop every mate.
- `cardd-watch.ts` is main's probe of `cardd`, started only for a mate whose lane is `main`. In flag or environment mode the lane comes from `FLEET_LANE`. Every 60 seconds it opens a fresh connection with no keep-alive and makes a timed call on the existing websocket, and labels the result `ok`, `slow`, `refusing-new`, `down`, or `unreachable`. A fresh connection that fails while the existing socket answers is `refusing-new`, decided before the port 22 control probe. After 3 failing probes in a row it tells main's own session once, and it tells once more when `cardd` answers again. A run of only `down` probes needs 5. It stays quiet while the lifecycle lock is held or the commit changes, and it never restarts `cardd`. `FLEET_PROBE_INTERVAL_MS`, `FLEET_PROBE_DEADLINE_MS`, `FLEET_PROBE_FAILS`, `FLEET_PROBE_DOWN_FAILS`, and `FLEET_PROBE_CONTROL_PORT` tune it. `e2e/extension/cardd-probe.test.ts` covers it.
- `plan.ts` fetches the mate's plan with `lane.plan` at the first connect, keeps it for the life of the process, and adds the goal and schedule to the system prompt in its own `before_agent_start` handler, after the role contract and the charter, waiting for a fetch that is under way. A plan that cannot be fetched is tried again at the next connect. Because it is read once, a changed plan applies at the next start. `wake.ts` is the `fleet wake` command: it posts the `wake` op with the lane's own token.
- `intake.ts` decides what the model took in from the fleet messages the process tracks, never from the requests Pi sends. A request is not a safe source: with conversation memory on, the request holds the memory's own projection of a fleet message, which has no fleet identity, and a failed request can be followed by a compaction that removes an entry before the retry. The process tracks the fleet entries that arrive through `message_end` and the ones already in the session file when it starts. A finished response (no abort, no error) sends `read` for the entries that arrived since the last one, and a settled run that ends without abort or error sends `ack` for every tracked entry. Every settle forgets the tracked entries, whether the run finished or not. A tracked entry is read or acknowledged only while it is still in the session's active model context at that moment, which is read from Pi's own session projection of the raw entries (compaction, the active branch, and context edits applied), so memory cannot hide it. An entry that compaction removed before the settle, whether before a restart, between the restart and its first request, or while a failed request was retried, is not read and not taken in, and the chase resends it. A run that ends aborted or with a failed answer acks nothing and forgets its entries, so a later run of the same process does not take them in even though their messages are still in its context. The chase resends them marked `again`, and the resent message is taken in by the settled run that follows. This holds for the abort and resume case and for a provider failure followed by recovery. The entries that were in the session file at start are tracked the same way, are dropped at the first settle whether or not it took them in, and send no `read`, because a filed entry does not block the report gate. Nothing is suppressed locally, so an entry that arrives again, which is how the chase and a connect push send one again, is tracked again, and an `ack` that `cardd` never received is made again by the next run that settles with the resent message in its context. The session file's own ID list (`idsInSessionFile`) goes to hello, to the push deduplication, and to this tracking at start. `link.ts` keeps a `read` or an `ack` made while `cardd` is unreachable and sends it at the next connect.
- The mate-only `yield` tool in `mate.ts` returns Pi's native `terminate: true` with empty content. It ends the automatic model follow-up without aborting, so normal settle, intake acknowledgment, activity, and conversation memory still run. Queued fleet messages still reach the model. Pi ends a tool block without another model call only when every result in it carries `terminate: true` (`shouldTerminateToolBatch` in pi-agent-core, unchanged from 1.0.0 to 1.5.2). A `tool_result` hook cannot set the flag (`ToolResultEventResult` has no `terminate`, and the session drops it), and the built-in tools never set it, so a block of yield with comment, hold, close, bash or any other call got one more model call, and the model filled it with chat such as ".". `registerYield` fixes this where Pi allows it: it keeps the result of every call of the current assistant message as the call ends, and once a `yield` has ended it sets `terminate` on all of them, including the ones that ended before it. A yield inside a codemode script counts too: Pi emits its `tool_execution_end` with `parentToolCallId`, and codemode does not pass a nested `terminate` on, so the hook ends the enclosing codemode call. Pi emits that event with the same result object that it reads for the block decision, and reads the decision only after every call of the block has ended, in sequential and in parallel mode. That is a mutation of an event payload, not a documented hook, so `e2e/extension/yield.test.ts` fails the day a Pi upgrade stops honoring it. A call of the block that fails does not stop the silent end: its error is in the transcript for the next turn, and the contract tells the mate to yield in a later block when the next step depends on a result. A message that arrives during the block is a steering message, and Pi still polls for it after a terminating block, so it starts a new turn. Its self-rendered call and result draw zero lines even with calm off. Silence never substitutes for a reply to the captain's own message or for one of the four interruptions in section 8 of `mate.md`. The contract ends every other turn that a fleet message started with `yield`: landings, relays, reminders, and results are not chat, and the board holds them, unless a result answers a question or investigation the captain asked for in a message of his that is still waiting: then the mate answers him once, as the reply. That rule is text, a request to the model, and no code forces it.
- `inbox.ts`: Pi skips session file lines that do not parse, such as a line torn by a crash, and so does the extension. Pi creates the session file late, so it may not exist yet. A time from the model must be ISO 8601 with `Z` or an offset, so no host's zone can shift it.
- `worker.ts`: a run may end only with a handoff, a tracked wait, or a queued continuation. Otherwise the worker gets one nudge, then files `stopped`. A run whose last turn failed gets neither: the failure is a runtime incident (see Runtime incidents). The extension remembers the last report it sent only as a hint for that nudge (`pauseHint`). It is not the card's pause: a mate's steer can resume the card while this process still remembers the old pause, and the timed check is what watches that card. Nothing is filed at a settle once the process is leaving, aborted or not, because a pane stop counts only while the process stays. The SIGTERM and SIGHUP handlers and the `fleet:leaving` event, which the maintenance relaunch emits before it asks Pi to shut down, mark the process as leaving, and cardd sees the lost connection as a runtime incident instead. Pi 1.5.1 and later abort a run that is still active when they shut down (`AgentSessionRuntime.dispose()` calls `session.abort()` first), and `agent_settled` then reports `aborted` just as it reports Escape. Pi 1.5.0, the version this repository pins, does not abort on shutdown, so there the e2e SIGTERM and SIGHUP tests pass without the guard.
- `worker.ts` also keeps the worker's herdr pane honest. The pane reads blocked only while `cardd`'s `standing` for the card says attention is blocked, never from the worker's own last report. It asks right after each report. While the pane reads blocked it asks again every 15 s (`FLEET_STANDING_MS`), so a mate's dated hold, a steer, or a close takes the red off, and a worker that waits on its mate with no hold keeps it. Herdr has only working, blocked, and idle, so a pane that is no longer blocked reads idle, not Waiting with its date. When `standing` cannot be read, the pane follows the report it just made, and a pane that reads blocked stays so. On session shutdown, including an in-process reload, the run stops asking and drops any answer still in flight, so a reloaded session never keeps the old run's timer alive.
- `prompts.ts` adds the role contract to the system prompt of every run, so the contract follows the role wherever Pi starts.
- `views.ts` prints `board` in the AXI shape (https://axi.md): TOON records, few fields by default, counts first, long text cut with its size, an explicit empty state, and next steps. It is pure. It prints a `dated` row for each dated wait, which main's catch-up reads, and a next step for an idle park. For one card it prints the `dated` line and the hold's `remaining` steps. The board's header is AXI ambient context: the projects with their yolo flag and, for main alone, the lanes. Past a set number of projects, it lists only those with open cards or yolo on. A second mate reads only its own lane through `board`, including its lane card and the cards it created. Main reads every lane. `cardd` scopes the `board` and `card` operations by the authenticated session's lane, so counts cover only visible cards and opening another lane's card tells a second mate to ask main. Projects remain shared. The captain's web board stays unrestricted. Mates never read with sqlite.

### Secrets from bws

- `bws.ts` is the one reader. `Bws.lookup(reference)` finds a secret by id (a UUID, `bws secret get`) or by key in `project`, then `common` (`bws secret list <project id>`). A project is named by its id only, and `bwsConfig` refuses anything that is not a UUID, so the reader never looks a project up by name. Another feature that needs a bws secret reuses it and `resolveSecret`.
- `bws` runs as a child with the machine-account token in that child's `BWS_ACCESS_TOKEN`, never in its arguments. `bws secret list` prints values, so the reader parses them in memory and keeps the list for the life of the `Bws` object, one list for each project. A failure becomes one fixed phrase: no `bws` on the PATH, a timeout, or its exit status with its first stderr line, cut short and with the token replaced. A JSON parse error is never passed on, because V8 puts a piece of the text in its message.
- `resolveSecret` returns the value and one note that names the source, never the value. The caller picks the fallback: `lane-secrets.ts` falls back to `token` in `config/lane.json` for the lane token, and to the variable the process already had for an entry of `bws.env`.
- A mate shows all its notes in one notice, because Pi's status line replaces the one before it.
- The mate reads its secrets in an async `session_start`, before `start()`, so Pi's first model call already sees the environment secrets. It hands `bws` to its workers as `--fleet-bws=<JSON>` inside `FLEET_PI_ARGS`. The JSON holds the token file's path, project ids, and the env map, so no value is in a worker's arguments. A worker resolves them on its own host, with its own `bws` and token file.
- A `run_long` job does not get these variables. Its tab is a new shell of the pane, so the fleet would have to write the values into the job's file or its command, and it must write neither.
- `fleet secrets` is the check before an old file goes. It resolves from bws only and compares the lane token with the file in memory, so it prints `the same as` or `different from` and no value.

### Dispatch and herdr

- `dispatch.ts`: `cardd` creates or finds the attempt. Each host step then looks for its own result by the names that derive from the attempt ID, so a retry after a lost connection never starts a second worker.
- herdr counts an agent as ready when it idles, and a worker starts on its task at once, so herdr's own wait often runs out. Dispatch does not rely on it: the pane shows whether Pi started. herdr's minimum wait is just above 3 s.
- herdr refuses a start and types nothing when the shell is not at its prompt yet, or when it still holds the agent name of a worker that died a moment ago, for up to about 4 s on CI. A refused start goes again at once. A command lost before the shell goes once more. herdr refuses a pane where Pi runs, so no second Pi starts.
- A new shell first runs its prompt's helpers, such as git, and keys typed then can be lost. So a start waits until the shell is idle.
- Pi in the worker's pane is the truth about a worker, because `cardd` may not have seen it die yet. Pi names its process `pi`: macOS reports it as argv0, Linux as the process name. Herdr may report the name as `MainThread`, so a `node` process running a script named `pi` also counts. A lane whose pane foreground is anything other than an idle shell counts as running, so a second `fleet up` does not start the mate again.
- `host.ts`: a host that is neither listed in `FLEET_HOSTS` nor this lane's own host (`host` in `config/lane.json`, `FLEET_HOST`, or the hostname) has no transport, and `NoTransport` is thrown before anything runs. Running its command here would act on this host's disk with another host's paths. The close and startup refreshes print `skipped: no transport for <host>`. A host listed in `FLEET_HOSTS` runs herdr through its transport, such as `["ssh", "p620"]`. ssh exits 255 for a lost or refused connection, which, like a probe that times out, means the host is unreachable. `--session` must come before a `--` delimiter, or herdr passes it to the agent. A command that runs to completion over a transport whose program is `ssh` goes through `runOnTransport` (`@fleet/protocol/transport`, a subpath export like `tunnel`), the one function that `host.ts` and every `cardd` route that does so (merged-PR check, empty-branch check, project repo lookup) call. The CDP tunnel (`@fleet/protocol/tunnel`) streams through its transport and does not use it. When such a run exits 255 and its error ends with `mux_client_request_session: send fds failed`, it runs the same command once more with `-o ControlMaster=no -o ControlPath=none` in front of the transport's arguments (the first value of an ssh option wins, so this beats `~/.ssh/config`). That line is the fatal that ssh prints after `mm_send_fd: sendmsg` fails, and ssh dies there. The master opens a session only after it has received all three descriptors, so the command never ran and the retry cannot run it twice. Any other 255, such as a connection timeout, is passed on as before, and when the retry also fails the caller gets the retry's error, so an unreachable host still says why. The other multiplexing diagnostics (`muxclient: master hello exchange failed`, `Control socket connect(`, `mux_client_request_session: session request failed`) are not retried, because ssh falls back to a direct connection by itself after them and the command may already have run. `mux_client_request_session: read from master failed` is not retried either, because the master may have started the command before it died. The cause is the size of one request: on macOS a mux client passes stdin, stdout, and stderr to the master with `sendmsg` and `SCM_RIGHTS` right after it writes the request, an AF_UNIX stream socket buffers 8192 bytes there, and XNU takes every byte that the master has not read yet off the sender's room, so a request that fills the buffer to within 16 bytes (the same just under each multiple of 8192) leaves no room for the descriptor and fails with `Message too long`, whatever the state of the master. The shared preferences push and the clone refresh script are the two requests that are 8 KB. `-O exit` would not help, because the next request of that size fails the same way, and it would end every session on that master. A herdr failure message never shows the command line or a worker token. A herdr call that fails with `server_not_running` starts the server detached and repeats once (`host.ts`); a `pane_not_found` from the foreground check means the pane is gone, so the lane counts as down. `e2e/extension/herdr-restart.test.ts` covers both.
- A command on another host runs through `routed` (`@fleet/protocol/route`), the one function that every caller uses to put a command behind a transport: `host.ts`, `cardd`'s checks of a clone and a pull request, and the CDP tunnel. It wraps the command in a short `sh` that appends the tool directories (`DEFAULT_TOOL_DIRS` in `route.ts`, listed in docs/setup.md under Prerequisites) to `PATH` when they exist and are not there, and then `exec`s the command. A non-interactive SSH session on macOS has no `/opt/homebrew/bin`, so `zstd`, `gh`, and `bws` were missing from it while they passed the prerequisite check in an interactive shell: on 2026-11-05 `close` on maverick from a mate on p620 failed with `zstd is required to archive`. A directory that is already in `PATH` keeps its place and the new ones go last, so a tool that was found before is found in the same place, and a host without these directories runs the command with the `PATH` it had. `FLEET_TOOL_DIRS` (colon separated) replaces the list. `e2e/support/launchd-transport.ts` runs a command with a bare `PATH` like launchd's, and `command-path.test.ts` dispatches, closes, and archives through it.
- A worker's `-e` is the extension of the host that it starts on, not of the mate that starts it (`extension-path.ts`). On the mate's own host it is the mate's own copy. On another host it is the extension in `roots.<host>` of the lane (`~/.fleet/app` if unset), and the dispatch refuses with the root it looked in when that checkout has none. Before this, the path of the mate's checkout went to every host. A second mate on p620 (`~/.fleet/app.worktrees/lane-yang-auto`) started c-1035 on maverick with a path that maverick does not have, and Pi exits with status 1 about a second after it starts when its `-e` file is missing. herdr counts the agent as started because Pi was in the pane for that second, so `restart_card` said it started the worker three times, and the pane that held Pi's message was closed by the next restart. Now a start that fails with no Pi in the pane throws the last 20 lines of the pane, and a Pi that is in the pane at first and gone within 3 s sends the mate a `[fleet] launch:` message with the same lines, after the tool has returned, so a healthy start waits for nothing. Both hide the worker token and the `--fleet-bws` value, and leave the pane open. Check the host's herdr log (`~/.config/herdr/herdr-server.log`) for `agent changed ... agent=None` a second after `agent.start`.
- The attempt's worktree is the one at `<clone>.worktrees/<session>`. The worker may switch to its own branch, so the path is the key.
- `place.ts` creates a worker's workspace, tags it with its lane and card, and arranges the host. `arrange.ts` owns the sidebar order: a worker's workspace sits right under its mate's workspace, labeled with the card's name after `└ `, because herdr does not nest plain workspaces, so order and label make the tree. The order is a pure function of the workspace list, so it is the same after any restart. The herdr CLI cannot move a workspace, so `arrange.ts` calls the socket API's `workspace.move_block`, once, only from the first workspace out of place. Ownership is a metadata token on the workspace (`lane`, `card`) because the host cannot ask `cardd`. A workspace with no token follows the workspace above it when its label starts with `└ `. A lane restart tags those followers before it closes the mate's workspace, so they keep their mate when it comes back at the end. `/updatefleet` tags the rest from the board, before it pulls anything. A failed arrange after a start or a dispatch only leaves the sidebar as it was. `/updatefleet` arranges every host once more at the end, through the same `arrangeOn`, even when no mate started there, and names each host that failed.

### Prompt cache policy

- `cache-policy.ts` sets prompt cache retention by role, when the extension starts a session. Every mate (main and each second mate) asks for one-hour retention, `long`. Every worker asks for the five-minute default, `short`. Fold mode keeps a mate's prefix stable (see setup.md), so a one-hour write is paid once and read for an hour, and the fold at cache expiry (`foldOnCacheExpiry`) refreshes the prefix only when it is cold. An earlier policy gave mates `short` because conversation memory rebuilt most of the prompt every turn. The role map covers a mate started by hand, by `fleet up`, and by a restart, and a worker started by `dispatch`, with no environment variable and no personal setting.
- `cache-ttl.ts` splits a mate's system prompt in two at an invisible marker that `index.ts` places after the role prompt: the stable block (base prompt and role prompt) and the mutable tail (lane plan, charter, standing rules, in that order). Each gets its own breakpoint, so an edit to `captain.md`, `learnings.md`, `charter.md` or `captain-shared.md` rewrites only the tail, and the first breakpoint covers the tools before it. A mate with no tail keeps one block and one breakpoint. OptChat replaces the provider's marks on the view and the end of the request with bare ones, which default to five minutes, so every surviving message mark is set to one hour here, at the final payload boundary. Anthropic allows four breakpoints, so when OptChat's view marks leave no room, the oldest message mark is dropped. It checks the payload shape, not the model api, so it also works behind a routed model. The expiry fold reads the cache lifetime of the physical model that answered last, not the routed model. Workers do not load it.
- Which providers honor `long`: Anthropic messages (`claude` accounts, and `vertex-claude` once it sets `supportsLongCacheRetention`) writes `ttl: "1h"`. `openai-codex` (`openai-codex-responses`) has no retention parameter and ignores it. `xai` (`openai-responses`) and `baseten` (`openai-completions`) have `supportsLongCacheRetention: false` in their model data, so Pi sends no long retention for them. A provider that ignores `long` keeps its own default lifetime, and its model has no `promptCache` lifetime, so the fold at cache expiry stays off for it.
- Pi has no setting for retention. `cacheRetention` is a request option that Pi's agent never sets, except `none` for compaction. The providers read `PI_CACHE_RETENTION` on each request, so the extension sets it in its own process. Each role sets its value and does not unset the variable, so a `long` that a session inherits from its launcher does not leak into it. A provider's own `env` in `auth.json` would still win over the process variable. The fleet does not write it.
- Warming is not managed per role, and the per-role policy for it is not implemented. `cacheWarming` is a global-only Pi setting, in `~/.pi/agent/settings.json`. Pi reads no project file, flag, or environment variable for it, and gives an extension no way to set it. The `cache_warming_decision` event can only stop a refresh that Pi already scheduled, so it cannot turn warming on. Every session follows the global setting. The wanted policy is idle warming for mates and streaming warming for workers. It needs a per-process way to set `cacheWarming` in Pi.

### Cache break log

- `cache-breaks.ts` runs in every fleet Pi (main, second mates, workers). On each answered request it compares the usage with the request before it in the same process. The first request is ignored, and so is a request that failed or was aborted.
- The rule: a break is a request whose `cacheRead` is below half of the prior request's `cacheRead + cacheWrite`, when that prior total was at least 1024 tokens (the smallest prefix Anthropic caches). A healthy request reads back the whole prior prefix and adds to it, so reading under half means the prefix broke. Half leaves room for a view that moves its marks, and the 1024 floor skips models that do not cache.
- The cause is the first that matches: `model` (provider or model id differs from the prior request), `compaction` (a `session_compact` event since the prior request), `system-prompt` (the hash of the stable system text changed), `tools` (the hash of the tool definitions changed), `idle` (the gap between the prior answer and this request is over the model's short cache lifetime, `promptCache.short`, else five minutes), else `other`. The system hash covers the text up to the mutable tail marker, or up to the first block with a breakpoint once `cache-ttl.ts` has split it (the stable head), so a change in the lane plan or charter tail, which sits after the one-hour breakpoint, is not blamed. The idle rule uses the short lifetime because the view breakpoint is the first to expire.
- Each break is a custom entry, `fleet-cache-break`, in the session file, so it is durable, sits with the session it belongs to, and needs no new path. The board or `jq` can read it. It holds the time, cause, provider, model, prior provider and model, `cacheRead`, prior cached tokens, idle seconds, cache lifetime, the system and tool hashes (12 hex digits), tool count, and the running count. It holds no prompt text, secrets, or tokens.
- The status line shows a third footer line with the cache state, never a break count. `cache warm 4m` is the time left, from the last answered request plus the cache lifetime. `cache cold` means it expired. The line never shows break history or causes: those are only in the recorded break entries. A request that read or wrote cache leaves it warm. A break whose response read and wrote nothing shows `cache cold`. A response with no cache use and no break shows no warmth. The lifetime is the `promptCache` entry of the model that answered last (`long` when `PI_CACHE_RETENTION` is `long`, else `short`), so a routed model uses the physical one. A model with no lifetime shows no line, and so does a new, resumed or switched session (`session_start`) until its first request. The line refreshes on an unref'd timer every 30 seconds, and at the expiry moment while warm, so it keeps moving while Pi is idle. The timer stops at `session_shutdown`. Times under a minute show as `<1m`.
- `e2e/extension/cache-breaks.test.ts` drives a tool change, a model switch, a system prompt change, and idle expiry (the fake cache lifetime is 12 seconds), and reads the entries and the rendered status line. It also waits for the line to go from warm to cold by itself.
- Idle warming has a second limit. Pi stops it after a run in a session that holds a custom message, such as the `[fleet]` messages every mate gets, because it compares the transcript by object identity and Pi rebuilds custom messages when it refreshes the finalized context. `/session` then shows `Inactive (conversation context changed)`. A fix in Pi is needed before idle warming helps a mate.

### Worker context policy

- `context-policy.ts` limits a worker's context when the extension starts a session. The effective limit is `min(the model's own window, 500K)`, so the 500K is a cap and never raises a window. Compaction runs at 80% of the effective limit: 400K on a 1M or 500K model, 217.6K on a 272K model, 160K on a 200K model. A mate keeps Pi's own limits. No personal setting and no project file changes.
- Pi 1.3.0 has no flag or environment variable for this. Its settings are files, and `compaction.reserveTokens` is one fixed number subtracted from the window, so no value gives 80% across windows from 200K to 1M. A worker runs in a worktree of any project, so the fleet cannot write a project file either.
- Where the window comes from: under a pi-tiers virtual model Pi stores a virtual model with window 0 and checks the physical model that answers. Before each request, `prepareRequest` routes and calls `AgentSession._exceedsCompactionThreshold(route.model, projection)` with the routed model. After each response, `_checkCompaction` takes the window from `_modelForMessage(message)`, the physical model that produced the message. Both are the routed model, not the virtual one. `SettingsManager.getCompactionSettings` receives only the selected (virtual) model, so it cannot know the window itself.
- The patch point: the extension wraps four members in the worker's own process, like the Calm presentation patches. `_exceedsCompactionThreshold` and `_checkCompaction` set the window they work on for the synchronous part of the call. `getCompactionSettings` turns it into `reserveTokens = 20% of min(window, 500K)`. `_exceedsCompactionThreshold` and `_modelForMessage` hand Pi a model whose window is capped at 500K, so the threshold and the overflow check never see more than 500K. A window that is unknown (0) leaves Pi's own settings, which never raise a window.
- `compaction-policy.ts` sends every compaction to the fleet's compactor, for every role. Pi's one shared summary step, `AgentSession._runDefaultCompaction`, serves manual and automatic compaction (threshold and overflow), so the extension wraps it and swaps the model. `compaction-model.ts` picks it: `tier/compact`, except for a CNP session, which tries `vertex-claude/claude-haiku-5-5` first and then `google-vertex/gemini-3.8-flash`, so company content never leaves Vertex. The CNP chain is hard-coded, not routed through `tier/compact`: the fleet cannot see which model a tier chain picks, a tier chain edit could send company content outside Vertex, and the CNP checks (provider, `~/cnp`) can hold without `PI_TIERS_RULE=cnp`. A model is skipped when it is not registered. A session is CNP when its provider is `google-vertex`, when `PI_TIERS_RULE=cnp`, or when its folder is under `~/cnp`. If the chosen tier model is not registered, Pi keeps the session's own model. If neither CNP model is registered, the compaction fails with a message that names both, whatever the session's provider. The OptChat memory summaries (mates with memory) use the same choice in `vendor/optchat/firstmate/loader.ts`; `compactorModel` and `compactorProvider` in `config/optchat.json`, and the profile's `compactor`, no longer pick it. Pi's own compaction is cancelled by OptChat for a mate with memory, so those mates use only the memory path. Pi 1.3.0 has no compaction-model setting, so the wrapper is the smallest point that covers every path.
- A model switch in mid-session needs nothing extra: each request is routed again and checked against the model that will answer. A session at 170K that a tier moves from a 1M model to a 200K model compacts before that request, because 170K is over the 160K of the 200K model. A session that goes the other way keeps its context until the larger model's 80%.
- A Pi that lacks one of the members makes the patch print `Fleet context limit: unavailable` and the worker keeps Pi's own limit. `e2e/extension/context-policy.test.ts` pins the behavior on the Pi version in [e2e/package.json](../e2e/package.json), so a Pi bump that moves a member fails it.
- The footer's percentage still counts against the real window.

### Chrome over CDP

The fleet has no browser of its own: no worker tool, no viewer, no logins, and no `browser_tabs` table (migration 029 drops it). `serve` still accepts a leftover `--browser`, ignores it, and logs one warning, so a launch command that still carries it does not stop `cardd` from starting. A later release will refuse it.

Two things stay in `@fleet/protocol` for a host's Chrome, and only [`@fleet/chrome`](#native-chrome-attach) and its tests use them:

- `cdp.ts` is the Chrome DevTools Protocol client: `Cdp.connect(endpoint)`, `send`, `listen`, and `parseCdp`, which checks an answer against a schema.
- `@fleet/protocol/tunnel` (`tunnel.ts`) is how a Chrome on another host is reached. `dial(route, address)` is a connect function: with an empty route (this machine) it connects to the address; otherwise it opens one TCP listener on `127.0.0.1` with a random port and, for each connection to it, runs `node -e <relay> <host> <port>` through the route (the host's transport argv, with the command appended as one string, as every other command on a host), which pipes the transport's standard input and output to the port on that host. `Cdp.connect` then goes to the listener, so Chrome sees an IP address in `Host`. The listener is made once for a host and lives as long as the process, and what the transport printed on a failed run is added to the connect error. It is a relay and not `ssh -L` because the transport is an argv prefix that runs one command, not necessarily `ssh`, and `node` is already a prerequisite of every host. It is a subpath export, not part of the barrel, so the board does not bundle `node:net`.

`e2e/support/chrome.ts` (`StandInChrome`) is a Chromium that listens for CDP as a host's Chrome does. The end-to-end tests of `@fleet/chrome` use it.

### Native Chrome attach

`packages/chrome` (`@fleet/chrome`) is for a host whose workers share one Chrome. It does not talk to cardd, the extension, or the board, and it imports only `@fleet/protocol`. Setup steps are in [setup.md](setup.md#the-hosts-chrome-and-the-captains-windows).

- The guard (`guard.ts`) is a loopback proxy in front of Chrome's DevTools port, and a worker dials it where it dialed Chrome. The captain types in an Xpra window on the host, so no process of the fleet sees his keys. Only Chrome knows, and the guard is the one place that DevTools traffic through the shared port crosses.
- The guard holds its own CDP connection to Chrome. `script.ts` runs in every page and frame and reports, through a runtime binding, whether a password field holds text or has the focus after a trusted pointer or key event. A page that merely focuses its own password field is not refused until someone uses it. `watch.ts` keeps that state for each page and frame and for each session that attached to them. The script also covers shadow roots. It wraps `Element.prototype.attachShadow` (it is installed with `Page.addScriptToEvaluateOnNewDocument`, so it runs before the page's own code), registers every root, open or closed, and listens on each one, because a listener on a closed root sees the real target and a listener on the window sees only the host. The script walks the open roots when it is injected into a live page and again when the document has loaded, and it walks the open roots inside a closed root when it is handed that root. A closed root cannot be seen from the page, so `Scanner` in `roots.ts` asks Chrome for them over the guard's own connection (`DOM.getDocument` with `pierce`) and hands every one, nested ones too, to the script. A look never skips a root that an earlier look handed over, because the parser can add open roots to it later. Looks of one session run one after another. A closed root that a page builds after it loaded by a route that the script cannot see, such as nodes moved in from a document that `Document.parseHTMLUnsafe` built, is not seen until the page loads or navigates again. A call of `setHTMLUnsafe` is reported by the script and looked at at once, and the tab is not unseen in the meantime, so a closed root that a page builds that way is exposed for as long as one look takes.
- `gate.ts` and `rules.ts` decide for each worker message and each Chrome event. While a tab reports a typed password, a method that can read the page (`Runtime.evaluate`, DOM, accessibility, screenshots) is refused, the events that carry typed text (console, WebSocket frames, `bindingCalled`) are dropped, and request bodies are cut from network events. The lists name what is allowed, and a method that is not named is refused. A session that the guard cannot place counts as typed while a password is typed in any tab.
- A read that was let through while its tab was clear is checked again when Chrome answers. `Watch` stamps each tab with the time it last became typed, and the `Gate` keeps the stamp of every read in flight (`epoch`). If the stamp changed or the tab is typed now, the worker gets the usual refusal and not the result. That covers a read that waits for a promise (`awaitPromise`) and a field that was typed and emptied again before the answer. A loss of the guard's connection to Chrome counts as a change.
- The guard knows what is typed only while `Watch` is connected to Chrome and has scanned its targets. Until then (before the first connect, after a loss, until the rescan), a read of a page, a frame, or a target that the guard has not identified is refused with `The browser guard is not ready`, and the events of those targets are screened as typed. A target that is known to be neither a page nor a frame stays clear. An empty target table must not read as nothing typed.
- A tab reads as unseen until every observation of it has succeeded, and every path to clear goes through one boundary, `observe` in `observer.ts`. The tab is unseen when it attaches, when a frame session attaches to it, when any of its frames starts to load (`Page.frameStartedLoading`), and when a frame commits a navigation (`Page.frameNavigated`). It is clear only when a look has succeeded that started after the parse of every frame that loaded: `DOMContentLoaded`, `load`, or `frameStoppedLoading` of the frame has arrived, or, for a tab that attached while it was loading, `document.readyState` of every context is not `loading` (the guard asks again on each look, and a context that does not answer or does not exist counts as loading). A look that started before the parse does not count, and neither does a look that started before a later navigation. A look is injecting the script into every context, enabling the events, and handing every closed root to the script. A look that fails keeps the tab unseen, and the slow tick (2 s) tries again for every unseen tab. If the parse of every frame that is loading has gone on for 10 s (`PARSE_WAIT_MS`, `--parse-wait-ms` of the guard, which the tests lower), the next look counts without waiting for it, so a page that never finishes loading does not keep workers out for ever. That makes the tab readable and nothing more: "readable" and "still parsing" are two facts. The tab stays in the loading set until the end of its parse really arrives (`DOMContentLoaded`, `load`, `frameStoppedLoading`, or the frame detaching) or its `readyState` is no longer `loading`, and the slow tick looks again for every tab in that set, readable or not. A closed root that the parser adds meanwhile is handed to the script by the next look, so the gap is one tick (2 s) between the parser building it and the guard seeing a password typed into it. A tab whose own session is gone is unseen. A worker's read waits up to 3 s for the tab and is then refused with `not ready`, a method that the guard allows while a password is typed does not wait, and the events of an unseen tab are screened as typed. A target that the guard cannot place is unseen while any tab is unseen.
- A target that Chrome has not announced to the guard is waited for 500 ms and is then unknown. It must not be taken for a page: a tool that attaches to every target (`chrome-devtools-axi`) sends resume commands to targets that only the browser owns and that the guard never hears of, and waiting for each of them to announce and settle stalled the attach by 5 s a target. A target of any type except a page or a frame is inert.
- The guard covers the shared DevTools port. It stops reads by habit and by tools that go through that port. It does not stop a worker that looks for Chrome's real loopback port on purpose: any process of the user can find it, as 9222 was before. The e2e tests drive the guard with Playwright and with raw CDP. Chrome runs with `--remote-debugging-port=0`, and the guard reads `DevToolsActivePort` in the profile folder on each connection, so there is no second fixed port and a Chrome restart is followed.
- `marker.ts`: every answer of the guard carries `x-fleet-guard: 1`. `fleet-attach` and `fleet-chrome xpra` look for it before they attach or start Xpra, so a port that answers without it, such as Chrome itself, is refused.
- `fleet-attach` (`attach.ts`) is the captain's launcher. It checks the guard over ssh with `curl`, because the guard's port is on the host and the Mac has no listener. It runs the Xpra client with `--window-close=disconnect` (the default closes the tab on the host, and the last window quits Chrome) and with `--reconnect=no`, because the client's own reconnect would attach again without the check. The launcher does that itself, with a pause that grows from `--retry-ms` to ten times that. It passes `--clipboard=no` to the client unless it is given `--clipboard`.
- Xpra exits 0 when the captain closes a window and also when the host says `server shutdown`. The launcher tells them apart by the client's own words, `server requested disconnect`. It keeps the last 26 characters of each of the client's output streams, because a read of a pipe can end in the middle of the phrase. If a later Xpra words it differently, a restart of the host's Xpra ends the launcher with 0 and the captain runs it again, which is the safe way to be wrong. Exit codes 1, 2, 8, 9, 18, 20, 25, and 26 attach again. Any other code ends the launcher with that code, because waiting does not fix a wrong password, a version mismatch, or a missing Xpra. An unguarded port ends it with 99.
- `fleet-chrome xpra` (`xpra-host.ts`) starts Xpra on Chrome's display for the host's service. It refuses to start unless the guard answers (98 when nothing does, 99 when something else does), binds one unix socket named `<host>-<display>` with mode 600 and no TCP, and stops Xpra when the guard fails two checks in a row, so there is never an attach path without the guard. The service restarts it. It starts Xpra with `--clipboard=no` unless it is given `--clipboard`. The clipboard works only when both ends say yes, and turning it on makes the captain's clipboard readable on the host by every process of the desktop user, workers included, so it is a decision for each host and for each attach ([setup.md](setup.md#the-hosts-chrome-and-the-captains-windows)).
- The fake `xpra` and `ssh` in `e2e/support` stand in for the programs on the captain's Mac. A run against real Xpra, Chrome, and ssh was done once on p620 and is in the pull request.

### Jobs

- `jobs.ts`: `cardd` records a job first. The wrapper posts the result, which arrives as a fleet entry, also after a Pi restart. Nothing runs a job again. A running job is a tracked wait.
- `stop_job` stops one named job of the calling worker. `cardd` decides ownership: `job.stop` finds the job only among the caller's attempt's jobs, so a foreign or missing job is refused before anything is signalled, and a finished one answers "not running". Only after that does the extension find the job's tab in the worker's own workspace and send ctrl+c to its pane. The wrapper stops its own process group and posts the usual `exited 130` result, so the result is reported the way an interrupt always was. The extension never signals by name or pattern, and `prompts/worker.md` forbids it for a worker.
- `shims.ts` and `packages/extension/shims/` stop `pkill` and `killall` for every session. Every session on a host runs as one account, so such a command signals every matching process on the host. The prompt rule alone did not hold: on 2026-10-24 an agent that had it in its prompt ran `pkill -f "node --test"` and ended another card's full end-to-end run. The extension puts that folder first in `PATH` when it loads, so the two refusing scripts win over the real commands, and `job.ts` does the same for `run_long`, so the shell itself decides what is a command: `grep pkill`, `command -v pkill`, and text that mentions the name still run. `sudo` and an absolute path bypass it by design. A shell builtin `kill` cannot be shimmed, so `guard.ts` also refuses a `kill` fed by `pgrep`, `pidof`, or `ps` with a regular expression. That is a heuristic, because guards catch ordinary agent mistakes and are not a security boundary (spec section 12.4). `kill <pid>` still runs.
- `job.ts` is the wrapper. It reads its job from a private file, so the token never appears in shell history. It keeps the last lines of output, whole across split reads and split characters. It sends heartbeats until the result is taken. A closed tab can take the wrapper down soon after its hangup, so it reports as soon as the command ends or a moment passes, and `cardd` keeps only the first result. A 401 means the attempt ended and nobody waits. The job row is `abandoned` by then, not left `running`.

### Recovery

- `restart.ts` is the parent's `restart_card` tool. It calls `card.restart` and, for `replace`, `replaceWorker` in `dispatch.ts`. With an incident it is the recovery of that incident, with its generation fence. Without one it restarts the same card's worker or lane mate on the same conversation, at most 3 times an hour for each card, and a repeated key does nothing. When the plan says `reconnect` (the card is paused, finished, or waiting, and the worker's process was disconnected), it starts the new process and posts no comment, because the comment that an ordinary restart posts would resume the worker. `dispatch` creates its own card and only starts new work. A repeated call finds the card by its name and the attempt that already started. A replacement finds the same attempt through a resumed `attempt.begin`, so no new attempt, branch, or token appears. It finds the pane's `pi` process by the pane's own process list, signals that pid with TERM and then KILL, and starts the new process only when the pane's shell is idle again. It never signals by name or pattern. If the old process cannot be confirmed stopped, nothing is started. The new process opens the same session id with the same arguments, so the conversation, the worktree, and its dirty files are the ones it had. A second mate is replaced through the existing `lane restart` of main. A request that repeats a key never stops a process: the plan says `repeat`, and a process that already runs is left alone, so a retry after a crash cannot kill the replacement it started. A second mate's repeat does nothing.
- Errors that happen before the extension loads, such as a Pi that exits at startup, are seen only by the watchdog, as a worker that never connected. The pane's output is not captured, so such an incident has no cause text and is classed `unknown`.
- `e2e/extension/runtime-failure.test.ts` drives real Pi workers and mates against a real `cardd` and moves the controlled clock. `e2e/extension/recovery.test.ts` replaces real herdr panes. They kill only the pids they started.

### Prerequisites

- Every prerequisite of a host is one table in `prerequisites.ts`: the tools with their floors and fixes, plus the conversation-memory profile of each home. `fleet up`, `fleet restart`, `fleet update`, use it, so there is one check and one set of messages. The profile check looks for both files the memory reads at start, `AGENTS.md` and `config.json`, because a missing one stops the memory and crash-loops the mate. `gh-login.ts` decides the gh login line from `gh auth status`, which exits 1 for every failure. Only "not logged into any" text, an empty `--json hosts` result, a rejected refresh token, or a 401 from GitHub says `gh is not logged in`. A timeout, a network error, a signal, a spawn error, or any other exit prints `warning: could not check gh login on <host>: <reason>` on stderr and does not refuse, with token-shaped text hidden. `fleet up --maintenance` skips the login check. `FLEET_PROBE_TIMEOUT_MS` sets the probe timeout.

### Review pages

- There is no review tool. A worker opens a Lavish page with `lavish-axi`, reports `needs-decision` with the page link so its mate hears that the page is ready, and polls with `run_long` (at most 2 hours for each job). A poll that times out is started again, and Lavish keeps feedback sent between polls until a poll takes it. The poll result is an ordinary job result for the worker.

### Closing on the host

`closing.ts` runs close in this order: stop every writer (close the worker's workspace, which ends Pi and its job tabs), stop every process whose working directory or command line names the worktree (`stop-procs.sh`: TERM, a bounded wait, then KILL; it matches whole path components and spares fleet's own processes and the host-shared no-mistakes daemons, see Process containment), archive and verify all unlanded work, remove the worktree, close the card, then clear the card's scratch folder on each host where it retired an attempt (see Scratch space). Ending Pi this way, or any exit by SIGTERM or SIGHUP, is not a pane stop (see `worker.ts` under Extension). Close's output lists each stopped process with its pid, short command, and TERM or KILL, names each shared no-mistakes daemon that it moved out of the worker's processes and kept (see Process containment), and says nothing when none ran. Each step finds its own result first, so a rerun converges. Closes of one card do not run together within one Pi process: `close` keeps one running close for each card. A second call for the same card that asks for no more than the running one (the same `landed` and `next`, and `confirm` only when the running one has it) returns the running close's result, so a duplicate finds the card closed once. Any other call waits for the running one and then runs on its own, so it reads the card as the first left it, usually already Done. The automatic close on a merged report asks for `confirm`, so it joins only a running close that has it, and otherwise waits and finds the card already Done. That single flight stops at the process: main and a second mate can both close a card of the second mate's lane, each in its own Pi, and `close.begin` only reads the plan, so cardd does not reserve the card. Such closes can overlap. The sweep of one spares the helpers of the other by the mark (see Process containment), and each step finds its own result first, but a step can still fail on the other's half-done work, and the second `close.finish` fails with `is already done`. When a close fails after `close.begin` and `close.begin` now says the card is Done or Dropped, it returns `c-N was closed by another close at the same time, so there is nothing left to do.` instead of the error. Any other failure is rethrown, and a close of a card that was already closed before it began still fails with `is already done`. A worker may have moved its worktree to its own branch, which goes too, after the archive. An unreachable host of an attempt that no longer runs cannot be asked, and its work stays in place. A commit has landed when it is on the base branch or on `origin/<base>`, because dispatch branches from origin's base, which can be ahead of the clone's. `ORIGIN_BASE_IF_FETCHED` names that ref when it exists, and `archive.sh` does the same. `UNLANDED_COUNTS_SCRIPT` prints the commits not landed and the changed or untracked files: the worktree decides while it exists, and its branch after. `DELETE_ARCHIVED_BRANCH_SCRIPT` deletes the task branch once its work is archived or landed. It tolerates only a missing branch, and is safe to rerun. A local-only card lands first, as Firstmate's `fm-merge-local.sh` does: `LAND_LOCALLY_SCRIPT` fast-forwards the clone's base branch to the newest attempt's branch, only when the clone is on its base branch and clean and the branch is a fast-forward, and never pushes. Any uncommitted file in a worktree refuses it first, so a landing never leaves work behind. A rerun after a landing is a no-op fast-forward. Last, close refreshes the clones that `close.begin` lists (see Clones). It lists none for a local-only card, and main's first refresh skips local-only projects, as Firstmate's fleet sync does, because their local base branch is ahead of origin by design. A host that just failed to answer is already named in the outcome, so it is not waited for again.

### Scratch space

[setup.md](setup.md#scratch-space-and-the-disk-alarm) owns what the folders are and when they go. Inside:

- `scratch.ts` runs on the host and holds the whole layout. Dispatch and close use two small `sh` scripts from it (`OPEN_SCRATCH_SCRIPT`, `CLOSE_SCRATCH_SCRIPT`) instead of `fleet scratch`, because they must work against a host whose checkout is older than the code that dispatches: `/updatefleet` moves hosts one at a time, and a dispatch must not fail because `fleet` on the target does not know a new command. The one thing that the scripts and the TypeScript share is the default folder, `${FLEET_HOST_DIR:-$HOME/.fleet}`, and `e2e/extension/scratch.test.ts` and `scratch-tidy.test.ts` check that both put a card's folder in the same place. They also share `host.json` in that folder, the host's one settings file: the move script and `scratch.ts` each parse it, with the same rules, and `scratch-host-setting.test.ts` checks that a close from another host and the host's own scratch report give the same folder.
- The variables go in at launch, as `--env` on `herdr workspace create`, because the compile cache is read when Node starts. By the time the extension loads, Pi has already enabled it in `/tmp`, and `module.enableCompileCache()` cannot move a cache that is already on. A second path from inside the extension would also leave Pi's own `os.tmpdir()` users, such as the extension loader's cache (80 files for each worker), on the old value. A herdr tab does not inherit the workspace's variables (measured with herdr 0.9.5), so `jobs.ts` copies the three variables that the fleet set into every `run_long` tab. It copies nothing for a worker that was not started with `FLEET_SCRATCH`.
- `TMPDIR` is a folder inside the card's, not the card's folder, so that close can remove the temporary part at once and keep the evidence. A worker that wrote evidence to `$TMPDIR` by habit loses it at close. The contract names `$FLEET_SCRATCH` for evidence.
- The name of a card's folder is its state, and each change of state is one rename. `c-<N>` is an open card. `c-<N>.closed-<epoch seconds>` (with `-<k>` added when that name is taken) is a closed card, and `.removing-<pid>-<id>` is a folder that the tidy is deleting. There is no marker file. The host cannot ask `cardd`, and a rule that guessed from file ages would delete the evidence of a card that waits for the captain for a month, so only the name says that a card is closed, and only close writes it.
- `clearScratch` in `closing.ts` runs once for each host where an attempt was retired, after every attempt is retired and cardd has recorded the close (`close.finish`), not in `retire`, because the attempts of a card share one folder on a host. `CLOSE_SCRATCH_SCRIPT` removes `c-<N>/tmp`, removes `c-<N>` when nothing else is in it (a card that wrote only temp files leaves no folder), and otherwise renames it to its closed name. A close that fails at any step leaves `c-<N>` as it was, which is the state that is kept. A close that cannot reach the host, or whose script fails, does not fail: the output names the host and the folder stays as `c-<N>`. A rename that fails inside the script is silent, with the same result. A file that cannot be removed inside `tmp/` (a root-owned file left by a container, for example) stays in the closed folder, and goes with it after 7 days. Close finds its own result first, so a rerun does nothing.
- `move-scratch.sh` (`scratch-move.ts` reads it) moves the old `/tmp/fleet-c-<N>` folder, and `clearScratch` runs it after `CLOSE_SCRATCH_SCRIPT` on the same hosts. It is a separate step from the rename to `c-<N>.closed-<epoch>` because the two folders have opposite rules: the closed folder stays on the same disk and the tidy deletes it after 7 days, while the old path crosses to another filesystem, leaves a symlink, and nothing deletes it. Routing it through the closed names would delete evidence that a symlink still points at. The script runs on the host from `sh`, as the other close scripts do, so a host with an older checkout still works. The order that [setup.md](setup.md#scratch-space-and-the-disk-alarm) lists is the safety. The second copy from the renamed original is there because a writer that does not hold the folder open can still write between the first verify and the rename. Verification compares contents (`rsync -c`), never size and time: a copy left in the stage by an earlier skipped run, or a write within the same second, can have the same size and time as the original and different bytes. Every rename is `rename(2)` through `node -e`, and the link is `symlink(2)`, as in the scratch scripts above: `mv` and `ln -s` onto a folder that a late writer made again at the old path would put the original, or the link, inside it. A failure at any step before the link renames the original back. A TERM, HUP, or INT in that interval takes the same path: the caller's 30 minute timeout sends TERM to the shell, and a lost ssh session sends HUP. `sh` runs the trap when the command that it waits for (the running `rsync`) ends, so the original goes back then and the skip says that the move was stopped. `say` writes to a saved copy of stdout (fd 3), because `sh` runs the trap while the `>/dev/null` of the interrupted `copy` is still in effect, and the skip line would go to `/dev/null`. The trap is armed before the rename and ignored from the link on, so the delete of the renamed original finishes and its result is reported. SIGKILL cannot be handled, and leaves the renamed original beside the stage. A failure after the link, in the delete only, leaves the renamed original beside the link and names it. The scan reads the cwd, open files, and mapped files of every process that `/proc` lets this user read; `lsof +D` is the fallback. It fails closed where the host gives it nothing to read: a `/proc` that this user cannot read, an `lsof` that prints anything but pids, and a host with neither skip the move, because not knowing is not the same as nobody holding it. It runs on the original and again on the renamed original: once the folder is renamed, nothing can open it by the old path, so a process that opened it after the first scan is found by the second. A process whose entries this user cannot read is invisible to the scan: a process of another user (a root daemon, a container), and also a process of this user that is not dumpable, such as `ssh-agent`. Skipping on every unreadable process would skip every move on a host that runs one of those, so this is the one blind spot, and the ownership check is what stops a folder that such a process filled with its own files. `FLEET_TMP_SOURCE_DIR` replaces `/tmp` as the folder that holds `fleet-c-<N>`; `e2e/support/run-root.ts` sets it, so no test touches the real `/tmp`. The destination root is `tmpScratch` in `host.json`, and `watchedFilesystems` in `scratch-use.ts` watches it, so the disk alarm names it when it fills. It is a file on the host and not an environment variable because the script runs in the environment of whoever starts it: the closing mate's own Pi process for a close on the mate's host, and the host's non-interactive ssh session for a close from another host, and the alarm reads a third one. A setting in any of those reaches only some of the readers. A file in the host folder reaches all of them, and an invalid file fails loudly (the move skips with the reason, `fleet scratch` exits) because a quiet fallback would put the folders on the small home disk that the setting exists to avoid.
- `OPEN_SCRATCH_SCRIPT` makes `c-<N>/tmp`. When `c-<N>` does not exist, it first renames the latest closed folder of the card to `c-<N>`: the highest time in the name, then the highest `-<k>`, both compared as numbers. When that rename fails (the tidy took the folder first, another reopen did, or there is none), the folder it makes is a new one. Every path ends with a live `tmp/`, and the script fails only when that is not so (a full disk, for example), which fails the dispatch before a worker starts. Older closed folders of the card stay under their names until the tidy. `fleet scratch --open <N>` runs the same script, so that a person or a test can reopen a card as dispatch does.
- A rename is `rename(2)` through `node -e` (`fs.renameSync`), never `mv`. `mv a b` moves `a` into `b` when `b` is a folder, which would put a closed folder inside a live one. `rename` fails with `ENOTEMPTY` when the target has content, so nothing is ever nested, and it replaces an empty target folder, which is harmless: the reopen that made that empty `c-<N>` has `mkdir -p c-<N>/tmp` still to run, and it ends with the same live `tmp/` either way. `node` is on the path of every host, because `bin/fleet` is `exec node`.
- The tidy removes a closed folder when the time in its own name is 7 days old. It matches only real folders called `c-<digits>.closed-<digits>`, with an optional `-<digits>`, and never follows a link, because a link there would make `rm -r` reach outside the scratch folder. It renames the folder to `.removing-<pid>-<id>` in the scratch folder and deletes that. When the rename fails, because a reopen took the folder first, it skips it. It reads no file, and it never touches `c-<N>`, so an open card, however old, is not its business. It deletes the `.removing-*` folders that a crashed tidy left. It prunes the compile cache by the time a file was written, not read. A hot entry is rebuilt once after 2 days, which costs less than a bound that needs read times.
- There is no lock, because no two of reopen, close, and the tidy can act on the same name in a way that breaks the other. Close acts on `c-<N>` and makes a closed name. Reopen turns a closed name into `c-<N>`, or makes `c-<N>`. The tidy acts only on a closed name that is a week old. Two that want one closed folder race on one rename, which has one winner: the reopen that loses makes a new `c-<N>/tmp`, and the tidy that loses skips. Nobody reads a state and then acts on it, so there is no half state to observe. A crash between two steps leaves `c-<N>`, which is kept, or a `.removing-*` folder, which the next tidy deletes.
- A filesystem owns the watched roots that live on it. `watchedFilesystems` in `scratch-use.ts` looks at `/tmp`, the temp folder, the host folder, and the move destination in that order, and keeps every root under the filesystem that holds it (a destination inside a root already kept for its filesystem, as `~/.fleet/tmp-scratch` is inside `~/.fleet`, is not a second root, because the listing would name the parent and its child for the same bytes), so `/tmp` and `~/.fleet` on one disk are one filesystem with two roots, and the first root is its `path` (and its key in the alarm state). The `--json` report lists `roots` for each filesystem, and a report without `roots` means `[path]`. It also carries `tmpScratch`, the destination that the host's own `host.json` gives, which the alarm does not read and the end-to-end tests do. `fleet scratch --largest` takes the option once for each root and ranks the entries of all of them together, so a crossing caused by `~/.fleet/node-compile-cache` or `~/.fleet/scratch` is named even when `/tmp` is empty. A filesystem with one root, the p620 `/tmp` tmpfs, is ranked and worded as before.
- `fleet scratch --largest` counts with `lstat` on every file and does not cross into another filesystem, as `du -x` does. It checks a budget of 20 seconds, for all roots together (`FLEET_SCRATCH_WALK_MS` changes it), before it opens each root, before each child of a root, and before each queued entry below it, and when the budget is spent it stops there, without draining what is queued, and says `partial`. A root that cannot be read is skipped, so the roots that can be read still answer. If none can be read, the call fails, and the alarm says that the directories could not be read. It runs only when main sees a crossing, never on the minute check. `du --inodes` would be shorter, but macOS has no `--inodes`.
- `disk-alarm.ts` is main's half. Main's session file is the only record of what it has said. The alarm is a custom message of type `fleet-disk` whose `details.crossing` is the key: the host's name in the lane config, filesystem path, and metric (`host|/tmp|inodes`). It does not key by the name that a host reports for itself, because main's own host and a configured host can answer to one name. When a use drops below the alarm, main appends a custom entry `fleet-disk-cleared` with the same key. Main keeps no set of held crossings. At every check, `heldIn` reads the session's entries (`ctx.sessionManager.getEntries()`) in order: a `fleet-disk` message holds its key and a `fleet-disk-cleared` entry releases it. A transition counts only once Pi has appended its entry, and Pi removes an entry from the session when it cannot write it, such as on a full disk. `message_end` is not that point: Pi emits it to extensions before it appends the entry. Pi writes a brand-new session's file only once the session holds its first user or assistant message, and keeps every entry in memory until then. So an alarm that comes first in a session is in the file only after the first assistant message ends. A main that is killed before that has no session file to continue, and says the alarm once more after the restart. That is a repeat, never a loss, and it is accepted. Otherwise a restart with `--continue` does not say a crossing again, a message that Pi did not append is said again on a later idle check, a `fleet-disk-cleared` entry that Pi did not append is tried again at the next check below the alarm, and a new session (`/new`) starts with nothing held. There is no state file and no timer. Main sends an alarm only when Pi is idle: no turn runs and no message waits (`ctx.isIdle()` and `hasPendingMessages()`), checked before the directory listing and again before the send, and at most one alarm for each check. Pi keeps a message sent during a turn in memory until the turn ends, writes the session file late, and drops that queue when the captain stops the turn, so a queued alarm could be lost while the crossing counted as said. An alarm that waits for an idle main is neither queued nor held, so a long turn delays it and loses nothing. A directory listing that fails sends nothing and leaves the crossing unheld, so the next check asks again and the alarm that arrives names the directories. After 3 consecutive checks in which the listing for one crossing failed, main gets the alarm once without the list, the message says so (`The largest directories could not be read.`), and the crossing is then held as said, because an alarm without the list is better than none, and a host that can never list cannot silence the alarm. The count is in memory, and a use that drops below the alarm clears it. A crossing is forgotten when the use is below the alarm again, with no margin: the captain's rule is "dropped below and crossed again". Inodes and space are separate keys. It reads the use in one call and the directories in a second call that only a crossing makes, which passes every root of the crossing's filesystem. A host that cannot be reached is the lanes check's to report, and the probe leaves that to it.
- The alarm and the tidy run on main's minute check and its host transport, not on the host's own cron, so one place decides who hears and each host needs nothing installed beyond the checkout. They run whether or not `fleet up --maintenance` worked on that host, because a lane that cannot start (a full disk, for example) is when the alarm matters most. A host that cannot be reached skips both. The tidy runs when the check has not asked that host for an hour, which a restart of main resets: the work is idempotent, so a second run does no harm.
- `e2e/support/run-root.ts` sets `FLEET_HOST_DIR` to a folder in the run folder, so no test touches the real `~/.fleet`, and a failed or killed run takes it away with everything else. `e2e/support/disk-transport.ts` is the transport of a fake host. It answers the `fleet scratch` calls from files that the test writes and runs every other command for real. That is the process boundary of the faked use.

### Process containment

`containment.ts` runs one shell script on the host: `lib.sh`, `service.sh`, one backend, then `main.sh`. On the systemd backend, only the pane's shell and Pi start the scope, as a delegated scope. `StartTransientUnit` fails the whole call when any listed pid has already exited, and a pane shell that keeps starting short-lived children leaves such pids in the list. The rest of the tree is attached with `AttachProcessesToUnit`, one pid at a time, and a pid that has exited is skipped. Writing the pids to the scope's `cgroup.procs` does not work: herdr usually runs in the login session's scope, and a user cannot move a process out of `session-N.scope` into the user manager's subtree, because their common ancestor, `user-<uid>.slice`, belongs to root. systemd moves the process on the user's behalf, but only into a delegated unit. systemd replies to `StartTransientUnit` once the start job is queued, before the scope's cgroup exists, so `await_cgroup` polls for the cgroup, at most 5 seconds. There is no event to wait for in a shell: the end of the job is a bus signal that must be subscribed before the call, and `busctl wait` needs systemd 257, while Ubuntu 24.04 ships 255. `e2e/extension/contain-churn.test.ts` covers the attach. It reaches the systemd backend only on a Linux host with a systemd user session, and it meets the permission limit only when the suite runs from a login session's scope, as an ssh shell or a herdr pane does, not from inside a user manager unit.

A `run_long` job runs in its own herdr tab, and that tab's shell is a child of the herdr server, not of the worker's shell. Without a step of its own, everything a job starts sits outside the worker's unit, so a server that the job detached and started from `/tmp` outlives `close` and `restart`: the unit does not hold it, and the cwd sweep of `stop-procs.sh` finds it only when its cwd or command line names the worktree. `Jobs.launch` therefore calls `joinContained` between creating the tab and running the wrapper: the `join` action of `contain/main.sh` moves the tab's idle shell into the worker's unit, so that every process the job forks is born there. It joins before the wrapper runs, because a process forked earlier would stay outside. `join` never creates a unit. It does nothing when the worker's unit does not exist, as for a Pi that no dispatch started or a worker that began before containment. It fails when the backend cannot tell, as when `systemctl` does not answer, so that the wrapper does not run outside the unit. The unit is named from `process.cwd()` the way dispatch names it from the worktree path. The cgroup backend places the unit's folder next to the caller's own cgroup, and `join` runs inside the unit, so `cgroup.sh` drops a trailing unit name from the caller's cgroup first: the mate that dispatches and the worker that joins find the same folder. The sweep backend does not join: a process group cannot hold a process that left it, and the recorded group of a finished job could name an unrelated group once its pid is reused. `e2e/extension/process-containment.test.ts` closes a worker whose job detached a server, once on the host's backend and once with `XDG_RUNTIME_DIR` pointing at an empty folder, which hides the systemd user bus and so selects the cgroup backend. That second run is skipped where `detect.sh` does not pick the cgroup backend without the bus, as on a host that does not let a user create cgroups: the sweep backend cannot hold a detached server. On a systemd host it also runs a job while a `systemctl` shim on `PATH` stops answering after the worker's unit exists, and checks that `run_long` fails with the join error and that its command never runs. The fixture server writes its pid next to its port, so that the test kills it when it fails, and registers the same kill with the e2e reaper for a runner that dies, so that a failed run leaves no server on the host.

A cgroup or a scope is stopped as a whole, so sparing a process means moving it out first. `reap` in `lib.sh` asks `service.sh` for the host-shared daemons (`shared_daemons`) and for everything under them (`service_tree`, by `ppid`), and moves the members that sit in the worker's unit with `backend_adopt`: into the `fleet-host-no-mistakes` scope on systemd (with `reset-failed` first, because a scope that ended with a failure keeps its name), and into a sibling cgroup on the cgroup backend. The daemon moves first, so that a child that it forks while the rest moves already starts in the host unit, and the listing is read again until no service pid is left in the worker's unit. If the move fails or does not settle in five rounds, `reap` exits before it signals anything, because a close that refuses is visible and a close that kills the daemon is not. The sweep backend cannot move a process out of a process group, so its `backend_adopt` always fails: a member of the group that is a shared daemon refuses the cleanup. `stop-procs.sh` asks `shared_daemons` and leaves each daemon and every process below it out of its victims. It finds that tree in the same `ps` snapshot that picks the victims, by walking `ppid`, so a step that the daemon forks after the daemons were found is spared too. It needs this because it finds processes by cwd and command line, which the daemon and its steps have when a worker started it. A daemon is told from a lookalike by what the daemon itself keeps: its argument vector and the pid in `<root>/daemon.pid`. A name alone is never enough, and a daemon whose executable or root is inside the worktree is the worker's own. A daemon that is still starting has not written its pid file yet, and a cleanup that read the missing file as permission to kill would take it along. So a candidate with the right argument vector and a root of this user also counts while it is younger than 60 seconds (`ps -o etime=`, which macOS has, unlike `etimes`) and `<root>/daemon.pid` is missing, names no live process, or names the candidate. A candidate whose pid file names another live process stays a lookalike, and an older process without a matching pid file is stopped. `e2e/support/fake-no-mistakes.ts` stands in for the daemon with the same argument vector, pid file, socket, log sink, and a step process, and for the client that starts it detached from the worker. `FAKE_NM_PUBLISH_AFTER` names a file that the fake waits for before it writes its pid file, so that a test can close a worker while its daemon is still starting. `e2e/extension/shared-daemon.test.ts` closes and restarts a worker whose pane started the daemon, next to a lookalike with a pid file that names another process and a daemon rooted in the worktree, which must still stop. It also closes a worker whose job tab started the daemon, and one whose daemon has not published its pid file yet. The tests run `detect.sh` for the host's backend. The daemon, its log sink, and its step must survive on every backend. The `Kept shared services` line, and a restart stopping the lookalike and the worktree's daemon, are required only where the backend is not `sweep`: there the daemon is already outside the group, so nothing is moved and the close result does not claim it, and a restart sends no cwd sweep.

`stop-procs.sh` also leaves fleet's own helpers out of its victims, because a helper's command line and working directory name the worktree just as a leftover's do (`archive.sh` even runs inside it). A helper is told from the worker's processes by a mark, never by its command line: every process that `closing.ts` and `containment.ts` start on a host to look at or change a worktree goes through `onHelper` in `host.ts`, which runs it as `env FLEET_HELPER=1 <command>`. The variable is in the environment from the first instruction, so no registry is needed and there is no window in which a new helper looks like the worker's, it crosses ssh, and every child inherits it. The sweep reads it from `/proc/<pid>/environ`, or, where there is no `/proc`, from what `ps -Eww` prints after the `ps -ww` command line (never the command line itself), and checks only the processes that would otherwise be victims. `helper_mark` in the script comes from `HELPER_MARK` in `host.ts`. A process counts as a helper when it or any ancestor carries the mark, and a process that is gone by the time it is read is not listed at all. Never start a long-lived process of the worker through `onHelper`: it would carry the mark and no cwd sweep would stop it. `e2e/extension/close-procs.test.ts` closes one card twice at once (the fake model's `alongside` field makes two parallel tool calls) while a leftover ignores TERM, closes a card while its merged report closes it automatically, plants a process that carries the mark in the worktree, stops a leftover whose command line copies a helper's or carries the mark as text (alone, or in its parent's), and closes the card from another session while a close is stopping the leftover. Restart and recovery (`replaceWorker`) do not run `stop-procs.sh`. They run `releaseAll`, which signals only the members of the worker's cgroup, scope, or process group, so they never take a helper. Their own helper carries the mark, so a close that runs at the same time leaves it alone.

### Clones

Clones keep up with their remote the way Firstmate's `fm-spawn.sh` and `fm-fleet-sync.sh` keep them. `sync.sh` is a POSIX port of `fm-fleet-sync.sh` and `fm-lock-lib.sh`, because a host's `sh` may be dash. It defines functions only, and each caller appends its own call.

- `ADD_WORKTREE` in `clones.ts` is the one script that makes a worktree on a new branch. Dispatch runs it for a worker and the Files tab runs it for a scratch worktree (see [The Files tab](setup.md#the-files-tab)). A new branch starts at `origin/<base>`, fetched just now, with no tracking, so a push never goes to the base. A failed fetch, or an origin without the base, refuses the dispatch or the scratch worktree rather than start from a stale base. A clone with no origin starts from its own base. A rerun that finds the branch reuses it without fetching.
- `refresh_clone` fetches with `--prune`, deletes branches whose remote branch is gone unless a worktree has them checked out, and fast-forwards a clean base branch. It never forces, stashes, or discards. A clone that needs attention is left alone and printed as `STUCK`: on another branch, detached with its own commits, diverged, or dirty and not level with origin, because a fast-forward would touch uncommitted work. A base branch level with origin needs nothing, so its uncommitted files are left alone and the line reads `up to date, uncommitted files left alone`. A clean detached HEAD with no commits of its own goes back on the base. A folder inside another repository is skipped, because git looks upward and would refresh that one. A fleet home (it has `config/lane.json`) is only fetched: it moves with `/updatefleet`, which also builds and restarts.
- `fetch_origin` retries a fetch blocked by `packed-refs.lock` three times a second apart, since a live owner soon exits. It then removes the lock only when it is at least 30 s old and `lsof` proves that nothing holds it or the clone. Any doubt keeps the lock.
- `clones.ts`: `close.begin` lists every host's clone of a ship card's project. A scout changes nothing on the remote, as in Firstmate's teardown. Two host names can lead to one clone, so clones are refreshed in turn. A fetch over a slow link gets 120 s. Main refreshes every registered clone when it first joins `cardd`, as Firstmate's session start does, and wakes only for a `STUCK` clone, the one state that Firstmate's bootstrap diagnostics mark as needing attention. A clone that is level with origin and holds uncommitted files is not `STUCK`: Pi rewrites its own settings in a clone, so that state is normal. Other lines wait for main's next turn.

### Lanes and homes

- `homes.ts`: main's home is the repository. A second mate's home is a worktree, `<root>.worktrees/lane-<lane>`, that shares the root's installed packages. A lane is running (its mate is in the pane), down (it should run and does not), or stopped (held by hand or for crashing, so only `up <lane>` starts it). A lane that starts too often within a window is held. Naming a held lane lifts the hold and forgets its crashes. A lane that is running is never held: a sweep that finds a mate in the pane deletes `state/stopped`, and `restart` of every lane restarts a running lane that still has the file, because the file only says what was true when it was written. `--continue` keeps the mate's conversation across a restart. A start defaults to `--model tier/orchestrator`, or the lane's `tier` from `config/lane.json`, because `--continue` would otherwise resume the model that the session last used. Explicit `--model` or `--provider` flags in the lane's `args` take precedence and are preserved (`mateStartArgs` in `lane-config.ts`), including routes tied to a lane's separate identity. `direnv exec` loads the folder's `.envrc` and replaces itself with Pi.
- Starting a mate waits until Pi shows in the pane. Until then the pane looks idle, and a second `up` would type the command again.
- `lifecycle-lock.ts`: `up`, `stop`, and `restart` own a lane only inside a `BEGIN IMMEDIATE` transaction on `<home>/state/lifecycle.db`. Each `fleet` command is its own process, so an in-process queue cannot stop a supervisor's `up` and a `restart` from both finding the lane down and both starting it. SQLite's lock is held by the open file, so the OS releases it when its owner dies, and no stale owner is ever reaped by age or PID. The database holds no rows. A command that waits longer than `FLEET_LIFECYCLE_WAIT_MS` (45 seconds by default, longer than one start) fails and changes nothing.
- `lanes.ts`: each host runs its own `fleet` for its lanes. Main reaches its host directly and the others over their transport. A non-interactive shell does not expand `~`, so a remote checkout path is given whole. A host that cannot be reached is named, never skipped, and reported once until it answers.
- A worker never takes its model from its folder. The fleet repo's `.pi/settings.json` puts the mates on the orchestrator tier, and every worktree of the repo has that file. So unless `workerArgs` name a model, dispatch starts workers on Pi's global default model from the agent folder's `settings.json`.
- Dispatch's optional `model` selects one worker's launch through Pi's existing `--model provider/id` flag. It removes both forms of the lane's `--provider` and `--model` flags first. The mate chooses the newest suitable `openai-codex` GPT from the live catalog for writing or reviewing non-English text. There is no language detector and no model version in fleet. Other work keeps its normal model. The chosen model is stored in the attempt's `model` column and returned by both begin and resume. Dispatch retries and ordinary or incident recovery therefore keep the same explicit model. A retry that asks for a different explicit model is refused. Only `restart_card(model)` from the card's own mate changes it, and it sets the worker's model whether or not the worker was dispatched with an explicit model. It applies only when a worker's process is replaced, and it leaves a note on the card's thread when the model changes. The restart runs in one `cardd` transaction. It plans the restart first and stores the model only for an accepted restart that is not a repeat of an earlier key, so a refused or repeated restart leaves the model as it was. The new model is stored before the process starts, so every later restart launches it too. A pin such as `tier/visual` hands the worker back to the router, which is how a worker leaves an account that cannot serve it. A restart whose `avoid` names the provider of the model it will launch (the new `model` when one is given, otherwise the card's stored model) is refused in `cardd` before the restart or its incident recovery records anything, since `PI_TIERS_AVOID` reaches only the tier router and the accounts of a `tiers.json` group, and the model flag would otherwise start any other excluded provider directly.
- Why an explicit dispatch option: lane-wide `workerArgs` would change unrelated work. Installed pi-tiers supports a `Model override:` task line, but only when its private config enables it, and the override joins a chain that can fall back to Claude. The currently configured tiers are not GPT-only. A worker cannot switch its own chat model through codemode. Pi's launch flag selects the provider directly without requiring a router change.
- An explicit model pins the model, not the account. `account-rotation.ts` runs in a worker's own process. At `session_start`, when the model Pi started on is a physical model whose provider is a member of a `tiers.json` `accounts` group, it registers the virtual model `fleet/pinned` and selects it, then restores the thinking level, because Pi picks the level again on a model switch. Its `route` serves the pinned model from the pinned account first, then from the group's other members in order, skipping a member that does not serve the model, has no credentials, is named in `PI_TIERS_AVOID`, or is cooling. It keeps the account that answered last, so a cache stays warm. A worker whose provider is in no group, a tier worker, and a mate are not touched.
- Why a virtual model and not a restart: the move happens inside the same turn, on the same card, conversation, and branch, without a mate. A `message_end` handler sees every failed turn of a pinned account. 429 or rate-limit text cools the account for `cooldowns.rateLimitSeconds` of `tiers.json` (600 if unset). Quota text (the `vendor-quota` pattern of `classify`) cools it for `usageLimitSeconds` (3600 if unset). The record is a custom session entry, so a replaced or restarted process, which resumes the same session file, restores the unexpired ones and does not start on the account that ran out.
- The move does not wait for Pi's retry. Pi never retries some of these texts (`insufficient_quota`, `billing`), and retries can be switched off or spent. When another account is usable, the handler rewrites the failed message to `fleet: <account> is <why> for <model>; continuing on another account.`, which Pi does not retry. `agent_before_settle` then appends a one line custom message and asks for one more request. `route` runs again for that request and picks the next usable account. A chain of limited accounts is walked in one turn, with no incident and no replacement. `Failures` reports a turn's error only at `agent_settled`, after the continuation, so a failure that continued never reaches `cardd`. An account that failed is not tried again until a turn goes through or a new run starts, even when its cooldown ran out meanwhile (`usageLimitSeconds` can be as short as one second, and a slow account can outlast it). So a chain of failures ends after the accounts the group has, and cannot circle back past a healthy one.
- When no account is usable, the failed message, or `route` when it is asked with every account blocked (a replaced process whose accounts are all cooling, or `PI_TIERS_AVOID`), carries `fleet: no usable account for <model>: <account> (<why>), ...`, which names the model and every account that cannot serve it with its reason (`throttled until <time>`, `out of quota until <time>`, `throttled in this run` and `out of quota in this run` for an account whose cooldown ran out but that already failed in this run, `does not serve it`, `no credentials`, `avoided by the restart`). It replaces the account's own error text, and Pi does not retry it. `classify` reads it as `router-cooldown`, and `accountResumeAt` hands cardd the earliest `until` as `resumeAt`, so the recovery waits for the first account to free instead of spending its retries. An account that is already free for a new run (`in this run`, or an `until` that has passed) counts as free now, so it gives no `resumeAt` and the recovery takes its ordinary delay instead of waiting for a later cooldown. This also covers a pin whose group has no other account serving the model: the first 429 or quota failure ends the turn with this text. The cooling is in memory and in the session only. It never writes pi-tiers' cooldown files, and a tier worker's cooldowns do not move a pinned worker.
- `titles.ts` owns the mates' names: `1stmate` for main, `2ndmate-<lane>` for a second mate. A mate gives its Pi session and its herdr workspace that name at start, so main gets it too, though the captain opens main's workspace by hand. Workspaces are still found by the earlier `fleet-<lane>` label, because a mate that started on earlier code keeps that label until it restarts. A mate renames the workspace in `HERDR_WORKSPACE_ID` only when its Pi holds a terminal. Every child process of a pane inherits that variable, so a mate-lane Pi that only inherited it, such as one an end-to-end test starts with piped stdio from a worker's shell, would rename the worker's workspace. A mate whose Pi starts in a workspace with another label, which includes the relaunch that `/updatefleet` does, renames that workspace to its own name, so a wrong label on a mate's workspace corrects itself.
- `provision` (`fleet home add`) converges. It makes the worktree only when the home's folder is missing, and adopts a folder that is already a worktree of the root (made ahead, or left by a crashed run), then links `node_modules`, makes `data/` and `state/`, writes `state/stopped` when `--hold` is given, and writes `config/lane.json` last, by rename. A home is invisible to `laneHomes`, and so to every pass, until that file exists, so a half-made home is never started, and a held one is held from the first moment. `launch.ts` returns early when the home's `config/lane.json` exists, without needing the token. `--token-file` reads the token from a file or from standard input (`-`) into memory, so it is in no argument list, and no message names it. `home add` has no `--token`: `launch.ts` exits with status 2 on `--token` or `--token=<value>` anywhere on a `fleet` command line, with a message that names `--token-file -`, `--token-file FILE`, and `--bws`, and that never repeats the value. `reconfigure` (`fleet home set`) merges `args` and `workerArgs`, the only settings that `home set` takes, into the file's own JSON, so the token, the `bws` block, `hosts`, `roots`, `tier`, and `cardd` stay, checks the result with `parseLaneConfig`, and replaces the file by rename. `home set` refuses every other option with a message, because the rest of a lane's settings are `home add`'s. `listSettings` in `launch.ts` turns `--args` and `--worker-args` into settings, for `home add` and `home set`, and `laneSettings` adds the options that only `home add` takes.
- `lane-config.ts` reads `<home>/config/lane.json`. It is private because it can hold the lane's token. A lane needs a `token`, a `bws` block, or both, and `bwsConfig` checks the block (Secrets from bws). `roots` defaults to `~/.fleet/app` for a remote host. `direnv` names a folder whose environment the mate runs in, while its home stays where it is.
- `update.ts` is one host's half of `/updatefleet`, run as `fleet update [--check]`. It prints one JSON line. `--check` fetches and finds every reason to refuse: a checkout off `main`, uncommitted changes, or commits that are not on `origin/main`, in the checkout or in any lane home. The update checks again, fast-forwards, runs `npm ci` when the lockfile changed or `node_modules` is missing, always builds the board, and moves each lane home to the new commit. The board build is cheap and makes a rerun converge after a failed build. A lane home moves only after the build, so a failed build leaves every mate on the code it runs. `fleet cardd` does the same for `cardd`'s checkout, and restarts `cardd` only when the commit that `cardd` reports running differs from the new one in `cardd`'s code, or is unknown. The running commit decides, not the pull, because a checkout can move without a restart, and a restart that failed must happen again on the next run. It backs up the database with `VACUUM INTO`, which copies a live WAL database consistently, just before the restart, since migrations run only when `cardd` starts. Pending migrations never run while the old `cardd` serves.
- `updating.ts` is main's half. It checks every host before it changes any, so a dirty home or an unreachable host stops the update with nothing pulled. Then it updates the hosts in turn, and stops at the first failure without restarting a mate. Then it updates `cardd`, and waits until `GET /api/version` answers with the new commit, which proves that the new process serves, not the old one. HTTP and not a session, because a second session with main's token would supersede main's own. Only when every host is updated and `cardd` runs the new code does it restart the lanes, as `lane("all", "restart")` does. Main restarts last. Pi cannot restart its own process, so a detached `relaunch.ts` waits for main's Pi to exit and its shell to be idle, then runs `pi --continue` in main's herdr pane with main's arguments. A mate's model flags are recomputed from its current `config/lane.json` (`mateRelaunchArgs`), so a changed `tier` applies. Main restarts when the turn that tells the captain ends. The command hands its report to main as a message that starts that turn, because Pi saves a conversation only once it has a reply, and `pi --continue` would otherwise start a new one.
- `migrate.ts` only copies, so a repeat never overwrites edits. Undoing renames the settings back and sets each home's `lane.json` aside.

### Memory

- `optchat.ts` loads OptChat from `packages/extension/vendor/optchat` with `FM_HOME` set to the home, when the home has `config/optchat.json`. The loader reads `FM_HOME` when its module is evaluated, so the variable is set around the import. The vendored folder is third-party code with its own style: lint, format, and knip skip it because their config files list it, and the typecheck skips it because `optchat.ts` imports it by URL, which `tsc` does not follow. Fleet's own changes to it are listed in its `README.md`.
- `memory.ts` writes what the loader reads, all inside one home. Each step that is done already is left alone. A profile's lock socket must fit a socket path: 104 bytes on macOS and 108 elsewhere, with the NUL.

### Standing rules and stow

- `standing.ts` reads the three files in `data/` on every turn, in `before_agent_start`, so a mate's own edit takes effect on its next turn with no reload. Only `AGENTS.md` and the other context files need Pi's reload, because Pi reads them once.
- Main's `captain-shared.md` reaches second mates by copy, not by reading main's home, because a lane's home can be on another host. Main pushes the bytes as base64 on the command line of `fleet shared`, through the host's transport, so no host needs a shared file system. The push runs each minute before main starts lanes, so a lane that starts already holds the file. It also runs at the end of `/stow`. A failed push to a host that answers is told once, and never stops the lanes from being kept running. A copy is read-only and replaced by rename, so a mate never reads half a file. Like Firstmate, a copy that someone edited is kept aside before it is replaced or removed: the home's `state/captain-shared.published` holds the bytes main last put there, and a copy that matches neither that nor main's file was edited. The aside copy is a plain sibling that no loader reads, so it is never a second shared file. A copy with no record, such as one from before this existed, counts as edited. The mode is only a nudge: main's bytes always win.
- The stale flags in the stow report are computed, not judged, because the model gets date arithmetic wrong. The entry format is one bullet line with an optional trailing marker. Anything else in a file is prose that the report skips.
- `stow.ts` ends the command by waiting for `agent_settled`, then reloading. Pi allows `reload` only in a command handler. `sendMessage` returns before the turn starts, so `waitForIdle` right after it could return at once, which is why the command waits for the settle event it sets up first. A reload runs the extension factory again, so the link to cardd reconnects, and main checks the clones again on its first connection. The reload keeps the process id, because it is the same OS process.
- `e2e/extension/standing.test.ts` gives its mates Pi's context files and built-in tools, which the other tests turn off, because `AGENTS.md` and the model's `write` are what it checks. Its stow tests set `FLEET_SUPERVISE_MS` to ten minutes, so only the stow can have published the shared file. It does not wait a fixed time: it waits for the probe's `session_start` event with reason `reload`.

### Pane

[pane.md](pane.md) owns what the captain sees. Inside:

- `pane/glance.ts` is pure. `glanceOf` turns the board's cards into needs and a landed count. A card has at most one need, and the worst reading wins. A need is data (`kind`, `card`, `title`, `why`, `since`), and the screen text is made from it, so the status line and the strip cannot disagree.
- The pane reads the `board` op that the `board` tool already reads, so its reads add no cardd code. Only its answer and its Later do (`pane.answer` and `pane.later`, below). The op returns every card ever made, and the cost grows with them. Measured on a scratch `cardd` with 1,400 cards of 6 entries each: a call took 200 to 240 ms and carried 6.8 MB, and validating 1,400 cards in the extension took 55 to 95 ms of Pi's main thread, the thread that draws the pane. That is why the pane fetches on events and then once a minute, not on a short timer, and why it fetches one at a time: a request that arrives during a fetch asks for one more after it. A closed card has no `pulse`, so the field adds nothing to those. A `board` call that returns only open cards and the cards closed since a time would cut the rest. That is a protocol change, so it waits for a change that needs it.
- The pane has no limit of its own. A need's kind and age come from the card's `pulse` (`kindOf` in `glance.ts`): the state `you` is Needs you, a `broken` state or an `urgent` notice is Broken, and a `stalled` state or any other notice is Stalled (main's notice after 4 hours of idle included, because the pane is main's screen). Its `since` is the time that the state counts from, so a report ages from the report's own entry, not from `updatedAt`. `cardd` owns the limits, and a test shortens them with `CARDD_TIMING_SCALE` or ages the card in the scratch database. `FLEET_PANE_POLL_MS` and `FLEET_PANE_SILENT_MS` let a test shorten the minute between fetches and the 30 seconds without an answer that show `cardd: not answering`.
- `pane/list.ts` and `pane/view.ts` are `/pulse`. `listOf` sorts the open cards with `quietFirst` from `@fleet/protocol` and splits the running ones off. `PulseView` is the overlay component. It scrolls by blocks, so a card's lines stay together. An expanded running list is one block per card, so it scrolls inside the same budget and `⏎` on a running card shows its board link. It paints its selected row's background again after every reset, because `truncateToWidth` ends its text with one. It reads the board once, when the command runs, and keeps nothing between runs. The command is registered only on main, next to the pane, and its handler never calls `sendMessage`, so nothing it draws is in the model's context.
- The pane paints only when the text changed. A widget factory replaces the component, so repainting each poll would redraw the strip for nothing. The strip component keeps no theme colors: it reads `theme.colors` on every render, so a theme change reaches it.
- Card titles, lanes, job labels, and watcher texts come from mates, so the strip and `/pulse` remove control characters and terminal sequences before they draw any of them. A text with a newline or an escape would break the row or move the cursor.
- `truncateToWidth` ends its text with a full reset. A reset ends the strip's tint for the rest of the row. The strip removes that reset from a cut title and keeps one column between the cut and `+N more`. So the tint covers the whole row, and the ellipsis does not touch the count.
- `session_shutdown` clears the status and the widget, so a reload or a new session never leaves a count that no one refreshes. The new session paints again at its first connect.
- The footer's chips row also starts with a glyph, so `e2e/extension/pane.test.ts` tells the strip from the chips by the character after the glyph: a digit is a chip.
- The strip is a widget above the editor, under its own key, so Calm's boat draws beside it. Neither sets the title, and the editor stays with OptChat.
- `pane/decide.ts` owns opening the card, for the `/d` command and for the strip's click alike, and refuses a second open while one is up. It opens the card with `ui.custom` and no overlay option, so Pi puts the card in the editor's place, as it does for its own selectors, and puts the editor back with its text when the card closes. The pane hides the strip while the card is open, because the card says the same thing.
- `pane/decisions.ts` reads the decisions: the `board` op's cards with status Needs you, each with its hold from the `card` op, oldest first. It keeps a card only if the `card` op still says Needs you, because a card can be deferred or closed between the two reads.
- `pane/card.ts` keeps a deck of slots, one for each decision it was opened with, and marks a slot answered instead of removing it. So the place in `Decision 2 of 3` and the dots stay put while the captain answers out of order, and `←` and `→` skip the answered slots. After a refused answer it reads the decisions again and merges them into the deck: answered slots stay, a slot whose card still waits takes the fresh decision, a slot whose card does not wait goes, and a new decision is added at the end. The pointer follows its meaning, not its index: it stays on `My words…`, follows a choice by its label, or goes to the first choice when that label is gone. It keeps no other copy of cardd's state.
- `pane/card.ts` works out one `layout` from the pane's rows less what the footer and two rows of chat need, and the refusal note. The frame, the question, and the choices take what the layout gives them, and the blank rows are what it gives up first. The choices scroll with the selection, so a choice that can be selected is on screen. The card sets `capturesViewportInput`, so PgUp and PgDn reach it and not the chat's scrollback.
- `My words…` and `Later…` are the last two choices, and each is a pi-tui `Input`. There is no typing mode. A key that no choice binding takes goes to the `Input` of the row the pointer is on, and if that was a choice and the text changed, the pointer moves to `My words…`. On `Later…` it types into the later line. An `Input` that did not change its text (a function key, an unbound control key) leaves the pointer where it was. That is why a typed word can never fall through to `⏎` on the highlighted choice, which was the bug in the first card: it ignored keys it did not know and the `⏎` after them answered with the recommended choice. `Input` joins the lines of a paste with nothing, so the card turns the line breaks of a paste into spaces first.
- The mouse reaches the card because it is a component in Pi's editor container: `handleMouse` gets `y` relative to the card, and the card remembers the row where it drew the first visible choice. A `press` moves the pointer and a `click` (press and release on one cell) confirms, as pi-tui's `SelectList` does. A click on `My words…` or `Later…` only selects it.
- A pane answer is an op, not the board's HTTP route. The extension's link is authenticated as main, so `pane.answer` needs no host allowlist and no second client, and `cardd` refuses it from any other lane. It runs the board's answer code (`answerOnBoard`), so the stale check, the merge-choice rule, and the notifications are the board's, and only `source` differs. The stale check is `requireSeen` in `board.ts`, for an answer and for Later alike. The client sends the id of the hold entry it showed (`board.holds[].hold` on the board, `card.hold.entry` in the pane). `cardd` replays the card's entries up to that entry with `factsFrom`, so it has the hold as he saw it: its occurrence, holder, question, and options. It compares that with the open hold. It refuses only when there is no open hold, the open hold is dated into the future, or what the captain saw differs from what is open. A hold written again with the same words inside one occurrence, such as a mate answering an owed reply, still takes his answer, because a hold entry is compared by what it says and not by its id. A hold that was withdrawn, answered, or released and then asked again with the same words is a new occurrence, so the old card is refused. The answer entry keeps `by: "board"` so the board's thread shows it as the captain's answer.
- Later is one path for the board and the pane. The captain types words, and `cardd` reads them (`later.ts`): the board sends the `hold` action with `said` and `zone`, and the pane calls the `pane.later` op with the card, the hold entry it showed, `said`, and `zone`. The board's action carries the hold entry too. Both run `deferOnBoard`, which first runs the same stale check as an answer (`requireSeen`), refuses a hold that is not the captain's, and then writes a `hold` entry authored by the captain: the same holder, question, options, and merge flag as the open hold, `until` as the time it read, and `wait` as `{ by: "later", text: <his words> }`, with no remaining work. The hold leaves his list and returns when `until` passes, as any captain-said dated hold does. Both surfaces then tell him what `cardd` read: the `/api/action` reply and the `pane.later` result carry `until` and the zone used, and `laterLine` in `@fleet/protocol` turns them into one line (`c-12 comes back to you Thu, Dec 31, 4:00 PM CST (America/Chicago)`) for the pane's notice and the board's toast, which stays until he dismisses it. Text that holds no time is refused with the words he can say, and nothing is written, so the client keeps his text in place. Nothing configures a captain time zone, so the screen he types on sends its own IANA zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`: the browser's, or the zone of main's Pi process). The reader (`later.ts` for the resolving, `later-read.ts` for the words) splits his text on whitespace only, in the original case, and reads each token whole, by exactly one component: a clock, a date, a weekday or `today` or `tomorrow`, a length of time, or a zone. It never searches a token for a valid fragment and never rewrites the inside of a token: only sentence punctuation at the edges is dropped (`, ; ! ? ( )` and quotes at either end, a period at the end, a colon at the end of a token with no digit, and the dots of a lone `a.m.` or `p.m.`), so `UTC+2:abc`, `UTC+2.foo`, `4:PM`, and `cet+abc` stay whole and are never read as their valid part. A token that carries time information (a digit, a colon, a slash, or a `+` or `-` sign that starts the token or follows a zone name or a word of 2 to 5 capital letters, so `cet+abc` is refused in any case) and that no component reads is refused with the token named, as the single check after the components are read. A hyphen in a plain word (`follow-up`) carries none. A refused token holds nothing: `4:5PM`, `4:05:07PM`, and `c-12` are refused, never read as `5PM` or ignored. A clock is `4PM`, `4:05PM`, `4 PM`, `16:00`, `noon`, or `midnight`, read whole. Plain lowercase words and punctuation are prose and are ignored (`I have not run it. Snooze until 4PM CST` holds). A second component of one kind is refused (two times, two dates, two days, two weekdays, two zones). A zone named in his words wins, and it is never ignored or swapped for the screen's zone. The reader knows these zone names. The US ones are `ET`, `CT`, `MT`, `PT` with `S` or `D` between, `AKST`, `AKDT`, and `HST`. The others are `UTC`, `GMT`, and the abbreviations `CET` and `CEST` (Europe/Paris), `EET` and `EEST` (Europe/Athens), `WET` and `WEST` (Europe/Lisbon, read only in capitals, because west and wet are words), `BST` (Europe/London), `JST` (Asia/Tokyo), `KST` (Asia/Seoul), `AEST` and `AEDT` (Australia/Sydney), and `NZST` and `NZDT` (Pacific/Auckland). Each abbreviation means that region's local time all year, so `4PM CST` is 4PM in Chicago in July too and `4PM CEST` is 4PM in Paris in December. Any IANA name with a slash works too (`Europe/Paris`, `Canada/Eastern`, `US/Pacific`, `Etc/GMT-5`): `Intl` is asked, so no list of areas limits it. A fixed offset is `UTC+2`, `GMT-5`, `UTC+05:30`, or a bare `+05:30` token. `+2` means two hours ahead of UTC, and an offset must be from -12:00 to +14:00 with minutes of 00, 15, 30, or 45. The zone that goes back to the surface for an offset is `+HH:MM`, which `Intl` takes as a zone, so the notice shows the right local time. A zone token is read whole and accepted or refused whole: `GMT+abc`, `UTC+2:75`, `CET+2`, `+abc`, `+05:3`, and `+2000` are refused, not read as `GMT`, `UTC`, `CET`, or nothing. A word of 2 to 5 capital letters in the zone position, which is the token after a clock, a date, a day, a weekday, or a length of time (skipping the connecting words that follow it), is a zone that must be known: `CHT`, and `IST` and every other ambiguous abbreviation, so `in 2 hours IST` and `4PM IN IST` are refused too. The message gives the token, says it is not a time zone the reader knows, and says to use a city such as `Europe/Paris`, an offset such as `UTC+2`, or one of `ET`, `CT`, `MT`, `PT`. A connecting word in capitals (`AT`, `ON`, `BY`, `OF`, `IN`, `TO`, `THE`, `AND`, `OR`, `AM`, `PM`, `NEXT`, `UNTIL`, `FOR`, `FROM`, `THIS`, `THAT`, `WITH`, `OK`) or a month name is never a zone, so `tomorrow AT 4PM`, `Friday AT 4PM`, and `4PM ON Dec 31 2099` hold. A day with no time is 09:00, a bare time already past today is its next occurrence, a bare weekday is the next one after today, and a date with no year is its next occurrence as a whole instant: `Nov 20 4PM` typed at 5PM on Nov 20 is next year's, and `Feb 29` is the next leap year's, at most 8 years ahead. A bare time, a weekday, and a date with no year all pick the next occurrence of a local wall time through one function: a candidate whose local date and clock are not after the current local minute in the zone is dropped before it is converted to an instant, and the first candidate left is converted. So a daylight-saving gap that has already gone by, today, this year, or this week, never refuses: `Mar 8 2:30am America/New_York` typed in November 2026 is March 8, 2027, and `2:30am America/New_York` typed at noon on the day the clocks went forward is the next day. A wall time that does not exist on the candidate that is chosen is refused. An explicit past year and a date that exists in no year (`Feb 30`, `Apr 31`, `Feb 29 2027`) are refused. `cardd` reads the clock from its timing (`CARDD_CLOCK_FILE` in the end-to-end tests) for both surfaces. The reader never guesses: text that names two days, two times, or both a time ahead and a time of day, a duration with more than one amount (`in 2 hours and 30 minutes`, which must be `in 150 minutes`), a date that does not exist, a wall time that does not exist in the zone that day (02:30 on the day the clocks go forward, checked by reading the instant back in the zone against the date and clock he typed, for a date, a bare time, and a weekday alike), and a time in the past are refused. A wall time that happens twice, when the clocks go back, is its earlier one. No tool of the extension calls `pane.later`, and `cardd` refuses it from every lane but main's.
- The strip's click is a `MouseRegion` around the strip. It acts on a left `click` only and leaves presses and drags to the terminal's text selection. `e2e/support/decide-lab.ts` sends the SGR mouse sequences for press and release to the pane, for the strip and for the card, because herdr has no click command. Pi turns mouse reports on only in fullscreen mode.

### Neglect

[neglect.md](neglect.md) owns what the states mean and when someone is told. Inside:

- `pulse.ts` (`cardd`) computes a card's `pulse` from the card's entries, its standing, its live session, its running jobs, and its dated wait. It is next to `datedWait` in `board.ts` and in the timed check, and it is the only place that holds the state rules. The first rule that fits wins: Needs you, a reported need, a silent worker, running, a dated hold, a pause, then idle.
- `movedAt` is the newest real entry, `progress_at`, or the card's creation, whichever is latest. A real entry is a comment, report, hold, release, answer, review feedback, finished job, or cleanup. A wake from a schedule or a script, a reminder, a note, and a lost job are not. `cards.last_activity` is never read.
- Each state counts its age from its own evidence, in `since`: a report's time, a session's last output, the hold's age, the status change, or `movedAt`. The notice follows from that age and the limits in `timing.ts`. The clients compare nothing: they read `state` and `notice`.
- The board is built with the timings (`boardView(db, timing)`), because the notice depends on them. The one second cache holds the pulse too, and the board page and the pane both fetch again at least every 30 seconds and a minute, so a notice never lags by more than that.
- A pulse carries no free text from a mate except the label of a running job of the card's own attempt, in `running`. Everything about a dated wait stays in `datedWait`. `seenBy` in `board.ts` is the one place that makes a card fit a lane's eyes, for the `board` op and the `card` op alike: it hides what a dated wait watches in another lane, and it recounts `behind` with every step of a lane the viewer cannot see as open and not started.
- The words for a pulse (`ownerText`, `runningText`, `waitsText`, `behindText`) live in `@fleet/protocol`, so the pane and the board say the same thing and a Needs you row on either one carries `movedAt` and `behind` as every other row does.
- The board reads `alarming` in `Attention.tsx` for both the strip and the per-card alarm: a `broken` or `stalled` state, or a `captain` or `urgent` notice. A notice of `main` is not an alarm there. The Pi pane is main's screen, so it alone counts a `main` notice (`kindOf` in `glance.ts`).
- `bundle.ts` takes the pulses and routes them as [neglect.md](neglect.md) says. `neglectItem` makes the item for an idle card or a worker's pause, always for main. `openItems` drops it when `mateItem` already gave the same receiver that card. `waitGroup` puts a dated hold into the `parked` group when its pulse is parked and has a notice, and an idle park always into the first group. A `parked` item takes its age from `pulse.since`, not from the card's status change, so a hold that is dated again keeps the age of its first opening. `bundleMatches` lists the `parked` group only when the daily list is due. The `watched` count in a list entry's `fields` counts both daily groups, and is 0 in a list that was not due for them.
- `e2e/cardd/pulse.test.ts` ages cards by writing old times into the scratch database. It drops the `entries_no_update` trigger first, because entries are append-only. That is a fixture on a scratch database, never `cardd`'s own code.

### Calm

[calm.md](calm.md) owns what the captain sees. Inside:

- `layout.ts` patches the render of three Pi components. `ToolExecutionComponent` draws nothing, unless the row has an image, because an image is content. Without Pi's image list, a row counts as having images: showing a row is the safe error. `CustomMessageComponent` draws nothing for a `fleet` message. `AssistantMessageComponent` loses collapsed thinking and short pre-tool text from a shallow copy before layout. Pi's later refreshes read the full message back.
- Each patch probes the Pi member it replaces. `index.ts` skips a missing one with a diagnostic. A patch installs once per process. A reload evaluates the module again, so the flag lives in one process-wide object in `state.ts`.
- Calm drops thinking while it is on and Pi hides thinking (`hideThinkingBlock`). It does not read or set Pi's hidden-thinking label, because anything can reset the label, and a reset label shows `Thinking...`. Setting the label makes Pi lay out every assistant row again, so Calm sets it back to Pi's default on each toggle to apply the toggle to rows already on screen. Without a terminal (print and RPC modes), calm only records its state.
- `e2e/extension/calm.test.ts` navigates the fullscreen transcript before checking restored rows. Herdr's recent terminal output can contain only the current viewport after a redraw, not every retained message. Ctrl+Home reveals the earlier fleet, note, and tool rows; Ctrl+End reveals the later conversation. The test sends their standard terminal sequences because herdr 0.9.5 does not name those modified keys.
- One logical run lasts from `agent_start` to `agent_settled`, which also covers abort and failure, so the boat does not flicker between tool calls.
- `preference.ts` replaces `config/calm` atomically, so a crash never leaves half a value. The choice is saved before the screen changes, so a failed write changes nothing.
- `ship-sprite.ts` owns the geometry, the bounce track, and the two linked cadences. Every tick moves the water a quarter cell, and every fourth tick moves the boat one cell, so the trough stays under the boat. Ticks, not wall time, drive every change. Hiding freezes the sprite at its last painted frame, and the next run resumes there. A fresh session resets it. State never sits in a module-level singleton. The boat at an endpoint already carries the new direction. A resize recomputes and clamps the track before the next frame.
- `ship.ts` paints runs with standard ANSI codes only: one blue for water, so the swell reads through glyph height, and one yellow for the whole boat. It recomputes the track from the render width on every frame. The widget key `calm-working-ship` is shared with Firstmate's calm and the standalone Pi calm, so a session that loads more than one shows a single boat. Its timer never keeps Pi's process alive.

### Transcript

[transcript.md](transcript.md) owns what the captain sees. Inside:

- Pi has no hook around a whole message. Its Markdown transform sees one text block at a time and has no message identity, and `registerMessageRenderer` covers only custom messages. So `transcript/layout.ts` patches the `render` of `UserMessageComponent`, `AssistantMessageComponent`, and `CustomMessageComponent`, as Calm does, and each patch draws the rule around the lines Pi drew. A Markdown transformer would draw one rule for each text block.
- The patch keeps no state about earlier messages. Pi draws every message again at each frame, on a resize, and when a restart replays the history, so a rule that depended on the last message drawn would repeat or vanish. The rule depends only on the message and the width.
- Pi's assistant and custom rows start with their own blank line, and the rule goes under it. A user row has its blank line outside it, in a `Spacer` that Pi adds before the row, so the rule goes first. An empty row stays empty, which is why a silent reply has no rule.
- `state.ts` holds Pi's live theme, in one process-wide object like Calm's. `ctx.ui.theme` is a proxy for the current theme, so a theme change reaches rows already on screen. It never holds the extension context itself: after `/new`, the old context is stale, and reading it from a render crashes Pi. Without a terminal nothing sets it and nothing is drawn.
- The mate's own replies have a rule and no name. The one list of the fleet's own message types, `FLEET_ROW_TYPES` in `layout.ts`, decides both which rows are labelled `fleet` and which get the framed renderer. A type missing from it keeps Pi's raw `[type]` header.
- `patch.ts` is shared with Calm: install a patch once per process, probe the Pi member it replaces, and report a missing one with a line. Each patch loses only its own part if a Pi release moves the member.
- `window.ts` implements the [history window](transcript.md#what-it-does) with `DRAWN_ENTRIES` as its window size. Pi 1.4.0 draws every row of the chat at every frame: `Container.render` walks all of them, and the fullscreen layout needs the whole height to place the scroll position. A frame costs time in proportion to the rows, and the working spinner asks for about twelve frames a second, so one mate session of 28,000 entries kept the main thread at 100% CPU. Everything that shares that thread waits for a frame: `dispatch` makes about 25 awaited `herdr`, `git`, and `sh` calls, and each answer reached it only between frames (a dispatch took 5.4 s on that session, 17 s with the captain's footer and readable-row extensions, and 0.9 s on a new one). A mate cannot lean on compaction to bound the chat: OptChat cancels `session_before_compact` for every mate with memory, so those sessions never compact. `buildContextEntries` is not patched, because Pi also uses it for the model's context. The model, `/export`, the session file, and OptChat memory still see every entry, and nothing here rolls or writes the session file.
  - The patch is on `InteractiveMode.renderSessionEntries`, the one place where Pi turns session entries into chat rows at start, on `/reload`, and on every rebuild. It filters orphan tool results from the last `DRAWN_ENTRIES` entries, passes the remaining entries to Pi, and puts the notice row where the drawn history starts. There is one notice component. It lives in `state.ts` with the count of entries that are not drawn, and it reads that count each time it renders. The start and every rebuild set the count and put that same component back, so a rebuild never makes a second notice. Pi draws a tool result only inside the row of its call, so a result whose call is not among the drawn entries is left out with it, and the notice counts every entry that is not drawn.
  - Pi fills the editor's Up-arrow history only from the entries it draws. The patch adds the text of every older user entry first, so the captain's old prompts stay in the history after a restart.
  - The patch keeps the `InteractiveMode` that it is called on in `state.ts`, with the theme and the notice. On `agent_settled` the extension calls `trimDrawnHistory`. When the chat holds more than twice `DRAWN_ENTRIES` rows, it calls Pi's `rebuildChatFromMessages`, which clears the chat and renders every entry again through the same patch. The window, the notice, and its count are set in that one place. It rebuilds instead of removing the oldest rows because the rows of an entry are not tracked: an entry makes no row, one, or several, so only a render can say which rows belong to the last 500 entries. Rows that Pi made without an entry, such as a status line, go with the rebuild.
  - The trim waits while the captain is scrolled up, so the view does not jump under them. Pi exposes that as `renderer.isFollowingOutput` only in fullscreen mode. Without fullscreen there is nothing to read and the trim runs anyway. The next `agent_settled` that finds the transcript following its end trims.
  - The patch probes the Pi members it replaces or calls, `renderSessionEntries`, `getUserMessageText`, and `rebuildChatFromMessages`, and installs nothing when one is missing. Without the patch the extension never holds a mode, and the trim does nothing.
- `index.ts` registers a message renderer for the fleet's own rows. It draws the text in Pi's custom-message box without its `[fleet]` label. `@earendil-works/pi-tui` is a peer dependency of the extension, as `pi-coding-agent` is, because the renderer builds `Box` and `Text` at run time.

## Board

- `App.tsx` reloads the board on every change and every 30 seconds, because a card's notice depends on the clock. It keeps only the newest load. It keeps what the captain started to write on each card when he goes back to the board.

## End-to-end tests

- `e2e/support/run-root.ts` puts every test folder under one run folder in the real path of `/tmp`, whatever `TMPDIR` is. macOS's own `TMPDIR` is a long folder under `/var`, which is a symlink to `/private/var`. A memory profile's lock socket under it goes over macOS's 103-byte limit, so the memory never loads. And a path through the symlink differs from the real path that a pane's cwd and Pi report, so a test that builds one from the other no longer matches. The real `/tmp` keeps both the same on Linux and macOS. `FLEET_E2E_TMPDIR` overrides that folder, so `e2e/extension/tempdir-leak.test.ts` can run a nested suite in a folder it owns.
- `e2e/support/scratch.ts` makes a scratch copy of the repository with its own lane homes. A second mate's memory profile in a scratch home has a lock socket path longer than macOS's 103-byte limit, whatever `TMPDIR` is. So the tests that make one skip on macOS, and CI on Linux runs them.
- `e2e/support/fake-model.ts` is a Pi extension that posts each model call to the test's control server and returns the move the test chooses. Everything else in Pi stays real.
- `e2e/support/fake-anthropic.ts` registers a `tier` provider on Pi's real Anthropic Messages client, pointed at the control server, so the harness reads the actual request: its `cache_control` retention and whether it is a one-token warm. The harness answers with a server-sent-event stream. `harness.wire` lists the requests, with the role taken from the system prompt.
- `e2e/support/bws.ts` puts a fake `bws` first on a test's `PATH`. The fake keeps its secrets only in the environment of the test's processes (`FAKE_BWS_DATA`), never in a file, and logs each call's arguments. So `filesHolding` can scan the whole run folder for a secret, and a hit means the fleet wrote it. `bws-cli.test.ts` covers `fleet wake`, `fleet secrets`, and each fallback. `bws-session.test.ts` covers a mate, and a worker that its mate dispatched.
- `e2e/support/herdr.ts` runs an isolated herdr session whose name starts with `fleet-lab-`, so a test never touches the captain's session.
- `e2e/support/hermetic-env.ts` removes the fleet variables that a live mate exports, such as `FLEET_HOSTS`, `FLEET_ROOTS`, and `FLEET_ROOT`, as soon as a test loads its support. The extension and `fleet` read those variables before their lane config, so a run started from a mate's shell would otherwise send a scratch fleet's commands to the live hosts and checkouts. It also removes the herdr pane variables (`HERDR_WORKSPACE_ID`, `HERDR_PANE_ID`, `HERDR_TAB_ID`, `HERDR_SOCKET_PATH`, `HERDR_ENV`, and `HERDR_SESSION`), because the herdr CLI follows `HERDR_SOCKET_PATH`, so a run started from a worker's pane would otherwise reach that worker's live herdr and rename its workspace. Every module that spawns a fleet process imports it: `guarded.ts` and `scratch.ts`. `e2e/extension/hermetic.test.ts` runs a two-host test from such an environment and fails if any command reaches the live host. It also runs a mate test from a worker pane's herdr variables and fails if the pane's workspace is renamed.
- `e2e/support/remote.ts` gives a clone a bare remote, `<clone>.git`, and lands commits on it from another clone, as a merged PR does. The dispatch lab names its GitHub repository with `--repo acme/site`, so its clone needs no origin on GitHub: dispatch fetches any origin first. With `remote` set, the lab registers its clone for host `local` only, because the other lab hosts reach the same folder and would refresh it once each.
- A mate `Session` from `e2e/support/cardd.ts` acknowledges each entry it gets, as a mate whose runs end cleanly does, so the timed check never sends it anything again. `connect(token, inFile, false)` makes a mate that never takes anything in. `connect` also sends a process id in its hello, the same one for every connection that uses a token, as the extension's `Link` does for one Pi process. A hello with no process id never clears a startup or lost incident (see Runtime incidents), so a helper that sent none would leave the incident of a worker that connected late, or that reconnected after a stall, open for good, and a live incident holds back that worker's idle finding. With `CARDD_TIMING_SCALE=0.001` a worker has 120 ms to connect after `begin` and 120 ms to reconnect before that incident opens.
- `e2e/support/fake-gh.ts` supports only worker-initiated PR merges and logs every invocation. Discovery and PR-state commands are rejected. Merge fixtures are atomically published through same-directory renames. Every `Cardd` in the tests runs this fake gh, so no test reaches GitHub. The trial runs the real one.
- Scratch puts a successful `gh --version` and `gh auth status` stand-in before the host's tools. FakeGitHub takes precedence for PR commands. The prerequisite tests supply explicit missing and failed-login cases instead of using the host's credentials.
- `e2e/extension/sync.test.ts` scripts lsof's ownership answer. A real host's unrelated inaccessible mounts can make lsof's negative result incomplete. The product keeps the lock in that case. The test covers a clean negative result, a holder, an inspection failure, an incomplete clone scan, and a recent lock without weakening the product's checks.
- The model harness accepts only `POST /model`. Closing its websocket server removes the upgrade listener, so a late probe handshake can arrive as an ordinary HTTP GET. It receives 404 rather than entering the JSON model parser. Node 26 resets a connection whose request ends after `server.close()`, so there the handshake gets a reset instead. `e2e/pi/harness.test.ts` accepts either, and checks that no model call came of it.
- `e2e/support/fake-ssh.ts` (put on the `PATH` as `ssh` by `mux-ssh.ts`) is an ssh whose master refuses file descriptors: in mode `wedged` it prints `mm_send_fd: sendmsg(0): Message too long` and exits 255 until it is run with `-o ControlMaster=no -o ControlPath=none`, in mode `down` it always times out, in mode `wedged-down` it refuses and then times out, and in mode `fell-back-then-dropped` it prints `muxclient: master hello exchange failed`, runs the command, and exits 255 anyway, as ssh does when it falls back by itself and the connection then drops. It logs every call. `e2e/extension/ssh-mux.test.ts` and `e2e/cardd/ssh-mux.test.ts` use it.
- `e2e/support/flaky-transport.ts` behaves like ssh whose connection drops right after the worker started: the first `herdr agent start` that succeeds loses its output and exits 255. `switch-transport.ts` fails like an unreachable host once its marker file exists. A marker that starts with `hang` hangs instead, and one that starts with `flood` floods every command but herdr's.
- `e2e/support/login-transport.ts` runs a host's command as the host's non-interactive ssh session does: only the host's own `HOME`, the `PATH`, and `FLEET_TMP_SOURCE_DIR`, none of the closing mate's environment. A command that names `herdr` or `arrange` keeps the test's environment, because the lab's herdr needs it. `e2e/extension/scratch-host-setting.test.ts` uses it, so a close from another host can read the destination only from that host's `host.json`.
- `e2e/trial/trial.ts` is a real-model trial, not a test: `node e2e/trial/trial.ts <project clone> [model]`.
- `e2e/pi/contract.test.ts` pins the Pi behavior the extension depends on. A Pi upgrade that changes it fails there first.
- Tests that start processes stop every part even when one part fails, so no process outlives a test.
- A `cardd` token begins with `-` 1 time in 64. Tests force such tokens to prove that Pi reads each one as a value, not an option.
- `e2e/extension/dispatch.test.ts` bounds a restart below `FORMER_REFUSED_START_WAIT_MS`, the 10 s that a refused start once waited for a Pi that herdr never typed.
- `e2e/extension/start.test.ts` holds the worker's first model call open, so the worker stays busy while herdr's start command still waits for it to idle. The mate must hear back before that command ends. A clock on the whole dispatch would also count the shell's start and herdr's refusals, which load stretches.
- When a job's tab closes, either the wrapper posts what the command printed as it died, or the tab's processes go first and the heartbeat check reports the job lost. Which one wins depends on the platform and timing. `e2e/extension/jobs.test.ts` accepts either, once.
- `e2e/extension/memory.test.ts` runs the vendored memory. The model's turn may start with the memory's own context block, so the test finds the fleet message after it. Its second-mate tests skip on macOS, because the profile's socket path cannot fit 103 bytes there. CI on Linux runs them.
- `e2e/extension/worker-model.test.ts` starts main as a plain Pi in a scratch copy that picks its model from its settings, as the captain's does. Pi picks a model from its settings only when it knows a key for that model's provider at session start, so the test gives the scripted tiers a key. Main and its worker share the lab's model agent, so the system prompt tells their calls apart.
- `e2e/extension/account-rotation.test.ts` starts a real worker Pi on `--provider anthropic-3 --model <id>:medium` against a real `cardd`, with Pi's retries switched off. `tiers.json` in the test's agent folder groups fake providers: some serve the model, one serves another. The fake model fails a request with the text of a 429 or of a quota error, and the test reads which `provider/model` each request reached. It covers the move to the other account on either text in one process with no failure on the card, the walk past two limited accounts to a third, the unchanged thinking level, the one failure that names the model and the accounts when none is left, accounts with a one second cooldown that a slow answer outlasts (never revisited in the same chain, revisited after a turn that went through and by a new run, and not held back from recovery by a later account's longer cooldown), a second process on the same session that skips the account that ran out, and an `avoid` that names the other account.
