# The code

Code in this repository has no comments. A lint rule fails on any comment. What a comment would say goes into a name, a type, or a smaller function. What a name cannot carry, such as why a module is shaped the way it is, lives here. [The spec](spec.md) owns the design. This file owns the reasons in the code that the spec does not name.

## Gates

- `eslint.config.js` holds the lint rules. Inline disable comments are off (`noInlineConfig`), so a rule changes only there, in review.
- `fleet/no-comments` is a local rule in `eslint.config.js`. It allows one comment that the toolchain reads: a triple-slash `<reference lib="..." />` directive, which `e2e/board/board.test.ts` needs for the DOM types of the code it runs in the browser.
- `.dependency-cruiser.cjs` holds the module boundaries. `cardd`, the extension, and the board share only the wire protocol. End-to-end tests drive real processes, so they import only the protocol.
- `ci.yml` puts each pull request's runs in one concurrency group, so a new push cancels the run it supersedes. Each push to `main` gets a group of its own, keyed by its run id. With one group for `main`, a merge cancelled the run of the merge before it, both in progress and while it waited, so that commit never got a full result.
- `packages/cardd/scripts/check-migrations.ts` applies every migration to an empty database, checks the result, and compares it with the committed `schema.sql`. With `MIGRATIONS_BASE` set to a git ref, it also fails when a migration that exists at that ref was changed, renamed, or removed. `--write` updates `schema.sql`.

## Protocol

`packages/protocol` is the wire protocol between `cardd`, the extension, and the board. Each schema is the one source of its type and its validator. `parse` throws one readable error that names the first problem.

## cardd

### Command line

```
cardd serve --db <file> [--listen <host:port>] [--board <built board folder>] [--hostname <name>]...
cardd lane add <name> --db <file> --home <path> [--parent <lane>]
cardd lane plan <name> --db <file> [--plan <json>]
cardd project add <name> --db <file> --delivery <mode> [--clone <host>=<path>]... [--yolo] [--repo <owner/name>]
cardd project clone <name> <host>=<path> --db <file>
cardd project yolo <name> on|off --db <file>
cardd project delivery <name> <mode> --db <file>
cardd card delivery <number> <mode> --db <file>
```

`project add` without `--repo` reads the project's GitHub repository from the `origin` remote of a clone on the `cardd` host. `serve` fills in any that are missing at each start.

`project clone` sets one host's clone of a registered project to a new path, so a clone can move. Attempts already begun keep their worktrees where they are: close finds them through the clone's worktree list, not through a stored path.

`project delivery` sets the delivery mode that new ship cards of a project take: `no-mistakes`, `direct-PR`, or `local-only`. It changes no card: a card records its mode when it is created, and that record is what dispatch tells the worker. `card delivery` changes the recorded mode of one open ship card. It refuses a card that is closed, is not a ship card, or has a live worker, because that worker was told its mode in its task and a changed record would let it go on with a stale one. To change the mode of a card with a live worker, a mate dispatches again with `delivery=<mode>` and `replace=true`, which starts the worker over with the new mode. Setting the mode a card already has changes nothing. Each change is a note on the card.

`lane add` prints the mate's token. `CARDD_TIMING_SCALE=0.01` speeds up every timer, for tests. `CARDD_CLOCK_FILE=<file>` makes the scheduled wakes read their time from that file, an ISO 8601 time, instead of the clock, so a test moves time by writing the file. Nothing else reads it: entries and the other timers keep real time. `project yolo` sets the captain's standing merge authority for a project. Only the captain sets it, through this command line.

### Storage

- `store.ts` reads and writes `cards.db`. A mate's session ID is its lane name. Rows leave the database as JSON that SQLite builds, and are checked against the protocol schemas, so the types match the wire. A card from before names existed is known by its number.
- A session's token is the HMAC of its role and ID under the database's key. The same session always gets the same token, and no mate can share a token with a worker.
- `db.ts` applies every new migration in one transaction, so a failed migration leaves the database as it was. Foreign keys are off while migrations run, as SQLite's procedure for rebuilding a table requires: dropping a parent table counts each child row as a violation that its replacement never clears. Instead, every key is checked after each migration, and a violation names its rows. Every foreign key in the schema is one column.
- Each entry that the card's status reads raises the card's revision, so the board refuses answers to a hold that changed.
- The cards table stores no status, phase, or time of change. `store.ts` replays a card's entries through `status.ts` each time it reads the card.

### Status and holds

- `status.ts` is pure. A card's status is one function of its communication entries: the worker's reports, holds, the captain's answers, comments, and the close. Mostly the last report decides. An open hold wins. Nothing else feeds it: not GitHub, not the timed check's findings, not job results, not commands. No operation sets a status, and none is stored.
- A hold that waits on the captain makes the card Needs you. A hold that waits on a mate makes it With mate. A hold with a future date is Waiting until then. A closed card has no hold.
- A `paused` report with a date shows the card as Paused until that date. A `blocked`, `failed`, or `stopped` report shows the card as With mate with red attention. Any later report, steer, or answer replaces both.
- A captain's approval of the merge question, or yolo on a ship card's `done`, makes the card Merging. The worker's next `done` leaves it Merging, and the mate's close makes it Done or Dropped.
- `change.ts` holds the guards of spec section 7.4: a Done or Dropped card refuses reports, holds, and steers, and a lane card refuses all of them. `statusWith` reads the status a report will give, with the entries a caller writes next counted.
- `holds.ts`: a card has at most one hold, with every question of its gate bundled in it. The card's own mate owns it. It waits on the mate, then main, then the captain, and climbs one level at a time. Only main marks a hold as the captain's. Main's own cards skip main. Holding the same hold again writes nothing. A hold after a release is the next occurrence of the same hold.
- Only the captain's exact words release what waits on the captain. Merge approval is such a release. Own words on a merge question request changes: only the Approve option approves.
- A steer withdraws the merge question while the PR is reworked, because approving a PR that is about to change would approve the wrong head. The worker's next `done` asks again, as the same hold.
- The captain's comment takes the hold back from him. A comment written on the board goes to main only, never to a second mate or a worker, and it carries the card's lane when the card is not in main's lane. Main relays it as it sees fit. A hold that went back to a second mate's lane waits there until main does.

### Talking

- `comments.ts`: a comment is the one way to talk to an agent. A worker's card hears its mate. A second mate's lane card, or any card in its lane, hears main when main speaks, and main hears the second mate when it answers. Main never steers another lane's worker. A comment cannot answer a worker's decision that waits on the captain.
- `board.ts`: `/api/board` and `/api/card/N` give the board its data. Each card carries `activity`: the state of the session that works on it (a worker's, or a mate's for a lane card) and when cardd last heard from it. A change of that state reaches the board over the live socket.
- The board's thread (`thread.ts`) gives each entry a direction from its author, its `for` and `holder` fields, and the card's lane. Rows between two mates are quiet log rows. A board answer that main recorded again with the captain's words is not shown twice, and a quote of the captain's earlier words in another entry folds to a marker. A `replyTo="r-N"` entry shows a link to its question. Replies to a captain comment nest under it and keep their sender and recipient labels. The board's reply e2e uses real cardd comments and answers, with no direct database writes.
- `ops.ts`: a report reaches the mate when its status hands off, or when it is the first report after a comment that reached the worker (spec section 10.3). Each operation runs in one transaction.
- `replies.ts`: a mate can ask for a reply to one comment, on its worker's card or, as main, on a card in a second mate's lane. The comment entry is the record: it carries `owes`, the recipient, and the reply's id is `r-<entry id>`, so the record exists in the same transaction as the comment, before any push. The open replies are derived from the card's entries, like its hold. Only an entry from the recipient that names the id in `replyTo` answers it: a worker's report, or the second mate's comment or hold, which goes to the asker. Only the asker withdraws it. The timed check resends it once to the recipient, then tells the asker once, as findings that name the id. Each step waits until the recipient has been quiet (idle, or gone) for the grace period of `timing.ts`, and the grace starts again after a hold on the card ends, so an agent waiting on its own decision is not poked. After the escalation the reply stays open until it is answered or withdrawn. The captain's board comment opens one too: it carries `owes`, the lane of main for the card, and the answer is main's comment or hold with that `replyTo`, which notifies no one and is marked `for: captain`. It is resent once to main, then main is told once, even while the card is held by main or its owner, but not while it waits on the captain. Replies on a closed card are not nudged and not shown.
- `plans.ts`, `schedule.ts`, and `wakes.ts` are a mate's scheduled wakes (spec section 19 describes run cards for a standing card: this is the lighter form that wakes the mate and starts nothing). The plan is on the lane card in two columns: `plan_next` is what the captain set, and `plan` is what the mate loaded at its start, with the time it took effect. The `lane.plan` op, which the extension calls once when it starts, moves the next plan into the active one and returns it, so activation is the mate's own restart and the call is safe to repeat. Only the active plan fires.
- `schedule.ts` is pure. Time is compared as local wall-clock minutes (`YYYY-MM-DDTHH:MM`) in the plan's zone, never as instants, so a time that DST skips fires when the clock reaches it and a time that DST repeats compares true twice. For each wake it finds the latest slot at or before now, looking back at most a week. The slot is due when it is not before the minute the plan took effect. A wake is never made up for more than its latest slot.
- `wakes.ts` writes the wake in the timed check. A slot's key is its minute and its purpose, and the wake entry (and a skip note) carries the keys it covers in `fields.slots`, so what is issued is read from the card's own entries: a restart of `cardd` finds it, with no second table. Slots due together are one wake. The wake is a comment by `schedule` with `owes` the lane, `for: mate`, and `from` the lane's parent, so reply tracking in `replies.ts` treats it like main's `reply=true` comment, with three differences: the reply's asker is main only for the escalation and the withdrawal, so the mate's answer notifies no one; its text is the whole wake line; and while one is open, the next wake is skipped with a note instead of sent. A script wake (`wake` op) is a plain comment by `script` that owes nothing.
- `echo.ts`: when a parent commented on a card and the mate has not acted on it since, the mate's next action also reaches the parent. It is sent once, because the next action ends the wait.
- `authority.ts`: the mate's extension checks chat words against its own session file. For any other source, the words must be in a captain entry: a board comment, an option click, or an earlier answer. A project's yolo flag lets its mate have the worker merge a green PR without asking. A done PR in such a project goes straight to Merging.

### Attempts, delivery, and the server

- Delivery modes: a ship card records its mode in `cards.delivery`. `card.new` takes the project's registered mode, and maps `no-mistakes-prod-only` to `no-mistakes`, its most rigorous leg, as Firstmate's `fm-project-mode.sh` does for mechanical callers. `attempt.begin` records an override that the mate passes, and writes the card's mode into the task message as its `Delivery:` line, so the worker reads the mode from the card. A task that names another mode is refused. A worker that already runs keeps its mode: a new mode needs a new attempt. `cardd project delivery` changes the default for later cards only, and `cardd card delivery` changes one card that has no live worker (see Command line).
- A local-only card has no PR. Its worker starts from the clone's local base branch, without a fetch, because local-only work lands there and never on origin. Its `done` carries where its branch lands instead of a PR lookup, and raises the same merge question about the branch. The timed check and close never look up a PR for it.
- `attempts.ts`: an attempt is one run of a card by one worker. Its ID is the retry key for dispatch. A dispatch retry on the same host finds the same attempt, with the same token and no second task message. A new attempt gets its task message in the same transaction, so a retry can neither lose it nor repeat it.
- A worker names its own branch, as Firstmate's workers do (`fm-task-branch.sh`). A new attempt's worktree starts on a placeholder branch named for the attempt, such as `c-83-a1`, with `attempts.branch_named` at 0. The worker's first action is the `branch(name)` tool: the name is `<type>/<slug>` (`branchNameProblem` in `@fleet/protocol` owns the rule), the extension refuses a name taken in the clone or on origin and renames the branch it is on, and the `branch.name` op records it in `attempts.branch`, refusing a name that is another live attempt's in the same project. If the record is refused, the rename is undone. A branch is named once: naming the same name again confirms it, and another name is refused. Every consumer that needs a card's branch (the PR lookup, close's landed check, the archive, the local-only fast-forward, a resumed dispatch, and `board(card=N)`) reads `attempts.branch`, so none of them guesses a name. Attempts made before this, including those on `fm/c-N` branches, have `branch_named` at 1 and keep the branch they have. A scout makes no branch, so it never names one.
- `deliveries.ts`: every unconfirmed entry is pushed at a connect, otherwise only the pending ones. Each push carries its card's short name, which the message shows after the card number. No entry quotes the comment it answers, so when a second mate steers its worker right after main's comment, the worker gets the steer alone, never main's words to its mate.
- Delivery and intake are two facts. A delivery's state says where the entry is: pending, pushed, acknowledged, or confirmed in the session file. Its intake says whether the receiving model took it in: a run that held it in context ended with no abort and no error. A message can sit in the session file and still not be taken in, when the captain aborts the turn or the provider fails, and Pi drops a queued follow-up on Escape. The extension's `ack` therefore comes when that run settles, not when Pi adds the message, so a `cardd` that is older than the extension only records the acknowledgement later.
- The timed check chases a mate's delivery that is not taken in once the mate has been idle past the intake grace, as Firstmate's task inbox re-rings an unhandled record and then escalates it. It sends the same entry again once, marked `again`, which the extension injects even though the session file has it. One grace later it escalates once: to the lane's parent as a `missed` finding, or for main, as a note on the card, which the board shows. Then it stops. A worker's delivery is never chased: a worker the captain stopped stays stopped. This tracks whether a message was taken in, not whether anybody answered it.
- `server.ts`: one websocket per session, plus `POST /call` with a bearer token for scripts. The first message must be hello with the token. Every later message checks that the session is still live, so an ended or replaced attempt loses access at once. At start no session is connected: live sessions reconnect and become idle.
- `web.ts`: the board has no login, and only the Tailscale network reaches `cardd` (spec section 21.4). Every board request must name an allowed Host, which closes DNS rebinding, and its Origin, when present, must be allowed.

### The timed check

- `check.ts` is one level-triggered pass over `cards.db`. Each rule finds (card, condition) pairs. A finding is written once while its condition holds and clears when it stops. When everything is in order, the check wakes nobody.
- Workers never name their PR. `pulls.ts` finds a ship card's PR on GitHub by its attempts' branches, newest first, in the project's repository (`projects.repo`): `gh pr list --repo --head <branch> --state all`. It looks it up for a worker's done report, for each check pass, and before close, each time fresh. The URL found last is kept on the card only for the board and the merge question's text. A project with no repository on record is never looked up.
- PR state is read with `gh` before the check's transaction. A PR that could not be read keeps its PR findings open.
- A done report on a ship card carries what the lookup found, for the mate to read: the PR's URL and state, a note that no PR has the card's branch as its head, or why the lookup failed. A done with no PR still reaches the mate, which asks the worker to open one. A PR found already merged or closed raises no merge question.
- A finished card (done reported or PR merged, no hold) only needs closing, so its mate is reminded sooner, and the lane's parent hears when a second mate leaves it open. Only the mate closes it.
- Past the list of reminder times, one more fires for each repeat of the last gap.
- Before close, `cardd` finds the PR of a ship card whose merge is not on record yet, so a worker that just merged need not wait for the next pass. That finding is told to nobody, because the mate is closing the card.
- `github.ts`: `gh pr checks` exits non-zero while checks fail or pend, so its JSON decides. A failed read is an error, not an empty list. Only "no checks reported" is empty.
- `timing.ts` holds the timers of spec section 28. Three missed job heartbeats make a job lost.

### Runtime incidents

- A runtime incident is one failure episode of one actor, a worker or a mate: a model turn that ended in an error, a worker that never connected, or a worker connection that was lost. `incidents.ts` owns them. They are not report entries, so they never change a card's status and never take back a `done` or a pause. The record keeps the actor's intent (working, paused, completed, closed) from the card when the incident opens, and only a working card is offered recovery.
- The error comes from Pi's own failed assistant message, read at `agent_settled` by `failure.ts`, so no second model turn is needed to learn the cause. Reading it at the settle and not at each message keeps a failure that Pi's own retry or a queued follow-up cured in the same run from being reported. A failed turn also skips the handoff nudge and the `stopped` report, since both would need another model call that would fail the same way. A failure the extension cannot send at once is kept and sent at the next connect.
- A failed compaction (`session_compact_failed`, not an abort) is a `compaction` incident with its original error, told once like a turn failure. Only a successful `session_compact` verifies its recovery, after the recovery check reached the process; a retry or a replacement makes the extension compact once, without a model turn. A turn that succeeds does not clear a compaction incident, and a compaction does not clear a turn incident. A `stale-module` error, a missing import from an old loaded bundle, offers only `replace`, which keeps the same session and card. Fleet decides recovery from the error text alone and does not rely on any router fallback.
- Recovery never creates a card, a conversation, or an attempt: every incident and recovery entry is on the actor's own card. The one card fleet makes is the captain card for main's own failure, since main has no card, and it is not a recovery.
- `sanitize` hides bearer tokens, key-shaped strings, and long opaque words, and cuts the text, before it is stored or told. `classify` is a pure match on that text: `stale-module`, `router-cooldown`, `vendor-quota`, `auth`, `transient`, or `unknown`. Unknown stays unknown. A local router cooldown is never called a vendor quota, and the router's own timers are not used as a vendor reset. Only a `Retry-After` in the error is trusted as a reset time.
- An actor has at most one live incident (`one_live_incident`). Repeated errors of the episode add to its count and tell nobody. The direct parent hears once when it opens: a worker's mate, a second mate's main. Main has no parent, so its incident is a card for the captain with a hold on the captain, which the board shows with no agent involved. The timed check ties the `worker-never-connected` and `worker-not-connected` findings to an incident, so those findings carry its id and stay the one message. A worker that is paused or finished gets no incident from the watchdog. A second mate whose connection is lost, not closed cleanly, for longer than the not-connected grace gets an incident for main, unless main marked it with `lane.stopping` when it stopped the lane on purpose. The mark clears at the mate's next connect. A mate that reconnects in the same process clears a lost or startup incident, so a network blip leaves no open incident. A live incident also holds back the idle finding and the `missed` chase for that actor, since the same failure caused them.
- A session's `process` is a random id that the extension sends in `hello`. A new one raises `generation`. A new process closes an open incident as superseded, since a failure of the new process is a new episode. A cardd restart keeps the process id, so it keeps the incident and tells nothing again.
- `card.restart` (the `restart_card` tool) is for the direct parent only. It carries the card, the incident, the generation it read, a mode, and a key. In one transaction it refuses a foreign parent, a stale generation, a paused or finished card, a mode the class does not allow or whose budget is spent, and a time before the incident's eligible time. A second recovery with another key while one runs is refused, and the same key answers with the same plan, so a retried call after a crash never starts a second one. Budgets are two retries and one replacement for each episode. A retry waits 30 s, then 2 min, never less than the `Retry-After`. A vendor quota with no known reset and bad credentials are blocked at once: restarting is not a repair.
- Recovery sends a health check, never a task. `retry` delivers it to the live process. `replace` records it and delivers it only when the new process connects, so the old process can never answer it. The recovery is verified when the check's turn settled without an error (the same acknowledgement that marks intake) and the actor then made a `report`, `comment`, or `board` call after the check reached it. A process that merely started does not verify. A failed check turn, or no verification within the window, spends the attempt, is told once, and ends in `blocked` when no mode is left. The extension takes a recovery check as an end of run that needs no handoff, so it never nudges a paused worker into work.
- Times that a person or a vendor sets, the eligible time and the `Retry-After`, read the controllable wall clock. The verification window uses the real clock.

### Closing

`closing.ts`: close decides Done or Dropped from the record (guard 7, spec section 20.5), the way Firstmate's teardown did. A local-only card lands only when its landing is authorized: the card is Merging, by yolo or by the captain's approval. Then `close.begin` asks the host to land it. Done means landed. A merged PR landed everything. Otherwise the worker's latest handoff must be done. A task or comment routed to the worker takes that completion back, including a replacement attempt's task. Coordination routed to a mate or the captain does not: it asks no new work of the worker. The entry record is replayed for close and finished-card reminders, so a restart needs no separate completion state. A ship card must have no unmerged PR, and the host confirms that no attempt has a commit off the base branch or an uncommitted file. Dropped is never a fallback: the mate asks for it with `landed=false`, and a merged PR refuses it. A captain card has no worker, so it closes as Done once the captain acted. The record is checked again after the host confirms. When a second mate closes its own card, main hears. When main closes it, the card's mate hears.

## Extension

### Entry and arguments

- `index.ts`: dispatch starts each worker with `--fleet-url`, `--fleet-token`, and `--fleet-role`. `FLEET_URL`, `FLEET_TOKEN`, and `FLEET_ROLE` work too. A Pi in a lane home needs none of them: the home's `config/lane.json` makes it that lane's mate. Without either, the extension does nothing.
- `fleet-args.ts`: each value follows `=` in its flag, because Pi reads a separate value that begins with `-` as an option, and 1 `cardd` token in 64 begins with `-`. `launch.ts` turns `--token <value>` into `--token=<value>` for the same reason.
- `.pi/extensions/fleet.ts` loads the fleet extensions only in a lane home. A worker in a worktree of this repository has no `config/lane.json`, so it loads nothing from there and needs no installed packages. Dispatch gives workers the extension with `-e`.
- Activity at each run and tool call keeps `last_activity` fresh for the stall check (spec section 12.2).

### Sessions

- `link.ts` holds the session's one websocket. It sends hello with the fleet entry IDs found in the session file, reconnects with backoff, and matches calls with their results. A message from `cardd` that fails the protocol schema closes the socket, which reconnects with backoff, and the session says so once until it connects again. An exception in a websocket listener would end Pi, so a `cardd` on other code would crash-loop every mate.
- `plan.ts` fetches the mate's plan with `lane.plan` at the first connect, keeps it for the life of the process, and adds the goal and schedule to the system prompt in its own `before_agent_start` handler, after the role contract and the charter, waiting for a fetch that is under way. A plan that cannot be fetched is tried again at the next connect. Because it is read once, a changed plan applies at the next start. `wake.ts` is the `fleet wake` command: it posts the `wake` op with the lane's own token.
- `intake.ts` acknowledges each fleet message that reached the model when its run settles, unless the run was aborted or its last answer failed. `link.ts` keeps an acknowledgement made while `cardd` is unreachable and sends it at the next connect.
- The mate-only `yield` tool in `mate.ts` returns Pi's native `terminate: true` with empty content. It ends the automatic model follow-up without aborting, so normal settle, intake acknowledgment, activity, and conversation memory still run. Queued fleet messages still reach the model. Pi requires every tool in a batch to terminate, so the prompt asks the mate to call yield alone, after required card actions and replies. Its self-rendered call and result draw zero lines even with calm off. Silence never substitutes for a meaningful outcome.
- `inbox.ts`: Pi skips session file lines that do not parse, such as a line torn by a crash, and so does the extension. Pi creates the session file late, so it may not exist yet. A time from the model must be ISO 8601 with `Z` or an offset, so no host's zone can shift it.
- `worker.ts`: a run may end only with a handoff, a tracked wait, or a queued continuation. Otherwise the worker gets one nudge, then files `stopped`. A run whose last turn failed gets neither: the failure is a runtime incident (see Runtime incidents).
- `prompts.ts` adds the role contract to the system prompt of every run, so the contract follows the role wherever Pi starts.
- `views.ts` prints `board` in the AXI shape (https://axi.md): TOON records, few fields by default, counts first, long text cut with its size, an explicit empty state, and next steps. It is pure. The board's header is AXI ambient context: the projects with their yolo flag and, for main alone, the lanes. Past a set number of projects, it lists only those with open cards or yolo on. A second mate reads only its own lane through `board`, including its lane card and the cards it created. Main reads every lane. `cardd` scopes the `board` and `card` operations by the authenticated session's lane, so counts cover only visible cards and opening another lane's card tells a second mate to ask main. Projects remain shared. The captain's web board stays unrestricted. Mates never read with sqlite.

### Dispatch and herdr

- `dispatch.ts`: `cardd` creates or finds the attempt. Each host step then looks for its own result by the names that derive from the attempt ID, so a retry after a lost connection never starts a second worker.
- herdr counts an agent as ready when it idles, and a worker starts on its task at once, so herdr's own wait often runs out. Dispatch does not rely on it: the pane shows whether Pi started. herdr's minimum wait is just above 3 s.
- herdr refuses a start and types nothing when the shell is not at its prompt yet, or when it still holds the agent name of a worker that died a moment ago, for up to about 4 s on CI. A refused start goes again at once. A command lost before the shell goes once more. herdr refuses a pane where Pi runs, so no second Pi starts.
- A new shell first runs its prompt's helpers, such as git, and keys typed then can be lost. So a start waits until the shell is idle.
- Pi in the worker's pane is the truth about a worker, because `cardd` may not have seen it die yet. Pi names its process `pi`: macOS reports it as argv0, Linux as the process name.
- `host.ts`: a host that is neither listed in `FLEET_HOSTS` nor this lane's own host (`host` in `config/lane.json`, `FLEET_HOST`, or the hostname) has no transport, and `NoTransport` is thrown before anything runs. Running its command here would act on this host's disk with another host's paths. The close and startup refreshes print `skipped: no transport for <host>`. A host listed in `FLEET_HOSTS` runs herdr through its transport, such as `["ssh", "p620"]`. ssh exits 255 for a lost or refused connection, which, like a probe that times out, means the host is unreachable. `--session` must come before a `--` delimiter, or herdr passes it to the agent. A herdr failure message never shows the command line or a worker token.
- The attempt's worktree is the one at `<clone>.worktrees/<session>`. The worker may switch to its own branch, so the path is the key.
- `place.ts` creates a worker's workspace, tags it with its lane and card, and arranges the host. `arrange.ts` owns the sidebar order: a worker's workspace sits right under its mate's workspace, labeled with the card's name after `└ `, because herdr does not nest plain workspaces, so order and label make the tree. The order is a pure function of the workspace list, so it is the same after any restart. The herdr CLI cannot move a workspace, so `arrange.ts` calls the socket API's `workspace.move_block`, once, only from the first workspace out of place. Ownership is a metadata token on the workspace (`lane`, `card`) because the host cannot ask `cardd`. A workspace with no token follows the workspace above it when its label starts with `└ `. A lane restart tags those followers before it closes the mate's workspace, so they keep their mate when it comes back at the end. `/updatefleet` tags the rest from the board, before it pulls anything. A failed arrange after a start or a dispatch only leaves the sidebar as it was. `/updatefleet` arranges every host once more at the end, through the same `arrangeOn`, even when no mate started there, and names each host that failed.

### Prompt cache policy

- `cache-policy.ts` sets prompt cache retention by role, when the extension starts a session. Every mate (main and each second mate) and every worker asks for the five-minute default, `short`. `cache-ttl.ts` then raises the mate's system prefix to one hour (below). A mate used to ask for one-hour retention, but conversation memory rebuilds most of a mate's prompt on every turn, so a one-hour write (twice the input price) paid for text that the next turn wrote again: on 2026-10-21 one-hour writes cost the mates $141 more than five-minute writes would have. The role map stays so a role can move back to `long` in one line. It covers a mate started by hand, by `fleet up`, and by a restart, and a worker started by `dispatch`, with no environment variable and no personal setting.
- `cache-ttl.ts` splits a mate's cache lifetimes. It loads after `optchat.ts` in `.pi/extensions/fleet.ts`, so it sees the payload after OptChat has placed its view marks. It puts one `1h` breakpoint at the end of the system prompt, which covers the tools before it, and leaves every other breakpoint (the view and the end of the request) at the five-minute default. The view changes every turn, so a one-hour write for it is waste. Anthropic allows four breakpoints, so when OptChat's view marks leave no room, the oldest message mark is dropped. It checks the payload shape, not the model api, so it also works behind a routed model. Workers do not load it and stay at five minutes.
- Pi has no setting for retention. `cacheRetention` is a request option that Pi's agent never sets, except `none` for compaction. The providers read `PI_CACHE_RETENTION` on each request, so the extension sets it in its own process. Each role sets its value and does not unset the variable, so a `long` that a session inherits from its launcher does not leak into it. A provider's own `env` in `auth.json` would still win over the process variable. The fleet does not write it.
- Warming is not managed per role, and the per-role policy for it is not implemented. `cacheWarming` is a global-only Pi setting, in `~/.pi/agent/settings.json`. Pi reads no project file, flag, or environment variable for it, and gives an extension no way to set it. The `cache_warming_decision` event can only stop a refresh that Pi already scheduled, so it cannot turn warming on. Every session follows the global setting. The wanted policy is idle warming for mates and streaming warming for workers. It needs a per-process way to set `cacheWarming` in Pi.
- Idle warming has a second limit. Pi stops it after a run in a session that holds a custom message, such as the `[fleet]` messages every mate gets, because it compares the transcript by object identity and Pi rebuilds custom messages when it refreshes the finalized context. `/session` then shows `Inactive (conversation context changed)`. A fix in Pi is needed before idle warming helps a mate.

### Worker context policy

- `context-policy.ts` limits a worker's context when the extension starts a session. The effective limit is `min(the model's own window, 500K)`, so the 500K is a cap and never raises a window. Compaction runs at 80% of the effective limit: 400K on a 1M or 500K model, 217.6K on a 272K model, 160K on a 200K model. A mate has the same rule with a 400K cap, compacting at 320K. No personal setting and no project file changes.
- Pi 1.3.0 has no flag or environment variable for this. Its settings are files, and `compaction.reserveTokens` is one fixed number subtracted from the window, so no value gives 80% across windows from 200K to 1M. A worker runs in a worktree of any project, so the fleet cannot write a project file either.
- Where the window comes from: under a pi-tiers virtual model Pi stores a virtual model with window 0 and checks the physical model that answers. Before each request, `prepareRequest` routes and calls `AgentSession._exceedsCompactionThreshold(route.model, projection)` with the routed model. After each response, `_checkCompaction` takes the window from `_modelForMessage(message)`, the physical model that produced the message. Both are the routed model, not the virtual one. `SettingsManager.getCompactionSettings` receives only the selected (virtual) model, so it cannot know the window itself.
- The patch point: the extension wraps four members in the worker's own process, like the Calm presentation patches. `_exceedsCompactionThreshold` and `_checkCompaction` set the window they work on for the synchronous part of the call. `getCompactionSettings` turns it into `reserveTokens = 20% of min(window, 500K)`. `_exceedsCompactionThreshold` and `_modelForMessage` hand Pi a model whose window is capped at 500K, so the threshold and the overflow check never see more than 500K. A window that is unknown (0) leaves Pi's own settings, which never raise a window.
- A model switch in mid-session needs nothing extra: each request is routed again and checked against the model that will answer. A session at 170K that a tier moves from a 1M model to a 200K model compacts before that request, because 170K is over the 160K of the 200K model. A session that goes the other way keeps its context until the larger model's 80%.
- A mate over its 400K cap with compaction unable to run is refused, not truncated. While compaction is failing (a `session_compact_failed`, or OptChat's `fleet:compactor` unhealthy event), the mate keeps working and its memory keeps growing. `context-guard.ts` checks the context at each request (`context_with_system`: the last reported usage plus the size of what came after it). Over 400K with compaction down, it aborts the request, keeps the pending input in the session, and raises c-383's blockage with `blocked: context over 400K, waiting for compaction`. It retries a compaction every minute (`FLEET_COMPACTION_RETRY_MS`). When one succeeds, it clears the block and sends a `[fleet] compaction` message that triggers a turn on the same conversation, which picks up the pending input.
- A Pi that lacks one of the members makes the patch print `Fleet context limit: unavailable` and the worker keeps Pi's own limit. `e2e/extension/context-policy.test.ts` pins the behavior on Pi 1.3.0, so a Pi bump that moves a member fails it.
- The footer's percentage still counts against the real window.

### Jobs

- `jobs.ts`: `cardd` records a job first. The wrapper posts the result, which arrives as a fleet entry, also after a Pi restart. Nothing runs a job again. A running job is a tracked wait.
- `stop_job` stops one named job of the calling worker. `cardd` decides ownership: `job.stop` finds the job only among the caller's attempt's jobs, so a foreign or missing job is refused before anything is signalled, and a finished one answers "not running". Only after that does the extension find the job's tab in the worker's own workspace and send ctrl+c to its pane. The wrapper stops its own process group and posts the usual `exited 130` result, so the result is reported the way an interrupt always was. The extension never signals by name or pattern, and `prompts/worker.md` forbids it for a worker.
- `job.ts` is the wrapper. It reads its job from a private file, so the token never appears in shell history. It keeps the last lines of output, whole across split reads and split characters. It sends heartbeats until the result is taken. A closed tab can take the wrapper down soon after its hangup, so it reports as soon as the command ends or a moment passes, and `cardd` keeps only the first result. A 401 means the attempt ended and nobody waits.

### Recovery

- `restart.ts` is the parent's `restart_card` tool. It calls `card.restart` and, for `replace`, `replaceWorker` in `dispatch.ts`. With an incident it is the recovery of that incident, with its generation fence. Without one it restarts the same card's worker or lane mate on the same conversation, at most 3 times an hour for each card, and a repeated key does nothing. `dispatch` creates its own card and only starts new work. A repeated call finds the card by its name and the attempt that already started. A replacement finds the same attempt through a resumed `attempt.begin`, so no new attempt, branch, or token appears. It finds the pane's `pi` process by the pane's own process list, signals that pid with TERM and then KILL, and starts the new process only when the pane's shell is idle again. It never signals by name or pattern. If the old process cannot be confirmed stopped, nothing is started. The new process opens the same session id with the same arguments, so the conversation, the worktree, and its dirty files are the ones it had. A second mate is replaced through the existing `lane restart` of main. A request that repeats a key never stops a process: the plan says `repeat`, and a process that already runs is left alone, so a retry after a crash cannot kill the replacement it started. A second mate's repeat does nothing.
- Errors that happen before the extension loads, such as a Pi that exits at startup, are seen only by the watchdog, as a worker that never connected. The pane's output is not captured, so such an incident has no cause text and is classed `unknown`.
- `e2e/extension/runtime-failure.test.ts` drives real Pi workers and mates against a real `cardd` and moves the controlled clock. `e2e/extension/recovery.test.ts` replaces real herdr panes. They kill only the pids they started.

### Prerequisites

- Every prerequisite of a host is one table in `prerequisites.ts`: the tools with their floors and fixes, plus the conversation-memory profile of each home. `fleet up`, `fleet restart`, `fleet update`, use it, so there is one check and one set of messages. The profile check looks for both files the memory reads at start, `AGENTS.md` and `config.json`, because a missing one stops the memory and crash-loops the mate. `gh-login.ts` decides the gh login line from `gh auth status`, which exits 1 for every failure. Only "not logged into any" text, an empty `--json hosts` result, a rejected refresh token, or a 401 from GitHub says `gh is not logged in`. A timeout, a network error, a signal, a spawn error, or any other exit says `could not check gh login on <host>: <reason>`, with token-shaped text hidden. `FLEET_PROBE_TIMEOUT_MS` sets the probe timeout.

### Review pages

- There is no review tool. A worker opens a Lavish page with `lavish-axi`, reports `needs-decision` with the page link so its mate hears that the page is ready, and polls with `run_long` (at most 2 hours for each job). A poll that times out is started again, and Lavish keeps feedback sent between polls until a poll takes it. The poll result is an ordinary job result for the worker.

### Closing on the host

`closing.ts` runs close in this order: stop every writer (close the worker's workspace, which ends Pi and its job tabs), archive and verify all unlanded work, remove the worktree, then close the card. Each step finds its own result first, so a rerun converges. A worker may have moved its worktree to its own branch, which goes too, after the archive. An unreachable host of an attempt that no longer runs cannot be asked, and its work stays in place. A commit has landed when it is on the base branch or on `origin/<base>`, because dispatch branches from origin's base, which can be ahead of the clone's. `ORIGIN_BASE_IF_FETCHED` names that ref when it exists, and `archive.sh` does the same. `UNLANDED_COUNTS_SCRIPT` prints the commits not landed and the changed or untracked files: the worktree decides while it exists, and its branch after. `DELETE_ARCHIVED_BRANCH_SCRIPT` deletes the task branch once its work is archived or landed. It tolerates only a missing branch, and is safe to rerun. A local-only card lands first, as Firstmate's `fm-merge-local.sh` does: `LAND_LOCALLY_SCRIPT` fast-forwards the clone's base branch to the newest attempt's branch, only when the clone is on its base branch and clean and the branch is a fast-forward, and never pushes. Any uncommitted file in a worktree refuses it first, so a landing never leaves work behind. A rerun after a landing is a no-op fast-forward. Last, close refreshes the clones that `close.begin` lists (see Clones). It lists none for a local-only card, and main's first refresh skips local-only projects, as Firstmate's fleet sync does, because their local base branch is ahead of origin by design. A host that just failed to answer is already named in the outcome, so it is not waited for again.

### Clones

Clones keep up with their remote the way Firstmate's `fm-spawn.sh` and `fm-fleet-sync.sh` keep them. `sync.sh` is a POSIX port of `fm-fleet-sync.sh` and `fm-lock-lib.sh`, because a host's `sh` may be dash. It defines functions only, and each caller appends its own call.

- `dispatch.ts`: a new task branch starts at `origin/<base>`, fetched just now, with no tracking, so a push never goes to the base. A failed fetch, or an origin without the base, refuses the dispatch rather than start from a stale base. A clone with no origin starts from its own base. A rerun that finds the branch reuses it without fetching.
- `refresh_clone` fetches with `--prune`, deletes branches whose remote branch is gone unless a worktree has them checked out, and fast-forwards a clean base branch. It never forces, stashes, or discards. A clone that is dirty, on another branch, detached with its own commits, or diverged is left alone and printed as `STUCK`. A clean detached HEAD with no commits of its own goes back on the base. A folder inside another repository is skipped, because git looks upward and would refresh that one. A fleet home (it has `config/lane.json`) is only fetched: it moves with `/updatefleet`, which also builds and restarts.
- `fetch_origin` retries a fetch blocked by `packed-refs.lock` three times a second apart, since a live owner soon exits. It then removes the lock only when it is at least 30 s old and `lsof` proves that nothing holds it or the clone. Any doubt keeps the lock.
- `clones.ts`: `close.begin` lists every host's clone of a ship card's project. A scout changes nothing on the remote, as in Firstmate's teardown. Two host names can lead to one clone, so clones are refreshed in turn. A fetch over a slow link gets 120 s. Main refreshes every registered clone when it first joins `cardd`, as Firstmate's session start does, and wakes only for a `STUCK` clone, the one state that Firstmate's bootstrap diagnostics mark as needing attention. Other lines wait for main's next turn.

### Lanes and homes

- `homes.ts`: main's home is the repository. A second mate's home is a worktree, `<root>.worktrees/lane-<lane>`, that shares the root's installed packages. A lane is running (its mate is in the pane), down (it should run and does not), or stopped (held by hand or for crashing, so only `up <lane>` starts it). A lane that starts too often within a window is held. Naming a held lane lifts the hold and forgets its crashes. `--continue` keeps the mate's conversation across a restart. A start defaults to `--model tier/orchestrator`, because `--continue` would otherwise resume the model that the session last used. Explicit `--model` or `--provider` flags in the lane's `args` take precedence and are preserved (`mateStartArgs` in `lane-config.ts`), including routes tied to a lane's separate identity. `direnv exec` loads the folder's `.envrc` and replaces itself with Pi.
- Starting a mate waits until Pi shows in the pane. Until then the pane looks idle, and a second `up` would type the command again.
- `lifecycle-lock.ts`: `up`, `stop`, and `restart` own a lane only inside a `BEGIN IMMEDIATE` transaction on `<home>/state/lifecycle.db`. Each `fleet` command is its own process, so an in-process queue cannot stop a supervisor's `up` and a `restart` from both finding the lane down and both starting it. SQLite's lock is held by the open file, so the OS releases it when its owner dies, and no stale owner is ever reaped by age or PID. The database holds no rows. A command that waits longer than `FLEET_LIFECYCLE_WAIT_MS` (45 seconds by default, longer than one start) fails and changes nothing.
- `lanes.ts`: each host runs its own `fleet` for its lanes. Main reaches its host directly and the others over their transport. A non-interactive shell does not expand `~`, so a remote checkout path is given whole. A host that cannot be reached is named, never skipped, and reported once until it answers.
- A worker never takes its model from its folder. The fleet repo's `.pi/settings.json` puts the mates on the orchestrator tier, and every worktree of the repo has that file. So unless `workerArgs` name a model, dispatch starts workers on Pi's global default model from the agent folder's `settings.json`.
- `titles.ts` owns the mates' names: `1stmate` for main, `2ndmate-<lane>` for a second mate. A mate gives its Pi session and its herdr workspace that name at start, so main gets it too, though the captain opens main's workspace by hand. Workspaces are still found by the earlier `fleet-<lane>` label, because a mate that started on earlier code keeps that label until it restarts.
- `lane-config.ts` reads `<home>/config/lane.json`. It is private because it holds the lane's token. `roots` defaults to `~/.fleet/app` for a remote host. `direnv` names a folder whose environment the mate runs in, while its home stays where it is.
- `update.ts` is one host's half of `/updatefleet`, run as `fleet update [--check]`. It prints one JSON line. `--check` fetches and finds every reason to refuse: a checkout off `main`, uncommitted changes, or commits that are not on `origin/main`, in the checkout or in any lane home. The update checks again, fast-forwards, runs `npm ci` when the lockfile changed or `node_modules` is missing, always builds the board, and moves each lane home to the new commit. The board build is cheap and makes a rerun converge after a failed build. A lane home moves only after the build, so a failed build leaves every mate on the code it runs. `fleet cardd` does the same for `cardd`'s checkout, and restarts `cardd` only when the commit that `cardd` reports running differs from the new one in `cardd`'s code, or is unknown. The running commit decides, not the pull, because a checkout can move without a restart, and a restart that failed must happen again on the next run. It backs up the database with `VACUUM INTO`, which copies a live WAL database consistently, just before the restart, since migrations run only when `cardd` starts. Pending migrations never run while the old `cardd` serves.
- `updating.ts` is main's half. It checks every host before it changes any, so a dirty home or an unreachable host stops the update with nothing pulled. Then it updates the hosts in turn, and stops at the first failure without restarting a mate. Then it updates `cardd`, and waits until `GET /api/version` answers with the new commit, which proves that the new process serves, not the old one. HTTP and not a session, because a second session with main's token would supersede main's own. Only when every host is updated and `cardd` runs the new code does it restart the lanes, as `lane("all", "restart")` does. Main restarts last. Pi cannot restart its own process, so a detached `relaunch.ts` waits for main's Pi to exit and its shell to be idle, then runs `pi --continue` with main's arguments in main's herdr pane. Main restarts when the turn that tells the captain ends. The command hands its report to main as a message that starts that turn, because Pi saves a conversation only once it has a reply, and `pi --continue` would otherwise start a new one.
- `migrate.ts` only copies, so a repeat never overwrites edits. Undoing renames the settings back and sets each home's `lane.json` aside.

### Memory

- `optchat.ts` loads OptChat from `packages/extension/vendor/optchat` with `FM_HOME` set to the home, when the home has `config/optchat.json`. The loader reads `FM_HOME` when its module is evaluated, so the variable is set around the import. The vendored folder is third-party code with its own style: lint, format, and knip skip it because their config files list it, and the typecheck skips it because `optchat.ts` imports it by URL, which `tsc` does not follow. Fleet's own changes to it are listed in its `README.md`.
- `memory.ts` writes what the loader reads, all inside one home. Each step that is done already is left alone. A profile's lock socket must fit a socket path: 104 bytes on macOS and 108 elsewhere, with the NUL.

### Standing rules and stow

- `standing.ts` reads the three files in `data/` on every turn, in `before_agent_start`, so a mate's own edit takes effect on its next turn with no reload. Only `AGENTS.md` and the other context files need Pi's reload, because Pi reads them once.
- Main's `captain-shared.md` reaches second mates by copy, not by reading main's home, because a lane's home can be on another host. Main pushes the bytes as base64 on the command line of `fleet shared`, through the host's transport, so no host needs a shared file system. The push runs each minute before main starts lanes, so a lane that starts already holds the file. It also runs at the end of `/stow`. A failed push to a host that answers is told once, and never stops the lanes from being kept running. A copy is read-only and replaced by rename, so a mate never reads half a file. Like Firstmate, a copy that someone edited is kept aside before it is replaced or removed: the home's `state/captain-shared.published` holds the bytes main last put there, and a copy that matches neither that nor main's file was edited. The aside copy is a plain sibling that no loader reads, so it is never a second shared file. A copy with no record, such as one from before this existed, counts as edited. The mode is only a nudge: main's bytes always win.
- The stale flags in the stow report are computed, not judged, because the model gets date arithmetic wrong. The entry format is one bullet line with an optional trailing marker. Anything else in a file is prose that the report skips.
- `stow.ts` ends the command by waiting for `agent_settled`, then reloading. Pi allows `reload` only in a command handler. `sendMessage` returns before the turn starts, so `waitForIdle` right after it could return at once, which is why the command waits for the settle event it sets up first. A reload runs the extension factory again, so the link to cardd reconnects, and main checks the clones again on its first connection.
- `e2e/extension/standing.test.ts` gives its mates Pi's context files and built-in tools, which the other tests turn off, because `AGENTS.md` and the model's `write` are what it checks. Its stow tests set `FLEET_SUPERVISE_MS` to ten minutes, so only the stow can have published the shared file. It does not wait a fixed time: it waits for the probe's `session_start` event with reason `reload`.

### Calm

[calm.md](calm.md) owns what the captain sees. Inside:

- `layout.ts` patches the render of three Pi components. `ToolExecutionComponent` draws nothing, unless the row has an image, because an image is content. Without Pi's image list, a row counts as having images: showing a row is the safe error. `CustomMessageComponent` draws nothing for a `fleet` message. `AssistantMessageComponent` loses collapsed thinking and short pre-tool text from a shallow copy before layout. Pi's later refreshes read the full message back.
- Each patch probes the Pi member it replaces. `index.ts` skips a missing one with a diagnostic. A patch installs once per process. A reload evaluates the module again, so the flag lives in one process-wide object in `state.ts`.
- Calm drops thinking while it is on and Pi hides thinking (`hideThinkingBlock`). It does not read or set Pi's hidden-thinking label, because anything can reset the label, and a reset label shows `Thinking...`. Setting the label makes Pi lay out every assistant row again, so Calm sets it back to Pi's default on each toggle to apply the toggle to rows already on screen. Without a terminal (print and RPC modes), calm only records its state.
- `e2e/extension/calm.test.ts` navigates the fullscreen transcript before checking restored rows. Herdr's recent terminal output can contain only the current viewport after a redraw, not every retained message. Ctrl+Home reveals the earlier fleet, note, and tool rows; Ctrl+End reveals the later conversation. The test sends their standard terminal sequences because herdr 0.9.5 does not name those modified keys.
- One logical run lasts from `agent_start` to `agent_settled`, which also covers abort and failure, so the boat does not flicker between tool calls.
- `preference.ts` replaces `config/calm` atomically, so a crash never leaves half a value. The choice is saved before the screen changes, so a failed write changes nothing.
- `ship-sprite.ts` owns the geometry, the bounce track, and the two linked cadences. Every tick moves the water a quarter cell, and every fourth tick moves the boat one cell, so the trough stays under the boat. Ticks, not wall time, drive every change. Hiding freezes the sprite at its last painted frame, and the next run resumes there. A fresh session resets it. State never sits in a module-level singleton. The boat at an endpoint already carries the new direction. A resize recomputes and clamps the track before the next frame.
- `ship.ts` paints runs with standard ANSI codes only: one blue for water, so the swell reads through glyph height, and one yellow for the whole boat. It recomputes the track from the render width on every frame. The widget key `calm-working-ship` is shared with Firstmate's calm and the standalone Pi calm, so a session that loads more than one shows a single boat. Its timer never keeps Pi's process alive.

### Transcript

[transcript.md](transcript.md) owns what the captain sees. Inside:

- Pi has no hook around a whole message. Its Markdown transform sees one text block at a time and has no message identity, and `registerMessageRenderer` covers only custom messages. So `transcript/layout.ts` patches the `render` of `UserMessageComponent`, `AssistantMessageComponent`, and `CustomMessageComponent`, as Calm does, and each patch draws the rule around the lines Pi drew. A Markdown transformer would draw one rule for each text block.
- The patch keeps no state about earlier messages. Pi draws every message again at each frame, on a resize, and when a restart replays the history, so a rule that depended on the last message drawn would repeat or vanish. The rule depends only on the message and the width.
- Pi's assistant and custom rows start with their own blank line, and the rule goes under it. A user row has its blank line outside it, in a `Spacer` that Pi adds before the row, so the rule goes first. An empty row stays empty, which is why a silent reply has no rule.
- `state.ts` holds Pi's live theme, in one process-wide object like Calm's. `ctx.ui.theme` is a proxy for the current theme, so a theme change reaches rows already on screen. It never holds the extension context itself: after `/new`, the old context is stale, and reading it from a render crashes Pi. Without a terminal nothing sets it and nothing is drawn.
- The mate's own replies have a rule and no name. The one list of the fleet's own message types, `FLEET_ROW_TYPES` in `layout.ts`, decides both which rows are labelled `fleet` and which get the framed renderer. A type missing from it keeps Pi's raw `[type]` header.
- `patch.ts` is shared with Calm: install a patch once per process, probe the Pi member it replaces, and report a missing one with a line. Each patch loses only its own part if a Pi release moves the member.
- `index.ts` registers a message renderer for the fleet's own rows. It draws the text in Pi's custom-message box without its `[fleet]` label. `@earendil-works/pi-tui` is a peer dependency of the extension, as `pi-coding-agent` is, because the renderer builds `Box` and `Text` at run time.

## Board

- `App.tsx` reloads the board on every change and keeps only the newest load. It keeps what the captain started to write on each card when he goes back to the board.
- `route.ts`: each card has its own address, `#/c-21`. Opening a card adds a history entry, so Back returns to the board where it was scrolled.
- `format.ts` is pure. A card with a question for the captain needs him, whatever its status. The second mates' lane cards are the Mates group, not work.
- `icons.tsx`: each icon is decorative. The text next to it carries the meaning.

## End-to-end tests

- `e2e/support/scratch.ts` makes a scratch copy of the repository with its own lane homes. A second mate's memory profile in a scratch home has a lock socket path longer than macOS's 103-byte limit, whatever `TMPDIR` is. So the tests that make one skip on macOS, and CI on Linux runs them.
- `e2e/support/fake-model.ts` is a Pi extension that posts each model call to the test's control server and returns the move the test chooses. Everything else in Pi stays real.
- `e2e/support/fake-anthropic.ts` registers a `tier` provider on Pi's real Anthropic Messages client, pointed at the control server, so the harness reads the actual request: its `cache_control` retention and whether it is a one-token warm. The harness answers with a server-sent-event stream. `harness.wire` lists the requests, with the role taken from the system prompt.
- `e2e/support/herdr.ts` runs an isolated herdr session whose name starts with `fleet-lab-`, so a test never touches the captain's session.
- `e2e/support/hermetic-env.ts` removes the fleet variables that a live mate exports, such as `FLEET_HOSTS`, `FLEET_ROOTS`, and `FLEET_ROOT`, as soon as a test loads its support. The extension and `fleet` read those variables before their lane config, so a run started from a mate's shell would otherwise send a scratch fleet's commands to the live hosts and checkouts. Every module that spawns a fleet process imports it: `guarded.ts` and `scratch.ts`. `e2e/extension/hermetic.test.ts` runs a two-host test from such an environment and fails if any command reaches the live host.
- `e2e/support/remote.ts` gives a clone a bare remote, `<clone>.git`, and lands commits on it from another clone, as a merged PR does. The dispatch lab names its GitHub repository with `--repo acme/site`, so its clone needs no origin on GitHub: dispatch fetches any origin first. With `remote` set, the lab registers its clone for host `local` only, because the other lab hosts reach the same folder and would refresh it once each.
- A mate `Session` from `e2e/support/cardd.ts` acknowledges each entry it gets, as a mate whose runs end cleanly does, so the timed check never sends it anything again. `connect(token, inFile, false)` makes a mate that never takes anything in.
- `e2e/support/fake-gh.ts` keeps PR state in the JSON file named by `FAKE_GH_STATE`. Both writers publish a complete temporary file with a same-directory rename, so a reader never sees a truncated snapshot. A PR's repository is the owner/name in its URL, and `head` is the branch it was opened from, which `gh pr list --repo --head` matches. `broken` makes `gh pr checks` fail like a network error. `down` makes every call that reaches the PR fail. Every `Cardd` in the tests runs this fake gh, so no test reaches GitHub. The trial runs the real one.
- Scratch puts a successful `gh --version` and `gh auth status` stand-in before the host's tools. FakeGitHub takes precedence for PR commands. The prerequisite tests supply explicit missing and failed-login cases instead of using the host's credentials.
- `e2e/extension/sync.test.ts` scripts lsof's ownership answer. A real host's unrelated inaccessible mounts can make lsof's negative result incomplete. The product keeps the lock in that case. The test covers a clean negative result, a holder, an inspection failure, an incomplete clone scan, and a recent lock without weakening the product's checks.
- The model harness accepts only `POST /model`. Closing its websocket server removes the upgrade listener, so a late probe handshake can arrive as an ordinary HTTP GET. It receives 404 rather than entering the JSON model parser.
- `e2e/support/flaky-transport.ts` behaves like ssh whose connection drops right after the worker started: the first `herdr agent start` that succeeds loses its output and exits 255. `switch-transport.ts` fails like an unreachable host once its marker file exists. A marker that starts with `hang` hangs instead, and one that starts with `flood` floods every command but herdr's.
- `e2e/trial/trial.ts` is a real-model trial, not a test: `node e2e/trial/trial.ts <project clone> [model]`.
- `e2e/pi/contract.test.ts` pins the Pi behavior the extension depends on. A Pi upgrade that changes it fails there first.
- Tests that start processes stop every part even when one part fails, so no process outlives a test.
- A `cardd` token begins with `-` 1 time in 64. Tests force such tokens to prove that Pi reads each one as a value, not an option.
- `e2e/extension/dispatch.test.ts` bounds a restart below `FORMER_REFUSED_START_WAIT_MS`, the 10 s that a refused start once waited for a Pi that herdr never typed.
- `e2e/extension/start.test.ts` holds the worker's first model call open, so the worker stays busy while herdr's start command still waits for it to idle. The mate must hear back before that command ends. A clock on the whole dispatch would also count the shell's start and herdr's refusals, which load stretches.
- When a job's tab closes, either the wrapper posts what the command printed as it died, or the tab's processes go first and the heartbeat check reports the job lost. Which one wins depends on the platform and timing. `e2e/extension/jobs.test.ts` accepts either, once.
- `e2e/extension/memory.test.ts` runs the vendored memory. The model's turn may start with the memory's own context block, so the test finds the fleet message after it. Its second-mate tests skip on macOS, because the profile's socket path cannot fit 103 bytes there. CI on Linux runs them.
- `e2e/extension/worker-model.test.ts` starts main as a plain Pi in a scratch copy that picks its model from its settings, as the captain's does. Pi picks a model from its settings only when it knows a key for that model's provider at session start, so the test gives the scripted tiers a key. Main and its worker share the lab's model agent, so the system prompt tells their calls apart.
