# The code

Code in this repository has no comments. A lint rule fails on any comment. What a comment would say goes into a name, a type, or a smaller function. What a name cannot carry, such as why a module is shaped the way it is, lives here. [The spec](spec.md) owns the design. This file owns the reasons in the code that the spec does not name.

## Gates

- `.oxlintrc.json` holds the lint rules, including the resolved ESLint recommended, typescript-eslint strict and stylistic type-checked, and React Hooks recommended-latest policies. Every Oxlint category except nursery (correctness, suspicious, pedantic, perf, style, restriction) is on for the `typescript`, `eslint`, `unicorn`, `oxc`, `import`, `promise`, `node`, `react`, `react-perf`, and `jsx-a11y` plugins, and a rule the code does not pass is switched off by name in `rules`, so an off rule is a rule that some code violates. Nursery rules are unstable. The `jest`, `vitest`, `vue`, `nextjs`, and `jsdoc` plugins stay off: the tests use `node:test`, the repository uses none of the other libraries, and comments are banned. An Oxlint upgrade that adds a rule can turn the lint red, and that upgrade fixes the code or switches the rule off by name. The explicit entries in `rules` carry the options of the adopted policies. All core rules run natively and the Oxlint JS plugins are only `eslint-plugin-react-hooks` for the board and `lint-plugin.js`, because each JS rule costs a full AST transfer and the 56 rules of the old compatibility plugin were most of the lint time. Native Oxlint has no `no-octal` and no `no-dupe-args`; the parser and TypeScript reject both in modules, so only sloppy-mode CommonJS (`.dependency-cruiser.cjs`) is exposed. The `eslint` package is installed only because `eslint-plugin-react-hooks` lists it as a peer; nothing runs it. TypeScript rules run natively through Oxlint's tsrs backend. Native `no-unused-vars` explicitly reports values used only through `typeof` types, matching typescript-eslint rather than Oxlint's default. `lint.js` checks the whole project when it has no arguments: every tracked `.js`, `.cjs`, `.mjs`, `.ts`, `.tsx`, `.mts`, and `.cts` file from `git ls-files`, minus the `ignorePatterns` in `.oxlintrc.json`, applied once at discovery with gitignore-style semantics for the supported forms (literal segments, `*` within a segment, a leading `**/`, a pattern without an inner slash matching at any depth, hidden descendants included); every other form, including a leading `#`, `!`, or `/`, `?`, `[`, `{`, a backslash, a trailing space, or `**` elsewhere, fails with `fleet/unsupported-ignore-pattern`. A tracked path that is not valid UTF-8, or that contains a line break, fails with `fleet/unsupported-path`; a line break is a deliberate limitation because tsrs lists files one per line with no NUL mode, so such a path cannot round-trip. Tracked paths reach Oxlint after `--`, so names that look like options are literal files. Every run gives Oxlint every tracked source candidate before any ignore filtering and fails if the files it selects differ in either direction from the wrapper's list. Git paths are decoded without altering a leading U+FEFF. Ignore files and git ignores cannot remove a tracked file, and a selected file named with `.min.`, `-min.`, or `_min.` fails the lint with `fleet/minified-name`, a deliberate restriction relative to the old gate: Oxlint 1.94 never lints such names, even when given explicitly or with `--no-ignore`, so accepting them would skip linting silently, and untracked private lane files are not linted. It parses those exact files with Oxc, then passes the same list to type-aware Oxlint with `--no-ignore`. An `oxlint-suppressions.json` baseline at the root or at any depth in a tracked path outside `ignorePatterns` fails the lint before Oxlint runs, and the CI `code` filter matches that name at every depth. The `ignorePatterns` directory exclusions apply to every descendant, including dot-named ones. Oxlint has no `noInlineConfig` equivalent, so this mandatory preflight rejects inline lint directives using the policy in `.oxlintrc.json`. The same preflight preserves project-service membership: tsrs lists the real files of the projects named in `settings.fleet.projects` of the config (also the list `typecheck.js` compiles), and every selected source file except JS and CJS (the selected types minus those two exemptions: TS, TSX, MTS, CTS, and MJS) must belong to their union. JS and CJS keep their original type-unaware exception; JSX was not selected by the old gate and does not gain a membership requirement. Paths are resolved through realpath on both sides. Paths after the command (`bun run lint -- <paths>`) narrow the selected files to those paths, for the pre-push hook. Each path must be a tracked file, or the lint fails with `fleet/unknown-path`. A path that the ignore patterns remove, or that has no source extension, is dropped, and a narrowed run that selects nothing passes. The refusals about suppression baselines still look at every tracked path, and every other step runs unchanged on the narrowed list. Selection, discovery, parsing, and subprocess errors fail closed. Nested configs are disabled. CI and `bun run check` both use this entrypoint.
- `githooks.js` and `.githooks/pre-push` are the pre-push hook. The `prepare` script runs `node githooks.js install` on every `bun install`. It sets `core.hooksPath` to `.githooks` in the repository's own git config, which every worktree of the repository shares, and a relative path resolves at each worktree's top. It does nothing outside a repository root. It leaves an existing `core.hooksPath` alone and says so, and that is what keeps a no-mistakes gate worktree safe: no-mistakes sets the hooks path of its worktrees in per-worktree config, so a write to the shared config could not reach them, and the install does not write one anyway. On `git push` the hook takes each pushed branch that is the checked-out `HEAD`, and lists its changed files against the merge base with `refs/remotes/<remote>/HEAD`, `origin/HEAD`, `origin/main`, or `origin/master`. It excludes committed deletions. With no such base, or with more than 400 changed files, it runs `bun run format:check` and `bun run lint` for the whole project; otherwise it runs `bun run format:files -- <files>` and `bun run lint -- <files>` for the changed files, skipping the checks if that list is empty. It runs format, lint, and `bun run typecheck` in parallel and prints the output of those that fail. Typecheck is a whole-program check, so it takes no files. The hook calls only package scripts, so a tool swap changes the scripts and not the hook. The scoped `format:files` script runs `format-files.js`, which requires each input to remain a regular file with no symlinks in its path before handing it to the formatter. Ignored or unsupported files still have to pass that path check, but do not have to be formatted. A branch that is not checked out, a missing `node_modules`, or a missing `node` or `bun` skips the checks with a message, because the hook cannot check what it cannot run, and it must not block a push for that. `git push --no-verify` skips the hook on purpose. The hook is the fast first line and CI stays the full gate: a change to a lint rule or its config is checked against the changed files only, and knip, dependency-cruiser, the migration check, and the end-to-end tests run in CI. `e2e/extension/pre-push-hook.test.ts` pushes from a scratch repository and checks that a broken file is refused and a clean one goes through. It also covers a missing working-tree file and symlinks replacing a committed file or a parent directory.
- `fleet/no-comments` is an Oxlint JS plugin in `lint-plugin.js`. It allows one comment that the toolchain reads: a triple-slash `<reference lib="..." />` directive, which `e2e/board/board.test.ts` needs for the DOM types of the code it runs in the browser. The preflight prevents a native disable directive from suppressing this rule or itself.
- `bun run typecheck` runs `typecheck.js`, which runs standalone tsrs in order against each project in the `projects` list of `.oxlintrc.json` (the root and board TypeScript projects), read by `projects.js` for both `typecheck.js` and lint membership, with their existing options and a failure on the first non-zero exit. Each project is a directory whose compiler config is `<dir>/tsconfig.json`. The CI `code` filter covers source files and compiler configs through `**/*.{js,cjs,mjs,ts,tsx,mts,cts}` and `**/tsconfig*.json`. That is a deliberate limit: a project config or an inherited (`extends`) config not named `tsconfig*.json` is not tracked by the filter, so the project list and its configs must use `tsconfig*.json` names. Oxlint's `--type-check` covers only lint-selected files and omits program-wide global diagnostics, so it cannot replace whole-program checking. TypeScript remains installed for dependency-cruiser's TypeScript analysis, not as a second compiler gate.
- `fleet/no-kill-by-name` in `lint-plugin.js`, enabled for `e2e/**` in `.oxlintrc.json`, fails any string in `e2e/**` that names `pkill` or `killall`. A test that ran `pkill herdr` once took down the live herdr server of its host, with every lane on it. A test stops only what it started: its own lab session by `--session` name, or its own process by pid or process group. `kill-guard.test.ts` and `no-browser.test.ts` are exempt in the config, because they check that Pi refuses those commands.
- `.dependency-cruiser.cjs` holds the module boundaries. `cardd`, the extension, and the board share only the wire protocol. End-to-end tests drive real processes, so they import only the protocol.
- `ci.yml` puts each pull request's runs in one concurrency group, so a new push cancels the run it supersedes. Each push to `main` gets a group of its own, keyed by its run id. With one group for `main`, a merge cancelled the run of the merge before it, both in progress and while it waited, so that commit never got a full result.
- The end-to-end jobs install their tools through `.github/actions/install-direnv` and `.github/actions/install-chromium`, and no job calls `apt-get` for a package that a release download or the runner image already supplies. On 2026-11-11 the authoritative name servers of `ubuntu.com` stopped answering the Azure resolver that GitHub runners use, so `azure.archive.ubuntu.com`, `archive.ubuntu.com`, and `security.ubuntu.com` did not resolve for more than an hour. Only the jobs that used apt failed: `direnv` came from apt, and `playwright install --with-deps` ran `apt-get update` and then installed the fonts that the image lacks. `install-direnv` downloads the release binary and checks it against a pinned checksum. `install-chromium` caches the browser under `~/.cache/ms-playwright`, asks Playwright which system packages are missing (`install-deps --dry-run`), and calls apt only for those. It does not run `apt-get update` first, because the image's package lists are enough. When the first archive host in `/etc/apt/apt-mirrors.txt` does not resolve, it points apt at mirrors outside `ubuntu.com`. Those mirrors serve the same signed packages. Apt retries with backoff. Each retry refreshes the package lists and asks Playwright again which packages are missing, so the install and the final proof use the same lists. A failed install names the packages and says whether the archive resolves. A final dry run proves that Chromium has every package. The fonts stay, because the board tests measure text layout. The `board-e2e` and `extension-e2e` filters include `ci.yml` and the actions, so a change to how those jobs install their tools runs those jobs. The `cardd-e2e` and `extension-e2e` filters also include `e2e/run.ts` and `e2e/durations.json`, and `cardd-e2e` includes `ci.yml` and the install actions, so a change to how the runner splits or runs the shards runs every shard that it changes.
- `packages/cardd/scripts/check-migrations.ts` applies every migration to an empty database, checks the result, and compares it with the committed `schema.sql`. With `MIGRATIONS_BASE` set to a git ref, it also fails when a migration that exists at that ref was changed, renamed, or removed. `--write` updates `schema.sql`.

## End-to-end deadlines

`bun run test:e2e` runs tests through `e2e/run.ts`, which starts one `node --test` process for each test file and runs one file per 16 available cores by default, capped at eight and with a minimum of one. Set `FLEET_E2E_CONCURRENCY` to an integer from one through that default to run fewer. The runner starts the longest files first, by the seconds in `e2e/durations.json`. A file missing from that map counts as the median. `--shard=N/M` runs the Nth of M groups of the matching files. It fills the groups longest file first into the group with the least total seconds, so every runner computes the same groups. Each file argument may be a glob. Leave headroom because each file starts its own programs and several suites can run together. `node e2e/run.ts <file>...` runs only the files it names, in the same way. Each test has five minutes, and each file has twenty, because Node's test timeout does not stop a file that finished its tests but still has open handles. The whole runner has two hours, including teardown. Each file's output goes to its own log. A passing file prints one line with its time. A failing file prints its whole log, its exit code or signal, and any registered group left running. Suite totals are marked partial when a launched file does not provide a complete Node test footer.

Each file runs in its own process group. The runner and fixtures record groups they start in private per-file directories. Every detached child that test code starts, including job commands, relaunch helpers, replacement Herdr servers, reapers, and nested runners, goes through a test-only launcher (`e2e/support/owned-launch.ts`) that registers its group before executing the command. Once cleanup closes a registry, a late launcher fails before its command runs. Nested runners also register with their ancestors. Cleanup closes registration before inspecting records, and checks the PID, group, and start time before signaling. It does not inspect process environments or arguments. After a five-second grace, it kills verified groups that are still running. If a registered group remains but cannot be verified, the run fails and the runner keeps its directory. A direct child wait is bounded even if its group identity cannot be verified. Teardown cannot discover processes that detach without registering. SIGINT, SIGTERM, and SIGHUP stop the queue and are forwarded to every running group, and a group that is still alive five seconds later is killed. The deadlines kill only groups that the runner started. If infrastructure fails, the runner stops the queue, kills active groups, and waits for their lanes before sweeping the suite. SIGKILL of the suite runner can leave workers and their suite folder behind. Later runs leave that folder alone because the runner's death does not prove its workers are gone. A direct `node --test` run has a reaper that outlives it: after the runner dies, the reaper runs the lab hooks, sweeps the registered groups, and deletes the run root only after teardown is proved. Otherwise it keeps the root. Reports count a group as removed only when a verified signal reached it and it is gone afterward. A file that fails with "Interrupted while running" and "Promise resolution is still pending but the event loop has already resolved" was not hung: that is Node's report of a SIGINT or SIGTERM that reached the test runner, and the runner's line for the file names the signal. CI runs the cardd and extension suites through the runner too, in 3 and 9 shards, and each of those jobs sets `FLEET_E2E_CONCURRENCY` to 1. About thirty `p620-ci` runners share that host's 128 cores, so the default width would start eight files in every job, and the hosted fallback runners have four cores. Two or three files at once on hosted four-core runners finished sooner, but timing-sensitive tests such as `stale-import-incident.test.ts` and `calm.test.ts` then failed in about one shard in twelve (7 of 86), and not once in 39 shards that ran one file at a time. CI also bounds each end-to-end job to thirty minutes, including installation and build.

Every board test file calls `boundBoardFile` from `e2e/support/board.ts`, which ends the file after ten minutes even if its tests finished with open handles. Board fixtures register cleanup through `startBoardServer` and `openBoardPage` as each resource is acquired. A seed failure before the page exists must still stop its server. The kanban and links fixtures use normal timers: they do not assert timed-check behavior, and an accelerated timed check competes with fixture database writes.

## Long-command status

`run_long` uses `bash -o pipefail -c`, without `errexit`. A pipeline fails with its rightmost nonzero stage, so a passing `tail` or `tee` cannot hide a failed suite. Bash must be installed. The wrapper prints a warning before execution and the tool describes the policy before submission. The wrapper does not parse shell syntax. `cardd` separately checks [Lavish review polls](#review-pages) at job admission.

A command list still returns its last command's status. `false; true` succeeds, and `pipefail` does not change that. Use `suite && formatter` to run formatting only after success. To always format while retaining suite status, use `suite; code=$?; formatter; exit "$code"`. Intentional recovery such as `suite || recover`, `if suite; then ...; else ...; fi`, and explicit nested shells keep their normal shell meaning. A nested `sh -c 'suite | tail'` must set its own failure policy. An exit 0 means the supplied command succeeded under these rules, not that every subprocess succeeded.

The wrapper preserves the child status as its own process exit code after durable result delivery and cleanup. Child signals use `128 + signal number`. Wrapper cancellation reports 130 and command deadline expiry reports 124. Spawn errors report 127. Result retries, heartbeats, output tails, and worker wakeups retain their existing ownership. A bounded wait ending in a still-running pipeline is not a completed command failure.

## Protocol

`packages/protocol` is the wire protocol between `cardd`, the extension, and the board. Each schema is the one source of its type and its validator. `parse` throws one readable error that names the first problem.

## cardd

### Command line

```
cardd serve --db <file> [--listen <host:port>] [--board <built board folder>] [--hostname <name>]... [--hosts <json>] [--public-host <host> --access-team <team domain> --access-aud <tag> --access-email <email>]
cardd lane add <name> --db <file> --home <path> [--parent <lane>]
cardd lane list --db <file>
cardd lane home <name> <path> --db <file>
cardd lane remove <name> --db <file>
cardd lane plan <name> --db <file> [--plan <json>]
cardd project list --db <file>
cardd project add <name> --db <file> --delivery <mode> [--clone <host>=<path>]... [--yolo] [--repo <owner/name>] [--hosts <json>]
cardd project clone <name> <host>=<path> --db <file>
cardd project unclone <name> <host> --db <file>
cardd project remove <name> --db <file>
cardd project yolo <name> on|off --db <file>
cardd project delivery <name> <mode> --db <file>
cardd card delivery <number> <mode> --db <file>
```

`serve --hosts` takes JSON, and [setup.md](setup.md) owns its form. The four `--public-host` and `--access-*` flags turn on the public board link, and [setup.md](setup.md) owns that too (A public link through Cloudflare Access). They are set together or `serve` refuses to start. [Lanes and projects in setup.md](setup.md#3-lanes-and-projects) owns repository discovery, the `--repo` bypass, transport selection, registration output, and startup backfill. `lane add` and `project add` refuse a name that exists, with a message that names `lane list` or `project list`, so the database's constraint never shows.

`registry.ts` holds the commands that read and change the registry beyond `add`. `lane list` and `project list` print one plain line for each row. `lane home` sets a lane's informational home and refuses a relative path. `lane remove` deletes a lane that never worked: its row, its mate's session, deliveries, maintenance records and their batch memberships (through `dropMaintenance`, which counts the removed requests in the reload batch summary when the removal settles the last open one), its lane card, and its schedules, in one transaction. It refuses a lane that is a parent, whose mate is not `exited`, that has an open card, or that has entries or incidents, because entries are append-only and a card with entries cannot be deleted. Removing a lane that ever worked a card would need its cards to outlive it, as `cards.historical_project` does for a project, which is a schema change that nobody has asked for.

Every command except `serve` opens the database with `openDatabase(path, false)`, which refuses when the database has a schema (`user_version` above 0) older than the checkout's last migration, and names both numbers. Opening applies pending migrations, so a CLI run from a checkout newer than the running `cardd` would migrate the live database under it. `--migrate` lifts the refusal. `serve` always migrates, which is the supported way (section 7 of [setup.md](setup.md)).

`project clone` sets one host's clone of a registered project to a new path, so a clone can move. Attempts already begun keep their worktrees where they are: close finds them through the clone's worktree list, not through a stored path.

`project remove` refuses open cards, then moves the closed cards' project names into `cards.historical_project` and clears their registry references before deleting the project. Card reads coalesce the current and historical names, so their public history stays unchanged and foreign keys stay valid. Clone registration lives in the project row, so deleting it removes every refresh and dispatch target without touching files.

`ops` is a card-only delivery mode for an approved operation, not a project default. `dispatch(..., delivery="ops")` or `cardd card delivery <number> ops` records it on a ship card without changing product delivery, and project add and `project delivery` refuse it. A card that carries a PR cannot change to ops. The worker starts from the clone's local base branch, so dispatch never fetches origin and works offline. It makes no task branch, PR, commit, push, or merge. It verifies the operation and writes a report in `$FLEET_SCRATCH`, then hands it back with `report(status="done", text, evidence=<absolute path>)`. Only the done report of an ops card carries `evidence`. Cardd refuses it on any other card or status, refuses a done report without it, refuses an evidence path that fails `inEvidenceScope` in the protocol, and refuses any PR or merge claim. That check is shape only: the path must be absolute, contain a `scratch/c-<N>/<file>` segment with no empty, `.` or `..` part, and not start under `tmp`. It does not prove that the file exists, that it lies in the host's scratch folder for the card, or that it is not a lookalike, and nothing in this release reads or opens it. The evidence reference is a reported, unverified path. Close does not verify the file either: it ends the card on the done report that carries the path. The effective handoff of an ops card (`operationHandoff` in the protocol) is the latest handoff-status report, if it is `done` and no steer to the worker came after it. `board(card=N)` tells the mate only that evidence was reported and not verified and offers no read of it. The web thread (`GET /api/card/N`) carries no `evidence` field and no evidence path: cardd removes the field and replaces every reported evidence path in a report body or board summary, including a path that an earlier report named before the structured handoff. The card returns to the mate even on a yolo project, and yolo never lands an ops card.

An ops card closes through the same two operations as any ship card, with one rule of its own in `closing.ts`. `notLanded` has no PR or branch to check for an ops card. Instead it asks for the worker's standing handoff: `operationHandoff` in the protocol must return a done report whose `evidence` is a string, which means no steer to the worker came after it. Without it, `close.begin` and `close.finish` refuse a Done close with "its worker has not handed over an evidence report" (or "the worker has not reported done" when the latest handoff is something else), before the extension stops a worker, archives, or removes anything. `landed=false` still ends the card as Dropped without that report, as for any card. `confirm=true` keeps its meaning: the host's check for commits off the base branch and uncommitted files in the worktree still runs, because the plan asks to verify, and `confirm=true` archives what it lists before the card ends Done. An ops worker changes no project file, so that warning is a sign that something went wrong. An ops card lands nothing, so the close neither fast-forwards a branch nor refreshes the project's clones, which also keeps a close offline like the dispatch. The close is the same one the mate's `close` tool runs: it stops the worker's processes, archives unlanded work, removes the worktree and branch, and leaves scratch in place, so the evidence report stays on the host. A Done ops card has no open reminder: the finished-card reminder tells the mate to `close` it, and closing ends the card, so nothing is left to remind. The automatic close after a merged report still cannot reach an ops card, because an ops report that claims a PR or a merge is refused. A restart or a lane stop replaces or stops a worker process and never archives, removes a worktree or ref, or moves scratch.

`project delivery` sets the delivery mode that new ship cards of a project take: `no-mistakes`, `direct-PR`, or `local-only`. It changes no card: a card records its mode when it is created, and that record is what dispatch tells the worker. `card delivery` changes the recorded mode of one open ship card. It refuses a card that is closed, is not a ship card, or has a live worker, because that worker was told its mode in its task and a changed record would let it go on with a stale one. To change the mode of a card with a live worker, a mate dispatches again with `delivery=<mode>` and `replace=true`, which starts the worker over with the new mode. Setting the mode a card already has changes nothing. Each change is a note on the card.

`lane add` prints the mate's token. The first lane, added with no `--parent`, is the root. `one_root_lane` allows no second root, and `mainLane()` is the only reader of that row. A second mate is added with `--parent`. `CARDD_TIMING_SCALE=0.01` speeds up every timer, for tests. `CARDD_CHECK_EVERY_MS=<n>` sets only how often the timed check runs, in milliseconds, and leaves every other time at its scale. `CARDD_CLOCK_FILE=<file>` makes the timed checks, such as the scheduled wakes and a lane stop's end, read their time from that file, an ISO 8601 time, instead of the clock, so a test moves time by writing the file. Entries keep real time. `project yolo` sets the captain's standing merge authority for a project. The captain can set it through this command line or tell main to set or clear it with `project_yolo(project, on)`. The tool is offered only to main. The `project.yolo` operation validates its arguments, refuses workers and second mates, and reuses the registry's `setYolo`. Main never changes it on its own initiative or on a second mate's request. Destructive, irreversible, or security-sensitive merges still need the captain's words with yolo on.

### Storage

- `store.ts` reads and writes `cards.db`. A mate's session ID is its lane name. Rows leave the database as JSON that SQLite builds, and are checked against the protocol schemas, so the types match the wire. A card from before names existed is known by its number.
- A session's token is the HMAC of its role and ID under the database's key. The same session always gets the same token, and no mate can share a token with a worker.
- `db.ts` applies every new migration in one transaction, so a failed migration leaves the database as it was. Foreign keys are off while migrations run, as SQLite's procedure for rebuilding a table requires: dropping a parent table counts each child row as a violation that its replacement never clears. Instead, every key is checked after each migration, and a violation names its rows. Every foreign key in the schema is one column.
- Each entry that the card's status reads raises the card's revision, and so does any change to the card's row, such as `last_activity` when a session starts or ends a turn. The revision is for readers that cache a card's thread (the board's facts). An action never compares it: a board action names the hold entry the captain saw, so unrelated entries and card updates cannot refuse it.
- The cards table stores no status, phase, or time of change. `store.ts` replays a card's entries through `status.ts` each time it reads the card.

### Status and holds

- `status.ts` is pure. A card's status is one function of its communication entries: the worker's reports, holds, the captain's answers, comments, and the close. Mostly the last report decides. An open hold wins. Nothing else feeds it: not GitHub, not the timed check's findings, not job results, not commands. No operation sets a status, and none is stored.
- A hold that waits on the captain makes the card Needs you. A hold that waits on a mate makes it With mate. A hold with a future date is Waiting until then. A closed card has no hold.
- A `paused` report shows the card as Paused until its date. A `blocked`, `failed`, or `stopped` report shows the card as With mate with red attention, except a `stopped` that follows `done` or `merged`, which is never written (see Closing). Any later report, steer, or answer replaces both. Pause, finish, and idle-watch are decided once in `status.ts`, not read from the latest report row: `pausedNow`, `isFinished`, and `idleNow`. The timed check and incident recovery read those. A steer that resumes the worker clears the pause, so the idle watch starts then, not when the old pause date passes. `pausedNow` does not depend on the status: a pause while Merging leaves the card Merging on the board, and recovery still sees the pause. `isFinished` is the worker's done or merged handoff, until a steer or a later handoff report takes it back. `finishedOpen` is the wider fact for the close reminder and the bundle: a merge report still counts after either, because a merge is not taken back.
- A card shows one state, and `standingFrom` in `status.ts` is the only place that decides it: `status`, `attention`, and `until`. `until` is the date a Paused or Waiting card's wait ends, the report's or the hold's, and null when the card has no date, as a standing card that is Waiting has none. Attention shows only while the card has no open hold, so a hold with a future date reads Waiting with its date whatever the worker last reported, and when the date passes the card reads by its holder as above, with no attention. The board, the `board` tool, and the worker's own `standing` op read that state and never decide one of their own.
- A captain's approval of the merge question, or yolo on a ship card's `done`, makes the card Merging. The worker's next `done` leaves it Merging. See [Closing](#closing) for how the card reaches Done or Dropped.
- `change.ts` holds the guards of spec section 7.4: a Done or Dropped card refuses reports, holds, and steers, and a lane card refuses all of them. `statusWith` reads the status a report will give, with the entries a caller writes next counted.
- `waits.ts`: a dated hold says what it waits on and what work remains. `hold` with `until` refuses a call that does not give exactly one of `job`, `schedule`, `worker` (a card whose worker is live: its attempt runs and its Pi is connected), `watcher` (free text that fleet cannot check), `outside` (an outside date or event), or `said` (the captain's words for later, checked like a merge approval's: `source` is `chat` when the extension found them in the session file, otherwise `record`, which `cardd` looks for in the captain's entries). A mate may name only a job, schedule, or worker of its own lane (main may name any lane). One of another lane is refused with the words for one that does not exist, so the refusal gives away no label, time, or liveness. The same check runs each time the hold is read, against the lane that wrote it (`Hold.author`), because a schedule id is given out again once its schedule is removed: a hold whose id now belongs to another lane's schedule reads as gone, in the words for a schedule that was removed. It also refuses a call without `remaining`: an array of card numbers, `[]` for none, each an open card of the mate's reach other than the held card. The statement is stored in the hold entry's `wait` and `remaining` fields, so no migration is needed. `status.ts` reads them with `parseWait` and `parseCards`, which treat anything else as no statement. `datedWait` turns a hold that is Waiting into a `DatedWait` for the board and the reminder: `watch` is `running` (a job that runs, a schedule that exists, or a worker that is live), `unchecked`, `outside`, `later`, `gone` (the job, schedule, or worker is gone, or the worker's Pi is not connected: it never connected, exited, or was lost), or `none` (no statement: every dated hold from before this existed). `gone` and `none` are an idle park (`idlePark`). A `watcher` text is never idle, because fleet cannot see it. `since` is when the hold opened, so dating it again keeps its age. The `board` and `card` tools show a dated wait on a job, schedule, or worker of another lane, and a remaining step that is a card of another lane, to a reader that cannot reach it (not main, not that lane) as the kind and the state only (`a job in another lane (running)`, `c-N (another lane)`), and a list for a mate follows the same rule. The hold entry shows only the kind in its `wait` field in the same case, in the `card` tool and in the push to its mate. The `card` tool also leaves out a decision list that was sent to another lane's mate, for a reader that is not main, because main's list names objects of every lane and is kept on the oldest card in it. The web board stays whole. A Later preset on the board counts as the captain's later, with its date phrase as `said` (see the board's Later action in [Pane](#pane)).
- `holds.ts`: a card has at most one hold, with every question of its gate bundled in it. The card's own mate owns it. It waits on the mate, then main, then the captain, and climbs one level at a time. Only main marks a hold as the captain's. Main's own cards skip main. Holding the same hold again writes nothing. A hold after a release is the next occurrence of the same hold. A dated hold on a fleet-checked worker, job, or schedule (`waits.ts`) is announced only to the card's own lane, without escalation or automatic echo: `dating` has already refused a checked wait that reads as gone. An explicit `replyTo` still answers the request with an informational comment, not a hold notification. Free-text watchers, outside events, and the captain's later keep their existing routing. It keeps its holder, so the date's end (`hold ended`) and an idle park reach that mate as before, and the information list names it meanwhile. The same holds when it is dated again, and a rewrite without a date is announced as a decision.
- Only the captain's exact words release what waits on the captain. Merge approval is such a release.
- A merge question is a hold, and its question and options belong to whoever wrote them. The fleet writes it with `MERGE_OPTIONS` from `@fleet/protocol`, and only `Approve & merge` in `approves`. A mate may rewrite it, and then the hold names which of its own options approve the merge (`approves`, each one of `options`). A rewrite of the options must say `approves` (`[]` for none), so a mate cannot forget it. Nothing rewrites a mate's question or options into a fixed template. `status.ts` derives `originalMerge` from a fleet-authored merge hold and preserves it across rewrites within that open hold only while options and approval meanings remain identical. Deferral or escalation alone therefore does not change its presentation. [pane.md](pane.md) owns the board controls, including the written-answer action for legacy single-option fleet holds.
- Merge authority has one source: the captain picks an option in `approves`. `answerHold` then writes an `answer` with `approved: true`, and `status.ts` makes the card Merging. Any other pick on a merge question, or his own words, is never refused and never approves: `cardd` writes a captain comment (`answers` names the hold, with `choice` or `written`), the hold stays open and goes back to the mate through the comment machinery, and the mate gets `(answer, still open)`. The mate records the decision with `release(words, choice)`: the words are checked against the captain's entries, `choice` must be an option of the hold, and `approved` is true only when `choice` is in `approves`. A note never clears a merge question.
- Main cannot note-clear a second mate's hold marked `unlanded`. Keeping, landing, or discarding finished work that has not landed is the captain's call. `hold` sets the mark at write or rewrite time: the mate passes `unlanded=true`, the open hold already carries it, or `holdsUnlandedWork` finds a finished ship card with a PR or local landing, no merged report, and no empty branch. The mark is sticky across rewrites, including board deferral. `status.ts` reads it from the hold entry; worker holds start unmarked. Only `release` uses the mark to refuse main's note, naming the two ways out: `hold(to="captain")`, or the captain's exact words. An unmarked operational hold stays main's to clear when it is main's to decide, even if its worker later finishes. A hold that becomes a disposition question is marked only when its mate rewrites it. Holds already open when this ships are unmarked until their mate rewrites them.
- `approval.ts` in `@fleet/protocol` is the one place that reads the old record: a merge hold with no `approves` field approves `Approve & merge` only when that is one of its options, and an `answer` with no `approved` field approves when its choice is `Approve & merge`. `approvesOf` keeps only names that are options of the hold, so `approves` is always a subset of `options` and nothing outside the options can approve or be chosen. Entries are append-only, so those shapes stay readable. A hold already open when this shipped, with nobody having rewritten it, still approves with `Approve & merge`, and `Request changes` never approves. The board's presentation follows [pane.md](pane.md); a non-approving choice submitted through the API comes to the mate with the hold open. A merge hold that a mate rewrote without `Approve & merge` among its options names no approving option, so a pick comes to the mate, who holds it again with `approves`.
- `laidOut` in `@fleet/protocol` is the only text layout of a question. The board uses it. It breaks a line only where the structure is certain: a numbered list `1.` to `N.` inline after a sentence end, and a trailing path (starting `/`, `~/`, or `./`) or URL. Text that already has lines is left as written.
- A steer withdraws the merge question while the PR is reworked, because approving a PR that is about to change would approve the wrong head. The worker's next `done` asks again, as the same hold.
- The captain's comment takes the hold back from him. A comment written on the board goes to main only, never to a second mate or a worker, and it carries the card's lane when the card is not in main's lane. Main relays it as it sees fit. A hold that went back to a second mate's lane waits there until main does.

### Talking

- `comments.ts`: a comment is the one way to talk to an agent. A worker's card hears its mate. A second mate's lane card, or any card in its lane, hears main when main speaks, and main hears the second mate when it answers. Main never steers another lane's worker. A comment cannot answer a worker's decision that waits on the captain.
- `board.ts`: `/api/board` and `/api/card/N` give the board its data. Each card carries `activity`: the state of the session that works on it (a worker's, or a mate's for a lane card) and when cardd last heard from it. A change of that state reaches the board over the live socket. `cardd` sends `changed` to board tabs at most once per second, except right after a board action. `/api/board` is rebuilt only when the database changed or the last build is over a second old. A card that is Waiting on a dated hold carries `datedWait` (`waits.ts`), which the board shows as a line on the card and a Waiting row in its detail, marked when it is an idle park. An open work card also carries `pulse` (see Neglect, below).
- The board's thread (`thread.ts`) gives each entry a direction from its author, its `for` and `holder` fields, and the card's lane. Rows between two mates are quiet log rows unless they carry a finding, a failed state, or a blocked, failed, stopped, or needs-decision report. A board answer that main recorded again with the captain's words is not shown twice, and a quote of the captain's earlier words in another entry folds to a marker. A `replyTo="r-N"` entry shows a link to its question. Replies to a captain comment nest under it and keep their sender and recipient labels. `Thread.tsx` owns presentation and preserves reply targets when folding technical history. See [README.md](../README.md) for the default card view. `e2e/board/thread.test.ts` covers folding, reply navigation, and waiting labels; it seeds maintenance entries directly in its test database.
- `ops.ts`: a report reaches the mate when its status hands off, or when it is the first report after a comment that reached the worker (spec section 10.3). Each operation runs in one transaction. A `paused` report with no `until`, or one that is not in the future, is refused with a message that tells the worker to report `blocked`. One more than 24 hours away is refused too, and the worker is told to ask its mate for a dated hold. `paused` is a wait on a time or an outside event. A wait on the mate's action is `blocked`, which reaches the mate and stays on its decision list. A paused report reaches the mate when no job of the worker's attempt is running (an unwatched pause), and stays routine, so it is batched and a pause behind a running job stays quiet. The first one after a comment, and one with a `replyTo`, reach the mate as for any report. The result of an unwatched pause carries an `advice` line for the worker: nothing runs for this pause, so start a `run_long` watcher for a task that finishes on its own. The extension fills in no default date, so a worker cannot pause without choosing one.
- `replies.ts`: a mate can ask for a reply to one comment, on its worker's card or, as main, on a card in a second mate's lane. The comment entry is the record: it carries `owes`, the recipient, and the reply's id is `r-<entry id>`, so the record exists in the same transaction as the comment, before any push. The open replies are derived from the card's entries, like its hold. Only an entry from the recipient that names the id in `replyTo` answers it: a worker's report, or the second mate's comment or hold, which goes to the asker. Only the asker withdraws it. The timed check resends it after two minutes, then every five minutes while its recipient is up, until it is answered or withdrawn. A dated hold pauses the reminders. The captain's board comment opens one too: it carries `owes`, the lane of main for the card, and the answer is main's comment or hold with that `replyTo`, which notifies no one and is marked `for: captain`. It uses the same repeating reply reminders to main. Replies on a closed card are not nudged and not shown.
- `plans.ts`, `schedule.ts`, and `wakes.ts` are a mate's scheduled wakes (spec section 19 describes run cards for a standing card: this is the lighter form that wakes the mate and starts nothing). The plan is on the lane card in two columns: `plan_next` is what the captain set, and `plan` is what the mate loaded at its start, with the time it took effect. The `lane.plan` op, which the extension calls once when it starts, moves the next plan into the active one and returns it, so activation is the mate's own restart and the call is safe to repeat. Only the active plan fires.
- `schedule.ts` is pure. Time is compared as local wall-clock minutes (`YYYY-MM-DDTHH:MM`) in the plan's zone, never as instants, so a time that DST skips fires when the clock reaches it and a time that DST repeats compares true twice. For each wake it finds the latest slot at or before now, looking back at most a week. The slot is due when it is not before the minute the plan took effect. A wake is never made up for more than its latest slot.
- `wakes.ts` writes the wake in the timed check. A slot's key is its minute and its purpose, and the wake entry carries the keys it covers in `fields.slots`, so what is issued is read from the card's own entries: a restart of `cardd` finds it, with no second table. Slots due together are one wake. The wake is a comment by `schedule` with `owes` the lane, `for: mate`, and `from` the lane's parent, so reply tracking in `replies.ts` treats it like main's `reply=true` comment, with two differences: main can withdraw the reply, but the mate's answer notifies no one; its text is the whole wake line. Open replies never suppress later scheduled wakes. A script wake (`wake` op) is a plain comment by `script` that owes nothing.
- `echo.ts`: when a parent commented on a card and the mate has not acted on it since, the mate's next action also reaches the parent. It is sent once, because the next action ends the wait.
- `authority.ts`: the mate's extension checks chat words against its own session file. For any other source, the words must be in a captain entry: a board comment, an option click, or an earlier answer. A project's yolo flag lets its mate have the worker merge a green PR without asking. A done PR in such a project goes straight to Merging.

### Attempts, delivery, and the server

- Delivery modes: a ship card records its mode in `cards.delivery`. `card.new` takes the project's registered mode, and maps `no-mistakes-prod-only` to `no-mistakes`, its most rigorous leg, as Firstmate's `fm-project-mode.sh` does for mechanical callers. `attempt.begin` records an override that the mate passes, and writes the card's mode into the task message as its `Delivery:` line, so the worker reads the mode from the card. A task that names another mode is refused. A worker that already runs keeps its mode: a new mode needs a new attempt. `cardd project delivery` changes the default for later cards only, and `cardd card delivery` changes one card that has no live worker (see Command line).
- A local-only card has no PR. Its worker starts from the clone's local base branch, without a fetch, because local-only work lands there and never on origin. Its `done` carries where its branch lands instead of a PR lookup, and raises the same merge question about the branch. A branch with no commit off the local base branch and no uncommitted file in its worktree is an operation, such as an ad change: its `done` raises no merge question, withdraws a merge hold already open, and the mate closes it directly. The comparison is against the local base only, so a branch fast-forwarded to `origin/<base>` still counts as having commits (`empty-branch.ts`). The timed check and close never look up a PR for it.
- `attempts.ts`: an attempt is one run of a card by one worker. Its ID is the retry key for dispatch. A dispatch retry on the same host finds the same attempt, with the same token and no second task message. A new attempt gets its task message in the same transaction, so a retry can neither lose it nor repeat it.
- A worker names its own branch, as Firstmate's workers do (`fm-task-branch.sh`). A new attempt's worktree starts on a placeholder branch named for the attempt, such as `c-83-a1`, with `attempts.branch_named` at 0. The worker's first action is the `branch(name)` tool: the name is `<type>/<slug>` (`branchNameProblem` in `@fleet/protocol` owns the rule), the extension refuses a name taken in the clone or on origin and renames the branch it is on, and the `branch.name` op records it in `attempts.branch`, refusing a name that is another live attempt's in the same project. If the record is refused, the rename is undone. A branch is named once: naming the same name again confirms it, and another name is refused. Every consumer that needs a card's branch (close's landed check, the archive, the local-only fast-forward, a resumed dispatch, and `board(card=N)`) reads `attempts.branch`, so none of them guesses a name. Attempts made before this, including those on `fm/c-N` branches, have `branch_named` at 1 and keep the branch they have. A scout makes no branch, so it never names one.
- `deliveries.ts`: at a connect, every delivery that is queued, in flight, or taken in but missing from the session file is pushed. While the session stays up, only a queued delivery is pushed. A delivery already in the session file but not taken in waits for the chase. Each push carries its card's short name, which the message shows after the card number. No entry quotes the comment it answers, so when a second mate steers its worker right after main's comment, the worker gets the steer alone, never main's words to its mate.
- A comment from a mate or the captain is a Pi steer unless the sender set `later=true`; other entries stay follow-ups. A `now` argument from an older caller is ignored, since steer is the default. A worker report other than `working` or `note` is refused while a comment to it is unread, and the error names the comment. A comment is unread while its delivery is `pending`, `pushed`, `resent`, or `pushed-again`: no finished model response of the worker has held it. A comment that a hello listed as in the session file is not unread, because the file holds it. Whether a settled run took it in is a separate fact, and the gate does not ask it. A comment that was queued while the worker was down, or lost before the file existed, is not in the file, so it stays unread until it is sent and a finished model response holds it. The gate never waits for the run to settle, so a worker that read a comment can hand off in the same run. A resend makes the comment unread again.
- A delivery has one state: `pending`, `pushed`, `resent`, `pushed-again`, `read`, `filed`, `acknowledged`, or `confirmed`. `pending` waits for its first push. `pushed` has been sent and no finished model response has held it. `resent` waits to be pushed again. `pushed-again` has been sent again and no finished model response has held it. `read` was held by a finished model response and is not taken in. `filed` is in the session file and not taken in. `acknowledged` was taken in by a settled run and is not yet in the file. `confirmed` was taken in and is in the file. The extension's `read` moves `pushed` and `pushed-again` to `read` and changes no other state. A hello that lists the entry confirms an `acknowledged` one and files any other, and it never takes one in, so a queued entry that the file lacks stays `pending` and is pushed. A `read` entry that the file lacks is sent again at the connect and stays `read`. Only the extension's `ack` takes it in, when that run settles with no abort and no error. Neither Pi adding the message nor a finished tool-use response takes it in: a run aborted or failed after such a response leaves the entry `read`, and the chase resends it. A message can sit in the session file and still not be taken in, when the captain aborts the turn or the provider fails, and Pi drops a queued follow-up on Escape. A `cardd` that is older than the extension only records the acknowledgement later, and drops the connection at a `read` it does not know until the update brings it onto the same commit. The chase never resends or reports a session whose run is still going: a queued follow-up or steer waits for the next model call, so a worker in one long turn has not taken it in yet, and its fate is known only at settle. A hung run is the stall check's business. The idle-worker check ignores a worker with an entry in flight (`pending`, `pushed`, `resent`, `pushed-again`, or `read`) and does not ignore a `filed` one.
- The extension holds every pushed entry until Pi has loaded all extensions (its `resources_discover` event). A push that arrives earlier would start the model's first request before other extensions, such as pi-fff, have registered their tools, and the tool list would change between requests and break the prompt cache prefix. `e2e/extension/prefix-stable-tools.test.ts` covers it.
- The chase resends every two minutes a delivery that is `pushed`, `pushed-again`, `read`, or `filed`, so one that is not taken in, while the receiver is up. Each resend uses the same entry, marked `again`, including entries already in the session file. Main hears after three resends, then every 15 minutes. Main's own entries keep resending without a self-escalation. The extension deduplicates repeated delivery within a turn, not forever. This tracks intake, independently of reply obligations.
- `server.ts`: one websocket per session, plus `POST /call` with a bearer token for scripts. The first message must be hello with the token. Every later message checks that the session is still live, so an ended or replaced attempt loses access at once. A hello from a known session whose attempt ended is refused with 4001, and `cardd` logs why once for that session until it restarts. At start no session is connected: live sessions reconnect and become idle, or running when their hello says a run is going, so a reconnect never makes a running worker eligible for the chase. The extension's link remembers the latest activity it was asked to send and sends it right after welcome, so a run that ends between hello and welcome still leaves the session idle.
- `web.ts`: the board has no login. Without a public host, only the Tailscale network reaches `cardd` (spec section 21.4): every board request must name an allowed Host, which closes DNS rebinding, and its Origin, when present, must be allowed. With a public host, a request for it needs Cloudflare Access's token instead (The public host, below).

### The public host

`access.ts` and `Web.channel` in `web.ts` decide what a request is before any route sees it. Without the four flags, every request is a tailnet request and nothing here runs. With them, each request is one of three things:

- Public: its Host is the public host exactly, with no port. Its Origin, when present, must be `https://<public host>`, and a write or a websocket upgrade must carry one. It needs a valid `Cf-Access-Jwt-Assertion` header. Only the board's own routes answer it: the pages, `/api/board`, `/api/card/N`, `/api/version`, `POST /api/action`, and the `/live` socket. `/call`, `/session`, and `/api/health` do not, even to the owner.
- Refused: its Host is anything else, but it carries a header that begins with `cf-`, a `Cdn-Loop` header, or an Origin whose host name is the public host, under any scheme or port. Cloudflare adds those headers to every request that it forwards, so such a request came through the tunnel with a rewritten Host. The markers only refuse: they never make a request public, so a valid token does not rescue it. This is the rule that stops a tailnet-looking request from becoming a way round the token check.
- Tailnet: everything else, handled exactly as before.

A process on the host that runs the tunnel can still send a request with the tailnet Host and none of the markers. It gets the tailnet's access, which any process on that host already has: the board with no login, and `/call` with a token.

The token is checked with `jose`: RS256 only (`none` and `HS*` are refused before a key is looked up), the signature against the team's certs endpoint, `iss` equal to `https://<team domain>`, `aud` holding the AUD tag, `exp` required, `nbf` and `exp` honored with five seconds of skew, and `email` equal to the owner, ignoring case. The keys are kept for ten minutes. An unknown key id fetches them again at most once every thirty seconds, and so does a failed fetch, because `Access` refuses without fetching for that long after a failure. A request whose keys cannot be had is refused, never let through. `CARDD_TIMING_SCALE` scales both times. A refusal gives a 403 with no reason and no board content. The reason goes to the log, once a minute for each reason. A reason is a name from a fixed set: a fixed sentence from `access.ts` or `Web.channel`, a `jose` error code, or a `jose` error code with the claim that failed. It never holds text from the request, so tokens that differ only in their text log once and keep nothing. A failed fetch of the keys logs its cause once for each cooldown. The token is read from the header only, never from the `CF_Authorization` cookie, so a cookie that Cloudflare would have turned into a header at the edge buys nothing at cardd. A websocket that was opened with a valid token stays open after the token expires. It carries only the word `changed`, and the data behind it still needs a valid token.

The test certs endpoint is served over TLS with a certificate that `openssl` makes for the test, and cardd trusts it through `NODE_EXTRA_CA_CERTS`. That keeps the production code free of any switch that fetches keys over plain HTTP.

### The timed check

- `check.ts` polls `cards.db` every 15 seconds. Each tick loads the open cards once and shares them between the rules. Finding identity includes the obligation, its occurrence when needed, and the current due tier. It emits the current tier once, never a backlog of missed tiers. Reminders pause while the receiving mate is down. See [Persistent wakes](wake-plan.md) for all cadences. An idle worker is a quiet session whose card is `idleNow`: working or in review, and not `pausedNow`.
- `pulse.ts` owns neglect eligibility. It uses protocol `idlePark` for dated hold coverage and `movement.ts` for [job coverage](neglect.md#what-counts-as-a-real-change). Armed waits and future checkpoints are quiet. The timed worker-stalled rule must also have a stalled pulse; it uses the same session last-seen clock. Disconnection and spinning retain separate rules: connection loss and unproductive turns are not silence.
- The timed check does not discover PRs, poll CI, or confirm merges. See [Closing](#closing) for on-demand verification.
- Finished open cards are reminded to their own mate after ten minutes, then every ten minutes (`chase` in `timing.ts`, the one interval for every reminder that waits on a mate's action). Escalating unresolved work is the second mate's decision.
- `timing.ts` owns the thresholds and test scale. A job is `running`, `lost`, `finished`, or `abandoned`. `@fleet/protocol` holds that state and the one rule table that moves it, and `cardd` is the only writer. A job is running only when that state is `running`. Three missed heartbeats move a running legacy job (one without a launch ID) on a live attempt to `lost`. A registered job is never lost for silence alone: when its heartbeats stop for three periods, the timed check runs one shell script on the attempt's host (through the `--hosts` route, with `LC_ALL=C`) that prints one verdict line. It first signals the pinned wrapper PID with `kill -0`: success, or `Operation not permitted`, means the process exists (so a restricted process view, such as `hidepid=2` or another account, never hides it), and only `No such process` proves it absent. For an existing process it reads the command line with `ps -ww -p <pid> -o args=`: a complete command line (not empty, not a bracketed name-only fallback) that carries the job's `fleet-job-<job>-<launch ID>.json` argument means the wrapper lives, and one that lacks it means the PID was reused, so the wrapper is gone. An empty, bracketed, or failed identity read is unknown. The job moves to `lost` only when the script exits successfully and prints exactly `fleet-probe absent`; the write guard re-checks the job, wrapper PID, and launch ID. A transport exit code is never evidence, whatever its value, so a route that exits 1, ssh failing with 255, a missing command, a timeout, a host with no route, and any other output are unknown and change nothing, and the next check asks again. A live wrapper that is stopped or slow stays running. One probe pass runs at a time and never inside the check's transaction. Its mate is reminded until the job is rerun or dropped. `job.drop` sets `dropped_at` on a lost job, for its worker or a mate of its lane, and the job stays lost. `dropped_at` is valid only on `lost`. Dropping twice is safe, and a job that is not lost is left as it is. A lost job that is not dropped runs again when its heartbeat returns: `job.alive` sets it back to running and sends its worker a `job-result` entry marked `revived`. A late result still finishes a lost job, dropped or not, and clears `dropped_at`. Ending an attempt, including close, abandons each running job of that attempt, so the row does not stay `running` after the attempt has ended. The extension syncs its tracked jobs from `cardd` before it delivers any job result, and keeps the result pending if the sync fails. The hub keeps one grace object for job loss: the time of the first check, and the stall deadline. The timed check skips lost-job detection for the first three heartbeat periods after `cardd` starts, so a restart does not lose jobs that have not yet reported. After a late check tick (the event loop stalled), job loss is skipped for three heartbeats too, so live jobs can report again.
- `bundle.ts` builds the one decision list for each mate: with-mate and merging cards, holds waiting on it, and for main every captain-held card, marked as the captain's. The holder of the hold picks the mate, not the card's lane. It is sent when its oldest card has waited ten minutes (`chase`) and the last list went out ten minutes ago, so a card resolved or held between lists never starts a second clock. A dated hold is a line in the list: it names what it waits on, until when, and how old the hold is. A watched wait, an outside date, and the captain's later are listed as information in their own group, and they ride along with every list. They never start a list on the ten minute cadence. A declared watcher, an outside date, and the captain's later stay in the information group until their date, regardless of hold age. When a mate has only such waits, it gets one information list (`information: N dated waits, nothing needs action`) once a day, `informing` in `timing.ts`, counted from the oldest wait or from the last list that was due for them, whichever is later. A list on the ten minute cadence that carries the watched group along does not count: its `watched` field is 0. The `watched` count in each list entry's `fields` is how the check reads that back after a restart, with no table of its own. An idle park (see `waits.ts`) is an item to act on, in the first group, so the date never hides it, and the check treats its card as acting. Its receiver is the holder's mate, as for any hold. The list is for the mate that owns the cards: it repeats to main every ten minutes while a captain decision is open, and that never asks main to write to the captain again, since main lists them to him only when he has written since its last list. For [expired worker checkpoints](wake-plan.md#worker-checkpoints), `pauseItem` uses the same job classification as pulse. It sets `since` to the pause date and lists `its worker's pause ended N min ago and nothing ran since`, with the first line of the paused report. It does not depend on a live session or delivery state.

### Health and logs

- Every `cardd serve` log line starts with an ISO timestamp (`log.ts`).
- `health.ts` watches the event loop two ways. `monitorEventLoopDelay` feeds the five-minute summary. A 100 ms timer measures how late it fires, and a line `warning: event loop lag <ms> ms, p99 <ms> ms, max <ms> ms` is logged when it is over 1 second. That timer also sets the latest lag that `/api/health` reports, so every incident counts, not only a record one.
- A check tick over 500 ms logs `warning: check took <ms> ms, over 500 ms (slowest part: <name>)`.
- Every five minutes it logs `health: loop p50 ... p99 ... max ...; longest tick <ms> (<part>); accepted <n>; sockets <n>; sessions <n>; rss <MB>`, then starts a new window.
- `GET /api/health` answers `Health` from `@fleet/protocol` with no card loading and no auth: `commit`, `now` and `windowStart` (epoch ms), `loopP50Ms`, `loopP99Ms`, `loopMaxMs` (since `windowStart`, the last five-minute summary), `lastLagMs` and `lastLagAt` (the last lag over 1 second, `null` until one happens, never reset), `lastTickMs`, `longestTickMs` (this window), `sockets` (open connections), `sessions` (live session sockets), and `rssBytes`.
- Policy: alert and shed load, never exit on lag. `cardd` has no exit or restart on lag.
- `e2e/cardd/health.test.ts` freezes a real `cardd` with SIGSTOP and SIGCONT, then reads the health and the log.

### Runtime incidents

- A runtime incident is one failure episode of one actor, a worker or a mate: a model turn that ended in an error, a worker that never connected, or a worker connection that was lost. `incidents.ts` owns them. They are not report entries, so they never change a card's status and never take back a `done` or a pause. The record keeps the actor's intent from the card when the incident opens. That intent is a checked set: working, paused, completed, closed, queued, with-mate, needs-you, waiting, and merging for rows saved before active Merging became working intent. `incidents.state` is the same kind of checked set. Both are parsed when a row is read. `nextIncident` in `incident-lifecycle.ts` is the only transition table, and every state write goes through it. Recovery is offered only for a working snapshot, or a saved merging snapshot, while the card's current intent is also working. The eligibility notice and every recovery step a message names check the current intent as well as the snapshot, so a later pause, hold, or completion is never offered recovery. Closing the card is a `card-closed` event: it supersedes every live incident of that card. Active Merging is working intent, including post-merge verification that a parent requested after the worker's done or merged report. An explicit merged report is a completed handoff until that new work is requested. A PR's merged state alone does not finish that verification. A future worker pause remains a pause even when the card's stage stays Merging. Recovery reads `pausedNow` and `isFinished` (see Status and holds).
- The error comes from Pi's own failed assistant message, read at `agent_settled` by `failure.ts`, so no second model turn is needed to learn the cause. Reading it at the settle and not at each message keeps a failure that Pi's own retry or a queued follow-up cured in the same run from being reported. A failed turn also skips the handoff nudge and the `stopped` report, since both would need another model call that would fail the same way. A failure the extension cannot send at once is kept and sent at the next connect. The extension keeps no record of what it reported. Each settled run that ended without an error, and each successful compaction, asks `cardd` to clear, and `cardd` answers from its own incident. A clear that could not be sent is kept the same way and sent at the next connect, before every kept failure of either kind, since an actor has one live incident across both phases and a failure sent first would join the incident that the clear then closes. A success also drops a kept failure of its kind, since that episode ended before `cardd` heard of it. What is kept lives in a process-wide cell, not in the reload-local `Failures`, because the process id and the incident survive a reload and so must what the extension still owes `cardd`.
- A failed compaction (`session_compact_failed`, not an abort) is a `compaction` incident with its original error, told once like a turn failure. The backoff's failure count and next retry live in the same process-wide cell as the patch that reads them, so a reload does not clear the backoff and does not retry a failed compaction at once. Only a successful `session_compact`, or a compaction of a session too small to compact (below), verifies its recovery, after the recovery check reached the process; a retry or a replacement makes the extension compact once, without a model turn. A manual compaction of a session too small to compact is not a failure. Pi gives no code for it, only the error text `Compaction failed: Nothing to compact (session too small)`, so `failure.ts` matches that whole text and treats it as a finished compaction: it opens no incident, feeds nothing to the backoff, and asks `cardd` to clear, which closes a live compaction incident and verifies a compaction recovery. Every other compaction error, such as `Already compacted`, is still an incident. A turn that succeeds does not clear a compaction incident, and a compaction does not clear a turn incident. A `stale-module` error, a missing import from an old loaded bundle, offers only `replace`, which keeps the same session and card. Fleet decides recovery from the error text alone and does not rely on any router fallback.
- Recovery never creates a card, a conversation, or an attempt: every incident and recovery entry is on the actor's own card. The one card fleet makes is the captain card for main's own failure, since main has no card, and it is not a recovery.
- `sanitize` hides bearer tokens, key-shaped strings, and long opaque words, and cuts the text, before it is stored or told. `classify` is a pure match on that text: `stale-module`, `router-cooldown`, `vendor-quota`, `auth`, `transient`, or `unknown`. Unknown stays unknown. A local router cooldown is never called a vendor quota, and the router's own timers are not used as a vendor reset. Only a `Retry-After` in the error is trusted as a reset time.
- An actor has at most one live incident (`one_live_incident`). Repeated errors of the episode add to its count and tell nobody. The direct parent hears once when it opens: a worker's mate, a second mate's main. Main has no parent, so its incident is a card for the captain with a hold on the captain, which the board shows with no agent involved. The timed check ties the `worker-never-connected` and `worker-not-connected` findings to an incident, so those findings carry its id and stay the one message. The message names the incident, its process generation, and the next step. Once the incident's retries and replacements are spent (and at least one was used), the finding is keyed to the incident id at tier 1, so it is sent once for that incident and generation and does not repeat every five minutes. The notice says no incident recovery is left and that it needs intervention. For a worker it also says that an ordinary `restart_card` without an incident is independent and keeps its direct-parent, card-state, and three-per-hour eligibility, with no new authority. A new incident or generation is notified again. A worker that is paused or finished gets no incident from the watchdog. A second mate whose connection is lost, not closed cleanly, for longer than the not-connected grace gets an incident for main, unless that mate is in a stop that has not ended. `lane.stopping` starts the stop, and it ends at `stopping_until` (four minutes, on the same scale as the other graces) or at the mate's next connect, whichever comes first. A loss that is still open after the stop ends is reported, so an abandoned stop cannot hide a later crash. A mate that reconnects in the same process clears a lost or startup incident, so a network blip leaves no open incident. A live incident also holds back the idle finding and the `missed` chase for that actor, since the same failure caused them.
- A session's `process` is a random id generated once for the OS process and sent in `hello`. An in-process reload keeps it. A new OS process raises `generation` and supersedes an open or blocked incident, since a failure of the new process is a new episode. A recovering incident stays, so a replacement can finish. If that recovery then fails to verify, the incident moves to the generation the actor is on now, so the generation in its next message is one that `card.restart` accepts. When recovery fails after a generation change, or a new process supersedes the incident, the same transaction retires the old generation's queued commands without deleting their entries. The migration `039-incident-generation-follows-process.sql` does the same for open or blocked incidents that the old code left behind. It withdraws queued advice with the former generation, including for recovering incidents whose state and generation stay unchanged, and resets the due-notice flag for the incidents it moves. A cardd restart keeps the process id, so it keeps the incident and tells nothing again. A reload or a relaunch completes a reload that was already in progress because that extension's first hello says it just started (`started`), not because the process id changed. A reconnect of the same link does not. The link sends `started` in each hello until `cardd` answers one with welcome, so a connection that drops before the answer does not lose it.
- `card.restart` (the `restart_card` tool) is for the direct parent only. It carries the card, the incident, the generation it read, a mode, and a key, and optionally `avoid` and `model`, whose rules are under Lanes and homes (Dispatch's `model`). In one transaction it refuses a foreign parent, a stale generation, a mode the class does not allow or whose budget is spent, and a time before the incident's eligible time. An ordinary restart of a working card or a card with its mate replaces the process as before. It writes its note before the process is started, because that note is what a repeated key finds. For failures known to precede worker launch, and the uninspectable-pane exception described below, the tool calls `card.restart.failed` with the key and request entry ID. An issued start with an inspectable pane and uncertain outcome remains counted. Cardd checks the exact request against that worker session's generation before refunding it. Lane restart plans omit the refund ID, and lane requests cannot be refunded. `cardd` records a fixed outcome, not pane output. If cardd does not confirm the refund, the initiating mate sees the scrubbed launch cause, available context, and a warning that the request might still count. A late report cannot cancel a different request that reuses the key. A restart whose note has such a note after it counts toward neither the three an hour nor the repeated key, so the same key starts it again. Only the direct parent can report a failed start, and a refusal by `card.restart` writes nothing, so it never counts. A refund drops that request's pending notice without deleting its entry. A refund also withdraws the model pin that request set: the pin becomes that of the latest request not refunded, or the one from before the first pin, so a retry of the key without a model keeps the earlier pin. A card that is paused, finished, waiting, or held for the captain is replaced only when its worker's session is disconnected (`lost`, `exited`, or never connected). The plan then says `reconnect`: the restart writes one note, resumes nothing, and leaves the card's status as it was. A connected worker of such a card is refused, because there is nothing to reconnect, and a repeated key still answers with the same plan. It rechecks the current card's execution intent before starting recovery, and the eligibility notice uses that same current intent, so a later pause or completion is protected too. Existing incidents whose saved intent is `merging` need no data rewrite: they may recover only while the current execution intent is working. A second recovery with another key while one runs is refused, and the same key answers with the same plan, so a retried call after a crash never starts a second one. Budgets are two retries and one replacement for each episode. A retry waits 30 s, then 2 min, never less than the `Retry-After`. A vendor quota with no known reset and bad credentials are blocked at once: restarting is not a repair.
- Recovery sends a health check, never a task. `retry` delivers it to the live process. `replace` records it and delivers it only when the new process connects, so the old process can never answer it. The recovery is verified when the check's turn settled without an error (the same acknowledgement that marks the delivery taken in) and the actor then made a `report`, `comment`, or `board` call after the check reached it. A process that merely started does not verify. A failed check turn, or no verification within the window, spends the attempt, is told once, and ends in `blocked` when no mode is left. The extension takes a recovery check as an end of run that needs no handoff, so it never nudges a paused worker into work.
- Times that a person or a vendor sets, the eligible time and the `Retry-After`, read the controllable wall clock. The verification window uses the real clock.
- `incident-escalation.ts`: a live incident of a worker in a second mate's lane goes to main when no recovery is left. Main hears it once, as one `runtime-failure-unrecoverable` finding in a single line that names the card, its lane, the incident, the failure, and why. It is written when the owning mate's first reminder is due, one `repeat` after the incident opened, and only while the incident's saved intent is working (or the old `merging`). It waits for main to be up. It is retired when the incident ends or the card closes or pauses, and a pause does not let it be written a second time: the entry already written for the incident keeps a resume from sending another. A recovery that is running holds back a finding not yet sent and keeps one already sent. The owning mate's reminders are unchanged. A worker in main's own lane is not escalated, since main is its mate.
- "No recovery left" is exactly one of two things. The incident is `blocked`: its class allows no mode (`auth`), or the retry budget and the replacement budget it allows are spent. Or the direct parent asked for a restart that avoids the provider of the card's explicit model, and `card.restart` refused it. The request must name an open incident of that card at its current generation, while the card is working. A refused avoid counts even while a retry is pending, and even when the same request is also too early or names a mode the class does not allow, since the avoid is checked before those: the mate tried to leave the failing provider and could not. The message to main then says that a retry is still pending and when it becomes eligible. A pending eligible retry holds back escalation only while no recovery has been refused. Any other refused restart is not a refusal that counts: waiting or a better request still reaches a recovery.
- The explicit-model refusal is the one that cannot be derived from the incident, so it is kept. `keepingRefusals` wraps every op. For an incident restart of an open incident, `card.restart` checks the direct parent, that the incident belongs to the card, the generation, and the card's current execution intent before it refuses the avoid. A request that fails one of these gets that error and records nothing. `AvoidRefused` carries the incident that the request named. A refusal of the request's own new `model` carries none, since the mate fixes that by naming another model, so it records no note and does not reach main. When `card.restart` throws it, a `restart-refused` check note goes on the card for that incident, in its own transaction, since the refused call rolled back. It records one note for each incident, and nothing for a restart that names no incident.

### Closing

`merged-report.ts` verifies a `status="merged"` report with `gh pr view` in the project's direnv on the latest attempt's host. The returned URL must match the reported URL and its state must be `MERGED`. Without verification, the report counts as `done`. For a ship card with a recorded PR but no merge in its record, closing can check the recorded URL directly. This checks landing, not merge authority. For the worker and mate workflow, see [linked ship cards](multiple-pr-delivery.md).

`closing.ts`: close decides Done or Dropped from the record (guard 7, spec section 20.5), the way Firstmate's teardown did. A local-only card lands only when its landing is authorized: the card is Merging, by yolo or by the captain's approval. Then `close.begin` asks the host to land it. Done means landed. A merged PR landed everything. Otherwise the worker's latest handoff must be done. A task or comment routed to the worker takes that completion back, including a replacement attempt's task. Coordination routed to a mate or the captain does not: it asks no new work of the worker. A `stopped` report is not a handoff of its own: `doneStands` (`status.ts`) is true when the worker's last report that says anything about the work (not a `note`) is `done` or `merged` and nothing was routed to the worker since, and then the `report` operation drops a `stopped` report without writing it, so a stop after done changes no status and never blocks close. Done then `working`, `paused`, or `in-review` is not that case: a later `stopped` is written as before. The entry record is replayed for close and finished-card reminders, so a restart needs no separate completion state. A ship card must have no unmerged PR, and the host confirms that no attempt has a commit off the base branch or an uncommitted file. Dropped is never a fallback: the mate asks for it with `landed=false`, and a merged PR refuses it. A captain card has no worker, so it closes as Done once the captain acted. The record is checked again after the host confirms.

A scout closes Done only when the close names what happens next (`next-step.ts`). Two scouts, c-1357 and its revision c-1368, closed as "nothing built": the go-ahead to build had been in the mate's head and not on any card, so no reminder carried it. `close.begin` and `close.finish` take an optional `next` with exactly one of `build` (a ship card, open or Done, never Dropped), `decision` (an open card whose hold waits on the captain, so the card has the `needs-you` status and is on his list), `drop` (the reason), or `delivered` (`evidence` of what was read or relayed, to whom and where recorded, and `disposition` stating why that completes the request with no authorized build or unresolved decision left). Delivered is an explicit mate attestation, not a claim inferred from a worker's done report. It does not invent a drop or replace a pending decision or authorized build. Both fields must contain nonblank text. No new card state or migration is needed. A follow-up must exist in the closing mate's own lane, a direct child lane, or its parent lane. This close-only reference check lets a second mate name main's follow-up without gaining read or write access to it. A sibling-lane reference is refused; main can close the scout naming that sibling's card. cardd still validates the follow-up's kind and state in both close operations. A card with no hold, a hold that is still dated, or a hold that waits only on main is not on the captain's list, so it is refused: the mate makes the decision's card, holds it, and a second mate's hold waits for main to escalate it before the close names it. `closable` runs the check for both operations, after the work's own check, so `close.begin` refuses before the extension stops a worker or archives anything, and `close.finish` refuses a caller that never asked `close.begin`. `next` is refused for every other close: a ship or captain card, and any close that ends Dropped, so `landed=false` works as it did. The scout's cleanup entry records it in `fields.next` and starts its body with one line (`Next: c-N carries the build.`, `Next: the captain decides on c-N.`, `Next: nothing is built, because <reason>.`, or `Delivered: <evidence>` followed by `Disposition: <disposition>`), the line that the board shows collapsed. The rule runs when a scout closes and stores nothing on the card, so a scout that was open before it existed is held to it too, with no migration. An extension that still has the older `close` tool has no `next` to send: it can close a scout only with `landed=false` until its lane restarts on the new code. A newer extension talking to an older `cardd` sends `next` and `cardd` ignores it. When a second mate closes its own card, main hears. When main closes it, the card's mate hears. Close also supersedes the card's live incidents (see Runtime incidents).

## Extension

### Entry and arguments

- `index.ts`: dispatch starts each worker with `--fleet-url`, `--fleet-token`, and `--fleet-role`. `FLEET_URL`, `FLEET_TOKEN`, and `FLEET_ROLE` work too. A worker whose mate has a `bws` block also gets `--fleet-bws` (`FLEET_BWS` works too), described under Secrets from bws. A Pi in a lane home needs none of them: the home's `config/lane.json` makes it that lane's mate. Without either, the extension does nothing.
- `fleet-args.ts`: each value follows `=` in its flag, because Pi reads a separate value that begins with `-` as an option, and 1 `cardd` token in 64 begins with `-`. `launch.ts` turns the separate value of each option it takes, such as `--url <value>`, into `--url=<value>` for the same reason. It refuses `--token` before it reads anything else, so no token value is ever in its argument list or in a message.
- `TRUST_ARG` (`--approve`) is the one place fleet answers Pi's project-trust prompt. Every launch of Pi by fleet puts it ahead of the configured arguments: a worker's start and replacement (`dispatch.ts`), a lane mate's start (`homes.ts`), and any relaunch (`relaunch-run.ts`, which adds it when the old command line lacks it, so a session that an older fleet started is covered after an update). Pi applies it to that one process and saves nothing to `trust.json`, so only a lane home or card worktree that fleet started a session in is ever trusted. A lane's own `--no-approve` still wins, because the last flag decides. Pi asks only when the folder holds project resources such as `.pi/settings.json` or `.pi/extensions`, and this repository holds both.
- `.pi/extensions/fleet.ts` loads the fleet extensions only in a lane home. A worker in a worktree of this repository has no `config/lane.json`, so it loads nothing from there and needs no installed packages. Dispatch gives workers the extension with `-e`.
- Activity at each run and tool call keeps `last_activity` fresh for the stall check (spec section 12.2).

### Sessions

- [Updating the fleet](setup.md#7-updating-the-fleet) owns what main sees. In `cardd`, `maintenance_batches` holds a reload batch's membership, so overlapping updates share a request that is still pending without taking it out of the earlier batch. A request that is already `reloading` is not shared: the later batch gets its own failed row, unverified, and the earlier batch keeps the request and its verification. `dropMaintenance` turns a removed lane's memberships into rows with no request that keep its host and outcome (`gone`: `failed` or `removed`), so each removal stays counted until the batch's last request settles. Settling a request checks every batch it belongs to, and a request that has no membership in its original batch (outstanding before batches) keeps its individual notice. The hello's optional `runtime` is the `Link`'s id, stored on the session; the request takes it at enrollment and again when it acknowledges, and `adoptMaintenance` completes a `reloading` request only for a started hello whose runtime differs from that one. It also fails a pending reload when the target says it lacks safe reloads, and `closeFinish` settles the closed card's open requests as failed. The summary is stored on the first verified target's card, because main has no lane card, and hidden from every reader but the registered root (`entryFor`, the board's thread, and `maintenanceStatus`). Its `maintenanceBatch` field prevents a second summary. A failed reload's stored note and reason have no runtime id: `identified` adds the card, host and runtime when `toPush` delivers it to the root, and `projected` does the same for the root's request and status results. The first failed acknowledgement of a pending request and an unsupported reconnect take the refusing connection's runtime (`actor`); a request that is `reloading` keeps the one that acknowledged. The runtime path is reload-only: a stow is completed by any started hello. `requestAndAwait` keeps the enrollment rows that a later status omits, and `requestMaintenance` enrolls no target for a reload batch that already has a request or membership row (`known`), tombstones included, so a retry changes nothing from the moment the first request or membership exists, not only after a summary; an open row that a later status omits is reported as failed and no longer reported. Stows keep their per-process notifications and their own `batch` column.
- `reload-observer.ts` records helper starts, verified successes and redacted errors in the host's `logs/reloads.jsonl`. It receives the maintenance receipt through the helper environment, not the command line. It reports helper errors with the existing `maintenance.ack` operation and checks completion with `maintenance.read`, which is restricted to the owning session. The update enforces its verification deadline with `maintenance.status`; only the request's original requester can use it to fail a reload still in progress. Worker hellos carry optional PID and process-start metadata, and cardd logs their accepted hello and socket close. These fields are diagnostic, not authentication or proof of a new process.

- `link.ts` holds the session's one websocket. It sends hello with the fleet entry IDs found in the session file, reconnects with backoff, and matches calls with their results. A close with code 4002 means a newer connection took the session. The link stops, the same as for 4001, so the old connection does not connect again and take the session back. A message from `cardd` that fails the protocol schema closes the socket with 4003 and the schema error as the reason, which reconnects with backoff, and the session says so once until it connects again. `cardd` logs that reason once for the session until the session sends anything else. A session that runs in a herdr pane also reloads itself, as `update_fleet` does: `MaintenanceQueue.reloadForStaleCode` relaunches Pi on the same conversation at its next safe point (its turn is over and no message waits), so that it loads the code on disk, which is the code that `cardd` runs. A result that fails its schema asks for the same reload. A reconnect does not cancel the request, because a welcome that parses does not show that the message or result that failed can be read: only the replacement process drops it. The relaunch passes `--fleet-stale-reload=<ms>`, and a process started with it does not reload again for 10 minutes, so a checkout that is behind `cardd` costs one relaunch each 10 minutes and not a loop. Jobs are not a reason to wait, because their results are queued in `cardd` and arrive when the session connects. A session that runs outside a herdr pane only says so. An exception in a websocket listener would end Pi, so a `cardd` on other code would crash-loop every mate.
- `cardd-watch.ts` is main's probe of `cardd`, started only for a mate whose lane is `main`. In flag or environment mode the lane comes from `FLEET_LANE`. Every 60 seconds it opens a fresh connection with no keep-alive and makes a timed call on the existing websocket, and labels the result `ok`, `slow`, `refusing-new`, `down`, or `unreachable`. A fresh connection that fails while the existing socket answers is `refusing-new`, decided before the port 22 control probe. After 3 failing probes in a row it tells main's own session once, and it tells once more when `cardd` answers again. A run of only `down` probes needs 5. It stays quiet while the lifecycle lock is held or the commit changes, and it never restarts `cardd`. `FLEET_PROBE_INTERVAL_MS`, `FLEET_PROBE_DEADLINE_MS`, `FLEET_PROBE_FAILS`, `FLEET_PROBE_DOWN_FAILS`, and `FLEET_PROBE_CONTROL_PORT` tune it. `e2e/extension/cardd-probe.test.ts` covers it.
- `plan.ts` fetches the mate's plan with `lane.plan` at the first connect, keeps it for the life of the process, and adds the goal and schedule to the system prompt in its own `before_agent_start` handler, after the role contract and the charter, waiting for a fetch that is under way. A plan that cannot be fetched is tried again at the next connect. Because it is read once, a changed plan applies at the next start. `wake.ts` is the `fleet wake` command: it posts the `wake` op with the lane's own token.
- `intake.ts` decides what the model took in from the fleet messages the process tracks, never from the requests Pi sends. A request is not a safe source: with conversation memory on, the request holds the memory's own projection of a fleet message, which has no fleet identity, and a failed request can be followed by a compaction that removes an entry before the retry. The process tracks the fleet entries that arrive through `message_end` and the ones already in the session file when it starts. A finished response (no abort, no error) sends `read` for the entries that arrived since the last one, and a settled run that ends without abort or error sends `ack` for every tracked entry. Every settle forgets the tracked entries, whether the run finished or not. A tracked entry is read or acknowledged only while it is still in the session's active model context at that moment, which is read from Pi's own session projection of the raw entries (compaction, the active branch, and context edits applied), so memory cannot hide it. An entry that compaction removed before the settle, whether before a restart, between the restart and its first request, or while a failed request was retried, is not read and not taken in, and the chase resends it. A run that ends aborted or with a failed answer acks nothing and forgets its entries, so a later run of the same process does not take them in even though their messages are still in its context. The chase resends them marked `again`, and the resent message is taken in by the settled run that follows. This holds for the abort and resume case and for a provider failure followed by recovery. The entries that were in the session file at start are tracked the same way, are dropped at the first settle whether or not it took them in, and send no `read`, because a filed entry does not block the report gate. Nothing is suppressed locally, so an entry that arrives again, which is how the chase and a connect push send one again, is tracked again, and an `ack` that `cardd` never received is made again by the next run that settles with the resent message in its context. The session file's own ID list (`idsInSessionFile`) goes to hello, to the push deduplication, and to this tracking at start. `link.ts` keeps a `read` or an `ack` made while `cardd` is unreachable and sends it at the next connect.
- The mate-only `yield` tool in `mate.ts` returns Pi's native `terminate: true` with empty content. It ends the automatic model follow-up without aborting, so normal settle, intake acknowledgment, activity, and conversation memory still run. Queued fleet messages still reach the model. Pi ends a tool block without another model call only when every result in it carries `terminate: true` (`shouldTerminateToolBatch` in pi-agent-core, unchanged from 1.0.0 to 1.5.2). A `tool_result` hook cannot set the flag (`ToolResultEventResult` has no `terminate`, and the session drops it), and the built-in tools never set it, so a block of yield with comment, hold, close, bash or any other call got one more model call, and the model filled it with chat such as ".". `registerYield` fixes this where Pi allows it: it keeps the result of every call of the current assistant message as the call ends, and once a `yield` has ended it sets `terminate` on all of them, including the ones that ended before it. A yield inside a codemode script counts too: Pi emits its `tool_execution_end` with `parentToolCallId`, and codemode does not pass a nested `terminate` on, so the hook ends the enclosing codemode call. Pi emits that event with the same result object that it reads for the block decision, and reads the decision only after every call of the block has ended, in sequential and in parallel mode. That is a mutation of an event payload, not a documented hook, so `e2e/extension/yield.test.ts` fails the day a Pi upgrade stops honoring it. A call of the block that fails does not stop the silent end: its error is in the transcript for the next turn, and the contract tells the mate to yield in a later block when the next step depends on a result. A message that arrives during the block is a steering message, and Pi still polls for it after a terminating block, so it starts a new turn. Its self-rendered call and result draw zero lines even with calm off. Silence never substitutes for a reply to the captain's own message, an outcome, findings, a review or merge request, a decision, or a real blocker. The restored original contract yields only when required actions leave no news for the captain. Reminder lists respect his absence. These presentation rules are text, not deterministic model behavior.
- `inbox.ts`: Pi skips session file lines that do not parse, such as a line torn by a crash, and so does the extension. Pi creates the session file late, so it may not exist yet. A time from the model must be ISO 8601 with `Z` or an offset, so no host's zone can shift it.
- `worker.ts`: a run may end only with a handoff, a tracked wait, or a queued continuation. Otherwise the worker asks cardd with `job.idle` and gets one nudge only when cardd confirms no job waits. A failed, timed-out, unsupported, or busy answer suppresses the nudge. It requests `stopped-if-idle` only after the current run received that nudge, so an unknown idle answer never leads to an automatic stop. A deliberate pane stop is not gated by the nudge. Cardd records `stopped` only if that attempt has no running jobs or outstanding startup reservations, checking within the same transaction that records the report. A missing or incomplete job list cannot authorize an automatic stop, including after reload. The worker only remembers an automatic handoff after a successful, non-deferred reply. If that reply is lost, it does not replay the mutation on reconnect. A deliberate pane stop still reports `stopped` directly and retries on reconnect. A run whose last turn failed gets neither: the failure is a runtime incident (see Runtime incidents). The extension remembers the last report it sent only as a hint for that nudge (`pauseHint`). It is not the card's pause: a mate's steer can resume the card while this process still remembers the old pause, and the timed check is what watches that card. Nothing is filed at a settle once the process is leaving, aborted or not, because a pane stop counts only while the process stays. The SIGTERM and SIGHUP handlers and the `fleet:leaving` event, which the maintenance relaunch emits before it asks Pi to shut down, mark the process as leaving, and cardd sees the lost connection as a runtime incident instead. Pi 1.5.1 and later abort a run that is still active when they shut down (`AgentSessionRuntime.dispose()` calls `session.abort()` first), and `agent_settled` then reports `aborted` just as it reports Escape. Pi 1.5.0, the version this repository pins, does not abort on shutdown, so there the e2e SIGTERM and SIGHUP tests pass without the guard.
- `worker.ts` also keeps the worker's herdr pane honest. The pane reads blocked only while `cardd`'s `standing` for the card says attention is blocked, never from the worker's own last report. It asks right after each report. While the pane reads blocked it asks again every 15 s (`FLEET_STANDING_MS`), so a mate's dated hold, a steer, or a close takes the red off, and a worker that waits on its mate with no hold keeps it. Herdr has only working, blocked, and idle, so a pane that is no longer blocked reads idle, not Waiting with its date. When `standing` cannot be read, the pane follows the report it just made, and a pane that reads blocked stays so. On session shutdown, including an in-process reload, the run stops asking and drops any answer still in flight, so a reloaded session never keeps the old run's timer alive.
- A mate's contract is its home's `AGENTS.md`. Fleet keeps the content Pi loaded at startup, reload, or /stow, and adds the content it read then when Pi did not discover the file (`--no-context-files`). Edits apply only at those moments. Before each turn Fleet only checks, without following symlinks, that the file is still a readable regular file. OptChat's refresh makes the same check for that path and keeps its loaded content. A missing, unreadable, rejected, or blank contract aborts the mate run before its model request. Fleet checks the file again when the run starts (`agent_start`), where the abort has a live run to stop, so a file that changes between the two checks still cannot reach the model. Restore the named file and retry; other project context cannot substitute for it. `prompts.ts` holds the worker contract, which `index.ts` adds to the system prompt of every worker run. Cardd compares the registered repository with `1yian/fleet` case-insensitively. Dispatch and replacement pass only the resulting Fleet/non-Fleet classification to worker startup, not the repository identifier. An explicit non-Fleet classification leaves context untouched. When classification is unknown, routing recognizes only worktrees that share a Git common directory with the extension checkout; separate mirrors and clones need `--repo 1yian/fleet`. Existing workers without the launch classification need replacement rather than reload to receive it. `contributorGuideForWorkers` removes the checkout's own `AGENTS.md` from worker context, whatever that file says. It puts the root `CONTRIBUTING.md` in its place if available, or adds it when no root `AGENTS.md` was loaded (`--no-context-files`). When the guide is missing, the worker still gets the worker contract, not the mate's. Context files from other paths, such as a global or ancestor `AGENTS.md`, are left alone. Workers of other projects are untouched. So a worker in this repository never loads the mates' job description.
- `views.ts` prints `board` in the AXI shape (https://axi.md): TOON records, few fields by default, counts first, long text cut with its size, an explicit empty state, and next steps. It is pure. It prints a `dated` row for each dated wait, which main's catch-up reads, and a next step for an idle park. For one card it prints the `dated` line and the hold's `remaining` steps, and for a merge question `merge` and the options that approve it (`approves`). The board's header is AXI ambient context: the projects with their yolo flag and, for main alone, the lanes. Past a set number of projects, it lists only those with open cards or yolo on. A second mate reads only its own lane through `board`, including its lane card and the cards it created. Main reads every lane. `cardd` scopes the `board` and `card` operations by the authenticated session's lane, so counts cover only visible cards and opening another lane's card tells a second mate to ask main. Projects remain shared. The captain's web board stays unrestricted. Mates never read with sqlite.

### Secrets from bws

- `bws.ts` is the one reader. `Bws.lookup(reference)` finds a secret by id (a UUID, `bws secret get`) or by key in `project`, then `common` (`bws secret list <project id>`). A project is named by its id only, and `bwsConfig` refuses anything that is not a UUID, so the reader never looks a project up by name. Another feature that needs a bws secret reuses it and `resolveSecret`.
- `bws` runs as a child with the machine-account token in that child's `BWS_ACCESS_TOKEN`, never in its arguments. `bws secret list` prints values, so the reader parses them in memory and keeps the list for the life of the `Bws` object, one list for each project. A failure becomes one fixed phrase: no `bws` on the PATH, a timeout, or its exit status with its first stderr line, cut short and with the token replaced. A JSON parse error is never passed on, because V8 puts a piece of the text in its message.
- `resolveSecret` returns the value and one note that names the source, never the value. The caller picks the fallback: `lane-secrets.ts` falls back to `token` in `config/lane.json` for the lane token, and to the variable the process already had for an entry of `bws.env`.
- A mate shows all its notes in one notice, because Pi's status line replaces the one before it.
- The mate reads its secrets in an async `session_start`, before `start()`, so Pi's first model call already sees the environment secrets. It hands `bws` to its workers as `--fleet-bws=<JSON>` inside `FLEET_PI_ARGS`. The JSON holds the token file's path, project ids, and the env map, so no value is in a worker's arguments. A worker resolves them on its own host, with its own `bws` and token file.
- A `run_long` job does not get these variables. Its tab is a new shell of the pane, so the fleet would have to write the values into the job's file or its command, and it must write neither.
- `fleet secrets` is the check before an old file goes. It resolves from bws only and compares the lane token with the file in memory, so it prints `the same as` or `different from` and no value.

### Dispatch and herdr

- The `dispatch` tool first resolves the host through this lane's transport map, before creating a card. A globally registered project clone does not give the lane a transport. An unsupported host leaves no card, attempt, branch, or workspace. This is a configuration check, not a connection probe. A later connection failure keeps the card and any attempt already created, so failed work stays visible. `e2e/extension/dispatch-preflight.test.ts` covers the refusal, corrected dispatch, repeated dispatch, and connection failures before and after attempt creation.
- The project check (`personal.ts`) refuses an unknown non-personal project with a pointer to `personal`. For a registered `personal` project, dispatch uses the exact clone key (including `local`) or refuses and lists the registered hosts. Only when bootstrapping a missing project does it translate `local` to the lane's Fleet host name, which it checks and passes unchanged to cardd and the attempt. It never adds a clone to a registered project.
- If `personal` is missing, `project.personal` accepts only a canonical host name and returns an acknowledgement. Cardd checks that the caller is main and the host is routable. It serializes bootstrap calls from registry lookup through repository creation and registration. The host stages one synthetic empty root commit on `main` using Git plumbing, without signing or running inherited hooks. It leaves normal Git configuration and workflows unchanged, then publishes the clone at `$FLEET_HOST_DIR/projects/personal` (default `~/.fleet/projects/personal`) without replacing an existing path. If publication happened but registration did not, only a marked, unchanged empty Fleet bootstrap can resume. Cardd validates the framed absolute path before registering the project as `local-only`, with yolo off and no repository metadata. If the administrator registers `personal` during bootstrap, that registration wins. Dispatch uses its exact clone key or reports the missing clone; any now-unused bootstrap checkout stays on disk. The regular repository discovery still probes `origin` for projects without repository metadata, including the built-in `personal` clone, even though it starts without a remote. `e2e/extension/fresh-install.test.ts` checks main-only bootstrap, host identity, interruption and recovery, and checked artifact handoff without a landing hold.
- `dispatch.ts`: `cardd` creates or finds the attempt. Each host step then looks for its own result by the names that derive from the attempt ID, so a retry after a lost connection never starts a second worker.
- herdr counts an agent as ready when it idles, and a worker starts on its task at once, so herdr's own wait often runs out. Dispatch does not rely on it: the pane shows whether Pi started. herdr's minimum wait is just above 3 s.
- herdr refuses a start and types nothing when the shell is not at its prompt yet, or when it still holds the agent name of a worker that died a moment ago, for up to about 4 s on CI. A refused start goes again at once. A command lost before the shell goes once more. herdr refuses a pane where Pi runs, so no second Pi starts.
- A new shell first runs its prompt's helpers, such as git, and keys typed then can be lost. So a start waits until the shell is idle.
- Pi in the worker's pane is the truth about a worker, because `cardd` may not have seen it die yet. Pi names its process `pi`: macOS reports it as argv0, Linux as the process name. Herdr may report the name as `MainThread`, so a `node` process running a script named `pi` also counts. Herdr reads a process's name and its arguments one after the other, so while a process execs a read can give `node` with no arguments, and that read matches no Pi. A read that matches no Pi therefore never says that Pi is gone. The launch watch (`confirmStays`) takes Pi as gone only when the shell is idle again (`shellIdle`). A lane whose pane foreground is anything other than an idle shell counts as running, so a second `fleet up` does not start the mate again.
- `host.ts`: a host that is neither listed in `FLEET_HOSTS` nor this lane's own host (`host` in `config/lane.json`, `FLEET_HOST`, or the hostname) has no transport, and `NoTransport` is thrown before anything runs. Running its command here would act on this host's disk with another host's paths. The close and startup refreshes print `skipped: no transport for <host>`. A host listed in `FLEET_HOSTS` runs herdr through its transport, such as `["ssh", "p620"]`. ssh exits 255 for a lost or refused connection, which, like a probe that times out, means the host is unreachable. `--session` must come before a `--` delimiter, or herdr passes it to the agent. A command that runs to completion over a transport whose program is `ssh` goes through `runOnTransport` (`@fleet/protocol/transport`, a Node-only subpath export), the one function that `host.ts` and every `cardd` route that does so (merged-PR check, empty-branch check, project repo lookup) call. When such a run exits 255 and its error ends with `mux_client_request_session: send fds failed`, it runs the same command once more with `-o ControlMaster=no -o ControlPath=none` in front of the transport's arguments (the first value of an ssh option wins, so this beats `~/.ssh/config`). That line is the fatal that ssh prints after `mm_send_fd: sendmsg` fails, and ssh dies there. The master opens a session only after it has received all three descriptors, so the command never ran and the retry cannot run it twice. Any other 255, such as a connection timeout, is passed on as before, and when the retry also fails the caller gets the retry's error, so an unreachable host still says why. The other multiplexing diagnostics (`muxclient: master hello exchange failed`, `Control socket connect(`, `mux_client_request_session: session request failed`) are not retried, because ssh falls back to a direct connection by itself after them and the command may already have run. `mux_client_request_session: read from master failed` is not retried either, because the master may have started the command before it died. The cause is the size of one request: on macOS a mux client passes stdin, stdout, and stderr to the master with `sendmsg` and `SCM_RIGHTS` right after it writes the request, an AF_UNIX stream socket buffers 8192 bytes there, and XNU takes every byte that the master has not read yet off the sender's room, so a request that fills the buffer to within 16 bytes (the same just under each multiple of 8192) leaves no room for the descriptor and fails with `Message too long`, whatever the state of the master. The shared preferences push and the clone refresh script are the two requests that are 8 KB. `-O exit` would not help, because the next request of that size fails the same way, and it would end every session on that master. A herdr failure message never shows the command line or a worker token. A herdr call that fails with `server_not_running` starts the server detached and repeats once (`host.ts`); a `pane_not_found` during a lane's foreground check means the pane vanished after listing. That check leaves the lane unread; only a fresh observation can confirm absence and start a replacement. `e2e/extension/herdr-restart.test.ts` covers both.
- A command on another host runs through `routed` (`@fleet/protocol/route`), the one function that every caller uses to put a command behind a transport: `host.ts` and `cardd`'s checks of a clone and a pull request. It wraps the command in a short `sh` that appends the tool directories (`DEFAULT_TOOL_DIRS` in `route.ts`, listed in docs/setup.md under Prerequisites) to `PATH` when they exist and are not there, and then `exec`s the command. A non-interactive SSH session on macOS has no `/opt/homebrew/bin`, so `zstd`, `gh`, and `bws` were missing from it while they passed the prerequisite check in an interactive shell: on 2026-11-05 `close` on maverick from a mate on p620 failed with `zstd is required to archive`. A directory that is already in `PATH` keeps its place and the new ones go last, so a tool that was found before is found in the same place, and a host without these directories runs the command with the `PATH` it had. `FLEET_TOOL_DIRS` (colon separated) replaces the list. `e2e/support/launchd-transport.ts` runs a command with a bare `PATH` like launchd's, and `command-path.test.ts` dispatches, closes, and archives through it.
- A worker's `-e` is the extension of the host that it starts on, not of the mate that starts it (`extension-path.ts`). On the mate's own host it is the mate's own copy. On another host it is the extension in `roots.<host>` of the lane (`~/.fleet/app` if unset), and the dispatch refuses with the root it looked in when that checkout has none. Before this, the path of the mate's checkout went to every host. A second mate on p620 (`~/.fleet/app.worktrees/lane-yang-auto`) started c-1035 on maverick with a path that maverick does not have, and Pi exits with status 1 about a second after it starts when its `-e` file is missing. herdr counts the agent as started because Pi was in the pane for that second, so `restart_card` said it started the worker three times, and the pane that held Pi's message was closed by the next restart. Now a start that fails with no Pi in the pane throws the last 20 lines of the pane, and a Pi that is in the pane at first and gone within 3 s sends the mate a `[fleet] launch:` message with the same lines, after the tool has returned, so a healthy start waits for nothing. Both hide the worker token and the `--fleet-bws` value, and leave the pane open. Check the host's herdr log (`~/.config/herdr/herdr-server.log`) for `agent changed ... agent=None` a second after `agent.start`.
- The attempt's worktree is the one at `<clone>.worktrees/<session>`. The worker may switch to its own branch, so the path is the key.
- `place.ts` creates a worker's workspace, tags it with its lane and card, and arranges the host. `arrange.ts` implements the [sidebar order and labels](setup.md#6-day-to-day). Herdr does not nest plain workspaces, so order and label make the tree. The order is a pure function of the workspace list, so it is the same after any restart: workspaces with no `lane` token first, then main's and each local mate's group, then workers with no local mate, sorted by lane and then card. The herdr CLI cannot move a workspace, so `arrange.ts` calls the socket API's `workspace.move_block`, once, only from the first workspace out of place. Ownership is a metadata token on the workspace (`lane`, `card`) because the host cannot ask `cardd`. A third token, `mate`, names the host where the lane's mate runs. `place.ts` writes it from the dispatching mate's host name, and `dispatch.ts` does so for every workspace it resolves for a worker (a new one, an existing one, and the one a replacement opens, but not the old one that a replacement is about to close), then arranges the host. `/updatefleet` rewrites it for every tagged worker with `mateHosts` in `lanes.ts`, which only decides what the sidebar shows. Placement discovery uses `status --placement --json`. For lane homes it checks for foreground Pi in the mate pane, not the lifecycle status that also counts busy shells. The caller is itself a running mate, and its host name is its own `FLEET_HOST`, or the hostname's first label. A local lane home reports its configured `host`, which names that lane's placement, so a co-located lane keeps the name its own dispatches write, and a lane with no configured host uses the hostname's first label. `/updatefleet` queries placement after all host checkouts have updated and before mate reloads. It rewrites placement only when exactly one running mate is observed for the lane. With no running mate or several, it leaves that lane's placement alone. If any host's placement cannot be read, it leaves placement alone for every lane. Starting, stopping, restarting, and recovering a lane still find its host by the first host whose status lists it (`hostOfLane`), as before. `tagWorkers` also adds the `card` token to a workspace that has a `lane` token and no card, from its worktree path, and keeps its lane. `tagWorker` clears the old `mate` and `away` tokens if a known replacement exceeds herdr's 80-character limit, and still writes ownership. Without a known replacement it leaves `mate` untouched. Placement keeps full configured host names. An unset name or the routing alias `local` falls back to the hostname's first label, and `local` is never a placement token. `fleet arrange` takes its identity from `--host`, `FLEET_HOST`, or the home containing the running `launch.ts`, in that order. With none of these it orders the sidebar without changing hints. `arrangeOn` passes the destination's configured name to remote arrange. Start and restart use the selected lane home's identity for their arrange, without changing routing. Arrange derives `away` from `mate` and the workspace grouping. A worker shows `↗ mate on <host>` only when its mate's workspace is absent here, the stored host is different, and the hint fits the value limit. Arrange clears only the derived hint, so it can return when a local mate workspace closes. A workspace with no token follows the workspace above it when its label starts with `└ `. A lane restart tags those followers before it closes the mate's workspace, so they keep their mate when it comes back at the end. `/updatefleet` tags the rest from the board by matching any pane's worktree, and never tags or corrects a workspace titled `1stmate` or `2ndmate-<lane>`, so a worker worktree opened in a mate's second tab cannot give the mate an owner. A failed arrange after a start or a dispatch only leaves the sidebar as it was. `/updatefleet` arranges every host once more at the end, through the same `arrangeOn`, even when no mate started there, and names each host that failed.

### Prompt cache policy

- `cache-policy.ts` sets prompt cache retention by role, when the extension starts a session. Every mate (main and each second mate) asks for one-hour retention, `long`. Every worker asks for the five-minute default, `short`. Fold mode keeps a mate's prefix stable (see setup.md), so a one-hour write is paid once and read for an hour, and the fold at cache expiry (`foldOnCacheExpiry`) refreshes the prefix only when it is cold. An earlier policy gave mates `short` because conversation memory rebuilt most of the prompt every turn. The role map covers a mate started by hand, by `fleet up`, and by a restart, and a worker started by `dispatch`, with no environment variable and no personal setting.
- `cache-ttl.ts` splits a mate's system prompt in two at an invisible marker that `index.ts` places at the end of Pi's system prompt: the stable block (base prompt, project context with `AGENTS.md`, skills) and the mutable tail (lane plan, charter, standing rules, in that order). Each gets its own breakpoint, so an edit to `captain.md`, `learnings.md`, `charter.md` or `captain-shared.md` rewrites only the tail, and the first breakpoint covers the tools before it. A mate with no tail keeps one block and one breakpoint. OptChat replaces the provider's marks on the view and the end of the request with bare ones, which default to five minutes, so every surviving message mark is set to one hour here, at the final payload boundary. Anthropic allows four breakpoints, so when OptChat's view marks leave no room, the oldest message mark is dropped. It checks the payload shape, not the model api, so it also works behind a routed model. The expiry fold reads the cache lifetime of the physical model that answered last, not the routed model. Workers do not load it.
- Which providers honor `long`: Anthropic messages (`claude` accounts, and `vertex-claude` once it sets `supportsLongCacheRetention`) writes `ttl: "1h"`. `openai-codex` (`openai-codex-responses`) has no retention parameter and ignores it. `xai` (`openai-responses`) and `baseten` (`openai-completions`) have `supportsLongCacheRetention: false` in their model data, so Pi sends no long retention for them. A provider that ignores `long` keeps its own default lifetime, and its model has no `promptCache` lifetime, so the fold at cache expiry stays off for it.
- Pi has no setting for retention. `cacheRetention` is a request option that Pi's agent never sets, except `none` for compaction. The providers read `PI_CACHE_RETENTION` on each request, so the extension sets it in its own process. Each role sets its value and does not unset the variable, so a `long` that a session inherits from its launcher does not leak into it. A provider's own `env` in `auth.json` would still win over the process variable. The fleet does not write it.
- Warming is not managed per role, and the per-role policy for it is not implemented. `cacheWarming` is a global-only Pi setting, in `~/.pi/agent/settings.json`. Pi reads no project file, flag, or environment variable for it, and gives an extension no way to set it. The `cache_warming_decision` event can only stop a refresh that Pi already scheduled, so it cannot turn warming on. Every session follows the global setting. The wanted policy is idle warming for mates and streaming warming for workers. It needs a per-process way to set `cacheWarming` in Pi.

### Cache break log

- `cache-breaks.ts` runs in every fleet Pi (main, second mates, workers). On each answered request it compares the usage with the request before it in the same process. The first request is ignored, and so is a request that failed or was aborted.
- The rule: a break is a request whose `cacheRead` is below half of the prior request's `cacheRead + cacheWrite`, when that prior total was at least 1024 tokens (the smallest prefix Anthropic caches). A healthy request reads back the whole prior prefix and adds to it, so reading under half means the prefix broke. Half leaves room for a view that moves its marks, and the 1024 floor skips models that do not cache.
- The cause is the first that matches: `model` (provider or model id differs from the prior request), `compaction` (a `session_compact` event since the prior request), `system-prompt` (the hash of the stable system text changed), `tools` (the hash of the tool definitions changed), `idle` (the gap between the prior answer and this request is over the model's short cache lifetime, `promptCache.short`, else five minutes), else `other`. The system hash covers the text up to the mutable tail marker, or up to the first block with a breakpoint once `cache-ttl.ts` has split it (the stable head), so a change in the lane plan or charter tail, which sits after the one-hour breakpoint, is not blamed. The idle rule uses the short lifetime because the view breakpoint is the first to expire.
- Each break is a custom entry, `fleet-cache-break`, in the session file, so it is durable, sits with the session it belongs to, and needs no new path. The board or `jq` can read it. It holds the time, cause, provider, model, prior provider and model, `cacheRead`, prior cached tokens, idle seconds, cache lifetime, the system and tool hashes (12 hex digits), tool count, and the running count. It holds no prompt text, secrets, or tokens.
- The status line shows a third footer line with the cache state, never a break count. `cache warm 4m` is the time left, from the last answered request plus the cache lifetime. `cache cold` means it expired. The line never shows break history or causes: those are only in the recorded break entries. A request that read or wrote cache leaves it warm. A break whose response read and wrote nothing shows `cache cold`. A response with no cache use and no break shows no warmth. The lifetime is the `promptCache` entry of the model that answered last (`long` when `PI_CACHE_RETENTION` is `long`, else `short`), so a routed model uses the physical one. A model with no lifetime shows no line, and so does a new, resumed or switched session (`session_start`) until its first request. The line refreshes on an unref'd timer every 30 seconds, and at the expiry moment while warm, so it keeps moving while Pi is idle. The timer stops at `session_shutdown`. Times under a minute show as `<1m`.
- `e2e/extension/cache-breaks.test.ts` drives a tool change, a model switch, a system prompt change, and idle expiry (the fake cache lifetime is 12 seconds), and reads the entries and the rendered status line. It moves the controlled clock (`e2e/support/clock.ts`) past the lifetime for the warm-to-cold change instead of waiting.
- Idle warming has a second limit. Pi stops it after a run in a session that holds a custom message, such as the `[fleet]` messages every mate gets, because it compares the transcript by object identity and Pi rebuilds custom messages when it refreshes the finalized context. `/session` then shows `Inactive (conversation context changed)`. A fix in Pi is needed before idle warming helps a mate.

### Worker context policy

- `context-policy.ts` limits a worker's context when the extension starts a session. The effective limit is `min(the model's own window, 500K)`, so the 500K is a cap and never raises a window. Compaction runs at 80% of the effective limit: 400K on a 1M or 500K model, 217.6K on a 272K model, 160K on a 200K model. A mate keeps Pi's own limits. No personal setting and no project file changes.
- Pi 1.3.0 has no flag or environment variable for this. Its settings are files, and `compaction.reserveTokens` is one fixed number subtracted from the window, so no value gives 80% across windows from 200K to 1M. A worker runs in a worktree of any project, so the fleet cannot write a project file either.
- Where the window comes from: under a pi-tiers virtual model Pi stores a virtual model with window 0 and checks the physical model that answers. Before each request, `prepareRequest` routes and calls `AgentSession._exceedsCompactionThreshold(route.model, projection)` with the routed model. After each response, `_checkCompaction` takes the window from `_modelForMessage(message)`, the physical model that produced the message. Both are the routed model, not the virtual one. `SettingsManager.getCompactionSettings` receives only the selected (virtual) model, so it cannot know the window itself.
- The patch point: the extension wraps four members in the worker's own process, like the Calm presentation patches. `_exceedsCompactionThreshold` and `_checkCompaction` set the window they work on for the synchronous part of the call. `getCompactionSettings` turns it into `reserveTokens = 20% of min(window, 500K)`. `_exceedsCompactionThreshold` and `_modelForMessage` hand Pi a model whose window is capped at 500K, so the threshold and the overflow check never see more than 500K. A window that is unknown (0) leaves Pi's own settings, which never raise a window.
- `compaction-policy.ts` sends every compaction to the fleet's compactor, for every role. Pi's one shared summary step, `AgentSession._runDefaultCompaction`, serves manual and automatic compaction (threshold and overflow), so the extension wraps it and swaps the model. `compaction-model.ts` picks it: `tier/compact`, except for a CNP session, which tries `vertex-claude/claude-haiku-5-5` first and then `google-vertex/gemini-3.8-flash`, so company content never leaves Vertex. The CNP chain is hard-coded, not routed through `tier/compact`: the fleet cannot see which model a tier chain picks, a tier chain edit could send company content outside Vertex, and the CNP checks (provider, `~/cnp`) can hold without `PI_TIERS_RULE=cnp`. A model is skipped when it is not registered. A session is CNP when its provider is `google-vertex`, when `PI_TIERS_RULE=cnp`, or when its folder is under `~/cnp`. If the chosen tier model is not registered, Pi keeps the session's own model. If neither CNP model is registered, the compaction fails with a message that names both, whatever the session's provider. The OptChat memory summaries (mates with memory) use the same choice in `vendor/optchat/firstmate/loader.ts`; `compactorModel` and `compactorProvider` in `config/optchat.json`, and the profile's `compactor`, no longer pick it. Pi's own compaction is cancelled by OptChat for a mate with memory, so those mates use only the memory path. Pi 1.3.0 has no compaction-model setting, so the wrapper is the smallest point that covers every path.
- A model switch in mid-session needs nothing extra: each request is routed again and checked against the model that will answer. A session at 170K that a tier moves from a 1M model to a 200K model compacts before that request, because 170K is over the 160K of the 200K model. A session that goes the other way keeps its context until the larger model's 80%.
- A Pi that lacks one of the members makes the patch print `Fleet context limit: unavailable` and the worker keeps Pi's own limit. `e2e/extension/context-policy.test.ts` pins the behavior on the Pi version in [e2e/package.json](../e2e/package.json), so a Pi bump that moves a member fails it.
- The footer's percentage still counts against the real window.

### Jobs

- `jobs.ts`: `cardd` records a job first. The wrapper posts the result, which arrives as a fleet entry, also after a Pi restart. Nothing runs a job again. A running job is a tracked wait.
- `stop_job` stops one named job of the calling worker. `cardd` decides ownership: `job.stop` finds the job only among the caller's attempt's jobs, so a foreign or missing job is refused before anything is signalled, and a finished one answers "not running". Only after that does the extension send ctrl+c to the exact pane it dispatched the command to, once that pane is confirmed to still be in the exact tab it created for the job; it finds no tab or pane by name or position. A legacy job's pane counts only after herdr acknowledged the `pane run` request, so a legacy command that started after a lost pane-run reply cannot be stopped by `stop_job` and must be stopped by hand on its owning host. The `job.stop` receipt has a five-second deadline, and an unknown outcome signals nothing. The wrapper stops its own process group and posts the usual `exited 130` result, so the result is reported the way an interrupt always was. The extension never signals by name or pattern, and `prompts/worker.md` forbids it for a worker.
- `shims.ts` and `packages/extension/shims/` stop `pkill` and `killall` for every session. Every session on a host runs as one account, so such a command signals every matching process on the host. The prompt rule alone did not hold: on 2026-10-24 an agent that had it in its prompt ran `pkill -f "node --test"` and ended another card's full end-to-end run. The extension puts that folder first in `PATH` when it loads, so the two refusing scripts win over the real commands, and `job.ts` does the same for `run_long`, so the shell itself decides what is a command: `grep pkill`, `command -v pkill`, and text that mentions the name still run. `sudo` and an absolute path bypass it by design. A shell builtin `kill` cannot be shimmed, so `guard.ts` also refuses a `kill` fed by `pgrep`, `pidof`, or `ps` with a regular expression. That is a heuristic, because guards catch ordinary agent mistakes and are not a security boundary (spec section 12.4). `kill <pid>` still runs.
- `job.ts` is the wrapper. It reads its job from a private file, so the token never appears in shell history. It keeps the last lines of output, whole across split reads and split characters. It sends heartbeats until the result is taken. A closed tab can take the wrapper down soon after its hangup, so it reports as soon as the command ends or a moment passes, and `cardd` keeps only the first result. A 401 means the attempt ended and nobody waits. The job row is `abandoned` by then, not left `running`.

### Recovery

- `restart.ts` is the parent's `restart_card` tool. It calls `card.restart` and, for `replace`, `replaceWorker` in `dispatch.ts`. With an incident it is the recovery of that incident, with its generation fence. Without one it restarts the same card's worker or lane mate on the same conversation, with an hourly cap of 3 per card. A repeat of a live request does not launch again. When the plan says `reconnect` (the card is paused, finished, or waiting, and the worker's process was disconnected), it starts the new process and posts no comment, because the comment that an ordinary restart posts would resume the worker. An ordinary worker restart asks `card.restart.notice` to post the comment after the old process stops and before the replacement starts. Cardd checks the current status and posts in the same transaction. It writes nothing if the card is not working, so a blocked or with-mate card stays with its mate. Before delivery, cardd rechecks that the request is live and the card is still working. A newer refundable request suppresses the older notice. A refund sends newly eligible queued notices on the existing connection. It does not replay an acknowledged notice, even if a refundable successor suppressed its replay on reconnect when the notice was missing from the session file. Ordinary reconnect without that suppression can replay an acknowledged entry missing from the file. A newer request with an advanced worker generation or an incident replacement retires older notices. When a card transition makes a restart notice ineligible, cardd retires it in the same transaction, without waiting for a delivery check. Once retired, it cannot replay after the card resumes. Retirement is stored separately from the worker's receipt and does not delete the thread entry or refund any request. Posted after the start, it raced the job results that closing the old workspace sends, and the worker could take a turn on those first. `dispatch` creates its own card and only starts new work. A repeated call finds the card by its name and the attempt that already started. A replacement finds the same attempt through a resumed `attempt.begin`, so no new attempt, branch, or token appears. It finds the pane's `pi` process by the pane's own process list, signals that pid with TERM and then KILL, and starts the new process only when the pane's shell is idle again. It never signals by name or pattern. If the old process cannot be confirmed stopped, nothing is started. The new process opens the same session id with the same arguments, so the conversation, the worktree, and its dirty files are the ones it had. A second mate is replaced through the existing `lane restart` of main. Repeating a recorded replacement key neither stops a process nor attempts a new launch. The result confirms only the recorded key and the no-op, not whether a process is running. A worker replacement issues one start command, without Herdr or transport replay, and waits for its readiness result even if Pi is already visible. If readiness fails and the pane is inspectable, the request remains counted unless the start was definitively refused. An idle pane and unchanged generation cannot distinguish a process that exited before hello from one that never spawned. Each worker replacement launches with its own process id (`--fleet-process`), which the new process announces in its hello and cardd stores as the session's process, so `attempt.resume` shows it. Only a structured Herdr readiness timeout (`timeout` from `agent start`) can be reported as a started replacement, and only when cardd's stored process equals the id of that launch. A generation increase, a hello from another process, a definitive refusal, or a pane observation is not evidence, and those cases stay failures and stay counted. When the evidence holds, the tool result reports the started replacement and the scrubbed Herdr timeout separately, never claims readiness succeeded, and is not refunded or relaunched. A failure of the final containment then reports both its own error and the Herdr timeout. If the replacement exits afterwards, the launch report says it connected to Fleet. If the host connection drops during worker start and the pane cannot be inspected, a launch that did not register a newer generation can still be refunded even if it ran, allowing an extra attempt. If the mate loses the plan response after cardd writes the request, no launch happens and no failure is reported. That existing request still counts for the hour, and the key repeats without launching. An error after confirmed start, including final containment, and any error from restarting a second mate still counts.
- Errors that happen before the extension loads, such as a Pi that exits at startup, are seen only by the watchdog, as a worker that never connected. The pane's output is not captured, so such an incident has no cause text and is classed `unknown`.
- `e2e/extension/runtime-failure.test.ts` drives real Pi workers and mates against a real `cardd` and moves the controlled clock. `e2e/extension/recovery.test.ts` replaces real herdr panes. They kill only the pids they started.

### Complaints

- A complaint is one sentence an agent records when the fleet asks it "Did anything about the system annoy you?". It is feedback only. Nothing reads it as authority to change infrastructure, bypass a check, or alter a rule, and the tool descriptions say so.
- The worker role context asks the question once per run before the final `report` of `done`, `blocked`, or `failed`: if yes, call `complain`, wait for its result, then report. If no, report without acknowledging the question. There is no extra model call, post-report steer, or close coordination. Routine reports, recovery checks, and waits do not ask it. `needs-decision` does not, because the worker continues after the answer.
- `complaints.ts` sends a mate one hidden steer after its own `close` ended a card, through `onClosed`. A close that only warned about unlanded work, and the automatic close of a merged report, send nothing: the second is the fleet closing the card, not the mate. The flag resets at `agent_settled`, so a run is asked once, and recording a complaint never asks again.
- `complain` calls `cardd` with a 5 second deadline. When that fails, the tool warns once (a pane notification, or stderr without a UI), tells the agent to carry on, and drops the sentence. Nothing retries, so an unreachable `cardd` cannot hold a finish.
- `cardd` keeps the `complaints` table. Time, session, role, lane, card, and project are plain values with no foreign key, because a lane's removal deletes its cards and sessions and the complaint has to stay. A worker's complaint always names its session's card. A mate may name a card, and it counts only when the card exists and is visible to that lane. Unknown and invisible cards both leave card and project empty. Main can name any lane's card. The text passes the protocol schema (not blank, at most 500 characters) and `sanitize`, the incident redaction.
- `complaints` is a mate-only operation and tool. Main lists every lane's, and a second mate its own lane's, newest first. There is no board view.

### Prerequisites

- Every prerequisite of a host is one table in `prerequisites.ts`: the tools with their floors and fixes, plus the conversation-memory profile of each home. `fleet up`, `fleet restart`, `fleet update`, use it, so there is one check and one set of messages. The profile check looks for both files the memory reads at start, `AGENTS.md` and `config.json`, because a missing one stops the memory and crash-loops the mate. `gh-login.ts` decides the gh login line from `gh auth status`, which exits 1 for every failure. Only "not logged into any" text, an empty `--json hosts` result, a rejected refresh token, or a 401 from GitHub says `gh is not logged in`. A timeout, a network error, a signal, a spawn error, or any other exit prints `warning: could not check gh login on <host>: <reason>` on stderr and does not refuse, with token-shaped text hidden. `fleet up --maintenance` skips the login check. `FLEET_PROBE_TIMEOUT_MS` sets the probe timeout.

### Review pages

- There is no review tool. A worker opens a Lavish page with `lavish-axi`, reports `needs-decision` with a review key and the page link, then polls with `run_long` (at most 2 hours for each job). The report opens a hold with the mate, who escalates it for the captain's feedback on the page. A poll that times out is started again, and Lavish keeps feedback sent between polls until a poll takes it. The poll result is an ordinary job result for the worker. For an unbound review the hold stays open while the poll is started again, and the mate resolves it when the captain ends the review. For a review the mate bound with `hold(review=...)`, Fleet launches its own Lavish round and records the captain's Send & End as below; the worker stops its old poll and reads the Fleet inbox feedback instead.
- `reviews.ts` checks for an open hold on the card when `job.start` recognises a Lavish poll. It matches `lavish-axi poll`, `lavish-axi@<version> poll`, `npx lavish-axi poll`, `npx --yes lavish-axi poll`, and `node <path>/lavish-axi/dist/cli.mjs poll`. The matcher accepts leading variable assignments and quoted words. It splits on unquoted, unescaped `|`, `;`, `&&`, and `||`, stops at a `#` that starts a word, and recognises forms such as `lavish-axi poll>poll.log`. It does not interpret Bash or look inside wrapper scripts. See `e2e/cardd/review-wait.test.ts` for supported command shapes.
- If nothing holds the card, the refusal asks for a `needs-decision` report with a new review key and the page link. A `working` report is not a substitute. The check does not tie the job to a particular hold or recheck it once the job is running. For a new review round, report `needs-decision` with a new key before polling.
- A second mate or main may bind a review-only hold to the stock Lavish link named by every open worker decision, and main's escalation of a bound hold carries the binding. The hold captures those report IDs. New or repeated requests remove the board answer, Later, and review link until main presents the current requests. `review=false` re-presents requests as a board-only decision, only for a hold that is already review-bound or whose requests include a Lavish link. Later preserves the binding and prevents answering until due. Merge and unlanded-work holds cannot use Send & End.
- Cardd imports the portable export from the exact configured source mapping (`CARDD_REVIEW_ORIGINS`, whitespace-separated `reported-origin=upstream-origin`). It launches the stock Lavish 0.1.97 from cardd's locked dependencies on loopback with fresh private state and a new artifact file for each rendered round. It does not use the worker or host CLI for this copy. Fleet never reopens that session. Direct end or reopen of the worker's source link does not change the Fleet copy. Unexportable artifacts and unavailable sessions leave the explicit board answer available.
- `CARDD_REVIEW_ARTIFACT_ORIGIN` is a separate HTTPS hostname routed to cardd with its Host preserved. It serves only the sandboxed artifact, not the stock control API or the authenticated board. Cardd does not forward credentials or follow redirects. Use the same Access application for both hostnames so the edge supplies its signed owner assertion for the artifact and SDK as well as the board. The browser must allow the authenticated iframe requests; the board answer is still available if it does not. Fleet keeps its own page because stock chrome cannot be framed and a proxy for its control channel would be a second trust boundary. Iframe messages queue local drafts only, and editing freezes while a send is in flight (late annotations are shown as undelivered, not dropped); rejected drafts must be explicitly discarded before sending. The form binds the Fleet-owned session and round, accepts an empty queue, and records one `review-feedback` entry for each open key (delivered once to the worker, and clearing the key through the base `resolves` rule) only after stock Lavish accepts the terminal request and the hold still matches. Direct stock actions and worker reports do not record Fleet answers. An orderly shutdown stops every owned session and removes its snapshot. A hard restart invalidates already-rendered forms but can leave an orphaned loopback process and temp snapshot until the host is cleaned; Fleet keeps no durable ownership record for them. Someone with the access of cardd's OS account can reach its loopback process, private files, or database; this is not a same-UID security boundary.
- The fixture in `e2e/board/review-completion.test.ts` drives a real Pi worker through the extension: it observes the Fleet-owned notice to stop the source poll and the completion message with the annotation's target. It also covers an unauthenticated artifact read (403), a retired artifact (404), a plain edit, worker and direct upstream submissions, stale and duplicate submissions with the replacement hold and recorded-answer count read back, a card that closes after Send & End alone, and the explicit board fallback. Residuals: a failed submission leaves the draft in its tab but a reload or restart does not restore it; annotations that arrive while a send is in flight are shown as undelivered, not delivered; a hard cardd restart can orphan a loopback Lavish process and its temp snapshot; and an upstream success whose Fleet round changes before settlement is answered on the board.

### Closing on the host

`closing.ts` runs close in this order: stop every writer (close the worker's workspace, which ends Pi and its job tabs), stop every process whose working directory or command line names the worktree (`stop-procs.sh`: TERM, a bounded wait, then KILL; it matches whole path components and spares fleet's own processes and the host-shared no-mistakes daemons, see Process containment), archive and verify all unlanded work, remove the worktree, and record the close. Ending Pi this way, or any exit by SIGTERM or SIGHUP, is not a pane stop (see `worker.ts` under Extension). Close's output lists each stopped process with its pid, short command, and TERM or KILL, names each shared no-mistakes daemon that it moved out of the worker's processes and kept (see Process containment), and says nothing when none ran. Each step finds its own result first, so a rerun converges. Closes of one card do not run together within one Pi process: `close` keeps one running close for each card. A second call for the same card that asks for no more than the running one (the same `landed` and `next`, and `confirm` only when the running one has it) returns the running close's result, so a duplicate finds the card closed once. Any other call waits for the running one and then runs on its own, so it reads the card as the first left it, usually already Done. The automatic close on a merged report asks for `confirm`, so it joins only a running close that has it, and otherwise waits and finds the card already Done. That single flight stops at the process: main and a second mate can both close a card of the second mate's lane, each in its own Pi, and `close.begin` only reads the plan, so cardd does not reserve the card. Such closes can overlap. The sweep of one spares the helpers of the other by the mark (see Process containment), and each step finds its own result first, but a step can still fail on the other's half-done work, and the second `close.finish` fails with `is already done`. When a close fails after `close.begin` and `close.begin` now says the card is Done or Dropped, it returns `c-N was closed by another close at the same time, so there is nothing left to do.` instead of the error. Any other failure is rethrown, and a close of a card that was already closed before it began still fails with `is already done`. A worker may have moved its worktree to its own branch, which goes too, after the archive. An unreachable host of an attempt that no longer runs cannot be asked, and its work stays in place. A commit has landed when it is on the base branch or on `origin/<base>`, because dispatch branches from origin's base, which can be ahead of the clone's. `ORIGIN_BASE_IF_FETCHED` names that ref when it exists, and `archive.sh` does the same. `UNLANDED_COUNTS_SCRIPT` prints the commits not landed and the changed or untracked files: the worktree decides while it exists, and its branch after. `DELETE_ARCHIVED_BRANCH_SCRIPT` deletes the task branch once its work is archived or landed. It tolerates only a missing branch, and is safe to rerun. A local-only card lands first, as Firstmate's `fm-merge-local.sh` does: `LAND_LOCALLY_SCRIPT` fast-forwards the clone's base branch to the newest attempt's branch, only when the clone is on its base branch and clean and the branch is a fast-forward, and never pushes. Any uncommitted file in a worktree refuses it first, so a landing never leaves work behind. A rerun after a landing is a no-op fast-forward. After recording the close, it refreshes the clones that `close.begin` lists (see Clones). It lists none for a local-only card, and main's first refresh skips local-only projects, as Firstmate's fleet sync does, because their local base branch is ahead of origin by design. A host that just failed to answer is already named in the outcome, so it is not waited for again.

Close has a deadline, and no step of it can hang the mate's turn. On 2026-11-20 a close on a Mac with a load average near 900 never returned: every `ps` took 20 to 40 seconds, `stop-procs.sh` runs `ps` for each candidate process and up to twice more for each ancestor of it (the mark check on a host with no `/proc`), and the only limit was 600 seconds for each call, which stopped only the `sh` and left the `ps` that it was waiting on. `onHelper` now runs its command in its own process group (`spawnDetached`, so the end-to-end launcher registers the group), and at its timeout it kills the whole group, destroys the pipes so that the call settles at once, and fails with `TimedOut`. `onHost` is unchanged. In `closing.ts`, `stepsOf` splits the steps in two. The scans and read-only steps (`check what is unlanded`, and `stop the worker's processes`, which is `stop-procs.sh` and `releaseAll`) get the smaller of their own cap and the time left in the close, and at that limit their whole process group is killed at once. The scans are capped at `SCAN_TIMEOUT_MS` in `host.ts` (180 seconds, `FLEET_SCAN_TIMEOUT_MS`, which restart and recovery use too through `releaseAll`), and `releaseAll` spends one budget across its backend detection and its helper. The whole close is capped at `FLEET_CLOSE_DEADLINE_MS` (600 seconds from the end of `close.begin`). A scan does not start once nothing is left. The destructive steps (`land the branch locally`, `archive unlanded work`, `remove the worktree`, `delete the task branch`) are never cut short by the close's deadline: once it has passed they refuse to start, and a step that has started runs under its own 600 second cap. At that cap its process group gets SIGTERM, then SIGKILL after a 2 second grace (`grace` in the transport's `Limits`), so git and `archive.sh` can release their locks and temp directories. `archive.sh` copies the finished archive into the archive directory under a temporary name, verifies it there, and renames it into place, so `<session>.tar.zst` never exists half written, and it removes a leftover temporary name when it runs again. A step that times out or refuses to start fails the close with `c-N was not closed. Step "<name>" for <session> on <host> did not finish within N s` (or `ran past close's overall limit of N s`, or `did not start because close ran past its overall limit of N s`), followed by the steps not done and `c-N stays open`. Nothing after that step runs, so a stalled scan archives and removes nothing and records no close, and an archive that finishes after the deadline leaves the worktree and the branch in place. The worker's workspace is already closed by then and the scan may be half done, and a second close converges because each step finds its own result first. Over ssh only the local ssh client's group is stopped: the remote scan keeps running until it finishes or its output pipe breaks, and a second close can start another scan next to it. A remote-side watchdog is a follow-up. Any timeout of `onHost` or `onHelper` (Node's `killed`) surfaces as `TimedOut`. The two `herdr` calls of `retire` and the one of `unlandedCounts` keep their own 120 second limit and are not counted in the deadline, so a close can run one of them past it. The cost of `stop-procs.sh` is still its `ps` for each process on a Mac, and on Linux its `readlink` fork for each entry of `/proc`: a normal run takes 19 seconds on a host with 2800 processes at load 70. This change bounds that cost and does not reduce it, so the scan cap stays far above it. `e2e/extension/close-bounded.test.ts` puts a `ps` on the mate's `PATH` that sleeps while a flag file exists, and closes a worker through it twice: once with a scan cap of 90 seconds, far above a normal run on that host, and once with an overall limit of 15 seconds. Each close fails with the step named and kills the sleeping `ps`, the card stays open with its worktree in place, and after the first the close that follows with the flag gone finishes. A third test puts a `zstd` on the `PATH` that blocks while its flag exists, lets the 45 second deadline pass during the archive, and then releases it: the archive finishes whole, `remove the worktree` refuses to start, the worktree and the branch stay, and the next close finishes.

### Scratch space

[setup.md](setup.md#scratch-space-and-the-disk-alarm) owns what the folders are and when they go. Inside:

- `scratch.ts` owns the host layout and compile-cache tidy. Dispatch sends its loaded `OPEN_SCRATCH_SCRIPT` over the host transport. The updated script makes the original folder without moving an existing closed path; an unreloaded mate can still send the old script that reopens a legacy closed folder. `fleet scratch --open` uses the script from the host CLI's own checkout.
- The variables go in at launch, as `--env` on `herdr workspace create`, because the compile cache is read when Node starts. By the time the extension loads, Pi has already enabled it in `/tmp`, and `module.enableCompileCache()` cannot move a cache that is already on. A second path from inside the extension would also leave Pi's own `os.tmpdir()` users, such as the extension loader's cache (80 files for each worker), on the old value. A herdr tab does not inherit the workspace's variables (measured with herdr 0.9.5), so `jobs.ts` copies the three variables that the fleet set into every `run_long` tab. It copies nothing for a worker that was not started with `FLEET_SCRATCH`.
- Updated mates leave scratch, including `TMPDIR` and legacy paths, in place on close. An unreloaded mate can still send the old cleanup even to an updated host. The scheduled tidy runs the target host's CLI, just as a manual tidy does; an old CLI can still delete legacy closed scratch. The updated tidy touches only the Node compile cache. Fleet-wide preservation requires both updated host tools and reloaded mates; a current checkout alone does not prove a mate reloaded. The separate manual `fleet scratch --move` command still moves legacy `/tmp/fleet-c-<N>` on request.

### Job registration and cutover

`job.prepare` reserves a job for its attempt with a unique launch ID. After an unreadable reply or a database error marked retryable by cardd, the launcher retries with the same ID and payload within the existing attempt limit. Only that attempt can recover the original reservation. A replay of an expired, registered, or ended reservation returns its disposition, not a new launch receipt. A startup fence names the launch ID so it can overtake the original receipt without opening a tab. The launcher applies a fence only when it is a complete terminal result (a positive job number, the fence flag, a launch ID, an integer exit code, and no loss or revival flag) and its job and launch ID match a launch it prepared. An early fence waits, kept by job and launch, for the prepare receipt to bind them. Registration evidence retires its fence eligibility: a job list row, an exact read, a loss or revival notice, a running stop receipt, or any result for the job. A loss notice alone never clears the wait. Job numbers in cardd replies must be positive safe integers, or the reply is rejected before any launch or wait changes. Heartbeat intervals must fit a timer (at most 2147483647 ms) in the receipt and in the wrapper input. A job result notice is applied only as exactly one of an exit with an integer code, a loss, or a revival, with `commandNotStarted` only on an exit. Anything else is reported and changes nothing. The prepare and register handshakes and the cutover command refuse redirects of their private POSTs, and the cutover command accepts only an HTTP 200 reply. Those private replies must be a success (`ok` and `value`) or a failure (`ok`, `error`, optional `retryable`); a reply that carries the other outcome's fields is rejected, and unrelated additive fields are ignored; legacy heartbeat and result posts and `fleet wake` keep their transport. An incomplete or unbound fence changes no wait, file, or tab, and an incomplete one is reported. A `job.stop` receipt is either running or not running (with optional cancellation), never both markers, and any other marker is rejected. A contradictory receipt is rejected as unreadable before the worker changes any state or signals a tab. The same holds for a job-related websocket reply that is both a success and a failure (`error` on a success, `value` on a failure): the worker ignores it before any local effect. The ID is in the wrapper's file argument and is not a credential. `job.register` pins the first wrapper PID for the job, attempt, and launch ID. The same PID can retry after a lost reply; a different PID cannot take the reservation. The wrapper sends heartbeats while waiting for registration. Cardd ignores them until the wrapper PID is pinned, and the wrapper only invokes Bash after parsing a positive receipt. `stop_job` cancels an owned reservation if registration has not won the transaction. Once registered, the wrapper receives the usual pane interrupt, even while it is waiting for its registration reply. The launcher retains the exact tab ID across job-list reads so a same-named tab cannot receive that interrupt instead. `stop_job` signals only the exact pane that this worker process dispatched the command to, and only while that pane is still in the exact tab it recorded for the job. A modern job needs its registered wrapper, and a legacy job needs herdr's acknowledgment of the `pane run` request: an attempt alone is not enough, and a lost acknowledgment leaves a running legacy command that must be stopped by hand on its owning host. A blank tab or pane ID in the tab-create receipt fails the launch before any `pane run` request, and so does a root pane that a fresh pane list does not place in the created tab (a contradictory pair is never owned, dispatched to, or closed). The startup-failure `job.finish` write and the legacy fallback `job.start` receipt each have a five-second deadline, are never retried, and leave the durable startup fence as cleanup authority when their outcome is unknown. Pre-registration cleanup stays scoped to the tab. A tab name, a legacy job row, or a unique label match is never proof of ownership, so a legacy or registered job whose launching worker was reloaded or replaced, a launch whose tab receipt carried no tab ID (the launch fails before dispatch), a launch whose tab creation failed, and a legacy launch whose start receipt was lost all answer that nothing was signalled, with the job left to finish, to be stopped by hand, or to be reported lost by the detector. A stop that arrives while the launch is still creating its tab or before dispatch is attempted also signals nothing. A wrapper result that says Bash never started still reaches the worker, but it does not count as card movement or make the next real run a repeat. After dispatch is attempted, the launcher keeps the reservation pending across job-list reads and reconnects until registration or a result is confirmed. Job lists only add running jobs, and a missing row never ends a wait. A job exit ends its wait and reaches the worker without a list refresh. A loss or revival notice never changes the wait by itself, because after a reload an older notice can be replayed after a newer outcome was acknowledged. The worker asks cardd for the named job with `job.running`, scoped to its own attempt, and applies the answer only if no newer result for that job arrived meanwhile. A failed, timed-out, unreadable, or unsupported answer (old cardd) leaves the known wait as it is, and the worker retries that exact read on each reconnect sync until it gets an answer or a newer result for the job arrives. A negative answer ends the wait but keeps the pending dispatch's launch, input file, and tab, so a durable startup fence that arrives later still closes the exact tab. Delivery of the notice never waits for that read. A successful pane reply cannot report a launch as started after its startup fence arrived. Cardd rejects first registration more than 30 seconds after prepare and uses its periodic check to finish still-unregistered reservations with a durable startup error. A failed write leaves the reservation for a later check. A confirmed pre-registration result lets the launcher release the exact tab created for that launch. It tries that tab ID up to three times and reports a failure if none succeeds. An ambiguous pane reply never retries dispatch, closes the tab, or overwrites a registered job's result. A modern launch keeps its launch ID, wrapper input file, and exact tab only in the worker's memory, with no owner record on disk. If the worker is replaced before cardd's startup fence is processed, the replacement ignores the fence and may leave either or both of the token-bearing input file and the tab behind, for example when the wrapper never ran, or when the wrapper removed its own input or closed its own tab after a refused registration. Each cleanup failure in the same worker can independently leave its own artifact: a failed input removal can leave the input file, and exhausted tab-close attempts can leave the tab, and both can happen together. Cleanup is independent, so one failure does not stop the other. Whatever is left is removed by hand. No recovery mechanism exists for it. Cardd refuses registration for that reservation, so its command cannot run.

The legacy `job.start` operation and old wrapper file shape still work until main seals legacy admission. The database rejects legacy inserts after the seal in the same transaction that would admit the job. A cutover status read is ready only when that seal exists, no legacy job is recorded as running, and every legacy job has an operator confirmation that its entire process tree can no longer run. A job result is not proof of process exit. A job that comes back to running invalidates its stop confirmation. The silence detector handles only legacy jobs. A registered job is lost only when its wrapper process is confirmed gone on its attempt's host, by the launch ID in the process's command line (see `job-presence.ts` under the timed check), so a worker or cardd that predates registration needs no change to keep a live job running. A reservation without a wrapper PID is not a running command and cannot be reported lost. Card movement counts a registered job from its first registration (`registered_at`, set once, never moved by a replay or a heartbeat) and a legacy job from its creation. The same effective start orders same-label runs (reservation ID only breaks ties), both for repeat classification and for which later job supersedes a lost job's reminders. Until registration or a terminal outcome, the reservation still counts as an outstanding wait for pause advice, dated job holds, idle checks, and automatic stopped handoffs. [Job liveness cutover](setup.md#job-liveness-cutover) describes the operator steps.

### Process containment

`containment.ts` runs one shell script on the host: `lib.sh`, `service.sh`, one backend, then `main.sh`. On the systemd backend, only the pane's shell and Pi start the scope, as a delegated scope. `StartTransientUnit` fails the whole call when any listed pid has already exited, and a pane shell that keeps starting short-lived children leaves such pids in the list. The rest of the tree is attached with `AttachProcessesToUnit`, one pid at a time, and a pid that has exited is skipped. Writing the pids to the scope's `cgroup.procs` does not work: herdr usually runs in the login session's scope, and a user cannot move a process out of `session-N.scope` into the user manager's subtree, because their common ancestor, `user-<uid>.slice`, belongs to root. systemd moves the process on the user's behalf, but only into a delegated unit. systemd replies to `StartTransientUnit` once the start job is queued, before the scope's cgroup exists, so `await_cgroup` polls for the cgroup, at most 5 seconds. There is no event to wait for in a shell: the end of the job is a bus signal that must be subscribed before the call, and `busctl wait` needs systemd 257, while Ubuntu 24.04 ships 255. `e2e/extension/contain-churn.test.ts` covers the attach. It reaches the systemd backend only on a Linux host with a systemd user session, and it meets the permission limit only when the suite runs from a login session's scope, as an ssh shell or a herdr pane does, not from inside a user manager unit.

A `run_long` job runs in its own herdr tab, and that tab's shell is a child of the herdr server, not of the worker's shell. Without a step of its own, everything a job starts sits outside the worker's unit, so a server that the job detached and started from `/tmp` outlives `close` and `restart`: the unit does not hold it, and the cwd sweep of `stop-procs.sh` finds it only when its cwd or command line names the worktree. `Jobs.launch` therefore calls `joinContained` between creating the tab and running the wrapper: the `join` action of `contain/main.sh` moves the tab's idle shell into the worker's unit, so that every process the job forks is born there. It joins before the wrapper runs, because a process forked earlier would stay outside. `join` never creates a unit. It does nothing when the worker's unit does not exist, as for a Pi that no dispatch started or a worker that began before containment. It fails when the backend cannot tell, as when `systemctl` does not answer, so that the wrapper does not run outside the unit. The unit is named from `process.cwd()` the way dispatch names it from the worktree path. The cgroup backend places the unit's folder next to the caller's own cgroup, and `join` runs inside the unit, so `cgroup.sh` drops a trailing unit name from the caller's cgroup first: the mate that dispatches and the worker that joins find the same folder. The sweep backend does not join: a process group cannot hold a process that left it, and the recorded group of a finished job could name an unrelated group once its pid is reused. `e2e/extension/process-containment.test.ts` closes a worker whose job detached a server, once on the host's backend and once with `XDG_RUNTIME_DIR` pointing at an empty folder, which hides the systemd user bus and so selects the cgroup backend. That second run is skipped where `detect.sh` does not pick the cgroup backend without the bus, as on a host that does not let a user create cgroups: the sweep backend cannot hold a detached server. On a systemd host it also runs a job while a `systemctl` shim on `PATH` stops answering after the worker's unit exists, and checks that `run_long` fails with the join error and that its command never runs. The fixture server writes its pid next to its port, so that the test kills it when it fails, and registers the same kill with the e2e reaper for a runner that dies, so that a failed run leaves no server on the host.

A cgroup or a scope is stopped as a whole, so sparing a process means moving it out first. `reap` in `lib.sh` asks `service.sh` for the host-shared daemons (`shared_daemons`) and for everything under them (`service_tree`, by `ppid`), and moves the members that sit in the worker's unit with `backend_adopt`: into the `fleet-host-no-mistakes` scope on systemd (with `reset-failed` first, because a scope that ended with a failure keeps its name), and into a sibling cgroup on the cgroup backend. The daemon moves first, so that a child that it forks while the rest moves already starts in the host unit, and the listing is read again until no service pid is left in the worker's unit. If the move fails or does not settle in five rounds, `reap` exits before it signals anything, because a close that refuses is visible and a close that kills the daemon is not. The sweep backend cannot move a process out of a process group, so its `backend_adopt` always fails: a member of the group that is a shared daemon refuses the cleanup. `stop-procs.sh` asks `shared_daemons` and leaves each daemon and every process below it out of its victims. It finds that tree in the same `ps` snapshot that picks the victims, by walking `ppid`, so a step that the daemon forks after the daemons were found is spared too. It needs this because it finds processes by cwd and command line, which the daemon and its steps have when a worker started it. A daemon is told from a lookalike by what the daemon itself keeps: its argument vector and the pid in `<root>/daemon.pid`. A name alone is never enough, and a daemon whose executable or root is inside the worktree is the worker's own. A daemon that is still starting has not written its pid file yet, and a cleanup that read the missing file as permission to kill would take it along. So a candidate with the right argument vector and a root of this user also counts while it is younger than 60 seconds (`ps -o etime=`, which macOS has, unlike `etimes`) and `<root>/daemon.pid` is missing, names no live process, or names the candidate. A candidate whose pid file names another live process stays a lookalike, and an older process without a matching pid file is stopped. `e2e/support/fake-no-mistakes.ts` stands in for the daemon with the same argument vector, pid file, socket, log sink, and a step process, and for the client that starts it detached from the worker. `FAKE_NM_PUBLISH_AFTER` names a file that the fake waits for before it writes its pid file, so that a test can close a worker while its daemon is still starting. `e2e/extension/shared-daemon.test.ts` closes and restarts a worker whose pane started the daemon, next to a lookalike with a pid file that names another process and a daemon rooted in the worktree, which must still stop. It also closes a worker whose job tab started the daemon, and one whose daemon has not published its pid file yet. The tests run `detect.sh` for the host's backend. The daemon, its log sink, and its step must survive on every backend. The `Kept shared services` line, and a restart stopping the lookalike and the worktree's daemon, are required only where the backend is not `sweep`: there the daemon is already outside the group, so nothing is moved and the close result does not claim it, and a restart sends no cwd sweep.

`stop-procs.sh` also leaves fleet's own helpers out of its victims, because a helper's command line and working directory name the worktree just as a leftover's do (`archive.sh` even runs inside it). A helper is told from the worker's processes by a mark, never by its command line: every process that `closing.ts` and `containment.ts` start on a host to look at or change a worktree goes through `onHelper` in `host.ts`, which runs it as `env FLEET_HELPER=1 <command>`. The variable is in the environment from the first instruction, so no registry is needed and there is no window in which a new helper looks like the worker's, it crosses ssh, and every child inherits it. The sweep reads it from `/proc/<pid>/environ`, or, where there is no `/proc`, from what `ps -Eww` prints after the `ps -ww` command line (never the command line itself), and checks only the processes that would otherwise be victims. `helper_mark` in the script comes from `HELPER_MARK` in `host.ts`. A process counts as a helper when it or any ancestor carries the mark, and a process that is gone by the time it is read is not listed at all. Never start a long-lived process of the worker through `onHelper`: it would carry the mark and no cwd sweep would stop it. `e2e/extension/close-procs.test.ts` closes one card twice at once (the fake model's `alongside` field makes two parallel tool calls) while a leftover ignores TERM, closes a card while its merged report closes it automatically, plants a process that carries the mark in the worktree, stops a leftover whose command line copies a helper's or carries the mark as text (alone, or in its parent's), and closes the card from another session while a close is stopping the leftover. Restart and recovery (`replaceWorker`) do not run `stop-procs.sh`. They run `releaseAll`, which signals only the members of the worker's cgroup, scope, or process group, so they never take a helper. Their own helper carries the mark, so a close that runs at the same time leaves it alone.

### Clones

Clones keep up with their remote the way Firstmate's `fm-spawn.sh` and `fm-fleet-sync.sh` keep them. `sync.sh` is a POSIX port of `fm-fleet-sync.sh` and `fm-lock-lib.sh`, because a host's `sh` may be dash. It defines functions only, and each caller appends its own call.

- `ADD_WORKTREE` in `clones.ts` is the one script that makes a worktree on a new branch. Dispatch runs it for a worker. A new branch starts at `origin/<base>`, fetched just now, with no tracking, so a push never goes to the base. A failed fetch, or an origin without the base, refuses the dispatch rather than start from a stale base. A clone with no origin starts from its own base. A rerun that finds the branch reuses it without fetching.
- `refresh_clone` fetches with `--prune`, deletes branches whose remote branch is gone unless a worktree has them checked out, and fast-forwards a clean base branch. It never forces, stashes, or discards. A clone that needs attention is left alone and printed as `STUCK`: on another branch, detached with its own commits, diverged, or dirty and not level with origin, because a fast-forward would touch uncommitted work. A base branch level with origin needs nothing, so its uncommitted files are left alone and the line reads `up to date, uncommitted files left alone`. A clean detached HEAD with no commits of its own goes back on the base. A folder inside another repository is skipped, because git looks upward and would refresh that one. A fleet home (it has `config/lane.json`) is only fetched: it moves with `/updatefleet`, which also builds and restarts.
- `fetch_origin` retries a fetch blocked by `packed-refs.lock` three times a second apart, since a live owner soon exits. It then removes the lock only when it is at least 30 s old and `lsof` proves that nothing holds it or the clone. Any doubt keeps the lock.
- `clones.ts`: `close.begin` lists every host's clone of a ship card's project. A scout changes nothing on the remote, as in Firstmate's teardown. Two host names can lead to one clone, so clones are refreshed in turn. A fetch over a slow link gets 120 s. Main refreshes every registered clone when it first joins `cardd`, as Firstmate's session start does, and wakes only for a `STUCK` clone, the one state that Firstmate's bootstrap diagnostics mark as needing attention. A clone that is level with origin and holds uncommitted files is not `STUCK`: Pi rewrites its own settings in a clone, so that state is normal. Other lines wait for main's next turn.

### Lanes and homes

- `homes.ts`: main's home is the repository. A second mate's home is a worktree, `<root>.worktrees/lane-<lane>`, that shares the root's installed packages. A lane is running (its mate is in the pane), down (it should run and does not), or stopped (held by hand or for crashing, so only `up <lane>` starts it). A lane that starts too often within a window is held. Naming a held lane lifts the hold and forgets its crashes. A lane that is running is never held: a sweep that finds a mate in the pane deletes `state/stopped`, and `restart` of every lane restarts a running lane that still has the file, because the file only says what was true when it was written. `--continue` keeps the mate's conversation across a restart. A start defaults to `--model tier/orchestrator`, or the lane's `tier` from `config/lane.json`, because `--continue` would otherwise resume the model that the session last used. Explicit `--model` or `--provider` flags in the lane's `args` take precedence and are preserved (`mateStartArgs` in `lane-config.ts`), including routes tied to a lane's separate identity. `direnv exec` loads the folder's `.envrc` and replaces itself with Pi.
- A failed or incomplete workspace, pane, or process read leaves the lane unknown. Status shows `unknown`; maintenance leaves that lane alone and still reports completed actions on other lanes. A workspace lookup reads the list twice before accepting a match, absence, or a legacy fallback. An exact current-title match found only on the second read takes precedence over a missing or legacy result, but a current candidate from the first read must still be unique with the same pane count on the second. Conflicting observations leave the lane unread. Before starting or crash-holding a lane, maintenance checks the state of any pane it finds. A matching workspace must return a complete list of distinct panes belonging to it, as counted by Herdr. Only a verified single pane can be treated as idle. In a complete current-title split workspace, Pi in the lane home confirms liveness, not which pane was created first. Herdr 0.9.5 identifies the original pane in the workspace creation reply, not in later reads. A legacy split stays unknown without verified root ownership, and placement refresh leaves existing worker placement unchanged rather than infer the root of a split. Explicit stop and restart retain the legacy workspace home check. A pane that disappears between listing and inspection is also unknown. Each maintenance observation has one hard deadline for listings, process reads, and server recovery. Main rotates the first lane in each negotiated sweep so repeated stalled reads cannot keep the same healthy lane waiting. The sweep stops checking before the host call times out, leaves unobserved lanes unread, and reports confirmed outcomes even if a later operation fails. An unread maintenance reply neither announces a host failure nor clears a reported outage. A typed reply clears it only if it has a distinct, confirmed outcome for every lane captured before the sweep. A confirmed transport outage and a reported operation failure alert main independently. Before maintenance on another host, main checks support with the short, read-only `--maintenance-outcomes-v1` probe. The probe and sweep share one caller budget, including any safe SSH fallback. Other SSH callers still get a fresh timeout on fallback. A timed-out maintenance call stops its owned local process group. A lane whose `config/lane.json` exists but cannot be read stays in the sweep's expected set, shows as `unknown` in status, and is reported as a failure that blocks recovery, while healthy lanes still start and converge shared preferences; placement, explicit stop, and restart fail before changing anything. An unreadable `state/stopped` or `state/starts` (anything but a missing file) leaves the lane unread, so it never authorizes a start or hides a hold. History is validated before any start, stop, restart, or hold reset, even when it would be discarded, and status validates both lifecycle files before it publishes a definite state. Status and placement take one more workspace listing after the last lane and compare each lane's candidate rows (workspace ids and advertised pane counts) with the rows its own read consumed: a changed row makes only that status row unknown and refuses the placement refresh. The final sample detects workspace and pane-count changes, not same-count pane replacement or foreground drift. Placement also validates each lane's captured start history and confirms the lifecycle files and lane claims are unchanged before it publishes. Two workspaces with the lane's current title, or two legacy workspaces rooted in its home, are ambiguous, so the lane is left unread; unrelated same-title workspaces are still excluded by the home check. Restart treats any mate still running after it closed its own workspace as a failure, never as the replacement. Once herdr accepts a launch, the lane still waits for readiness under its lock when recording the start fails, and the sweep reports the start alongside the failure. Every record must be a complete newline-terminated timestamp, so a torn final record or an existing empty file leaves the lane unread (only a missing file is empty history), and the history is replaced atomically. A busy foreground group with no listed process, or a non-shell process listed in the shell's own group, is an incomplete observation. The typed sweep command takes one canonical nonnegative decimal rotation offset and nothing else. A shared-preferences run that skips or fails on a lane still reports where it kept edited copies, and its parse error names the file but never quotes its contents. Held restart-all requires a verified running match before it closes or starts anything: a current-title workspace when one exists, otherwise a verified legacy `fleet-<lane>` workspace rooted in the lane home whose foreground is not idle, which it closes and replaces. A confirmed older host keeps the array and nonzero failure contract, which new hosts also retain for older callers. An ambiguous probe blocks the sweep instead of guessing, and a failed command is never replayed under another format.
- Maintenance starts a mate only when its sweep has enough time to launch and still wait the normal readiness window. Starting a mate records the start after herdr accepts `pane run`, then waits for Pi to show in the pane. Until then the pane looks idle, and a second `up` would type the command again. An unread observation during the wait does not undo the accepted start.
- `lifecycle-lock.ts`: `up`, `stop`, and `restart` own a lane only inside a `BEGIN IMMEDIATE` transaction on `<home>/state/lifecycle.db`. Each `fleet` command is its own process, so an in-process queue cannot stop a supervisor's `up` and a `restart` from both finding the lane down and both starting it. SQLite's lock is held by the open file, so the OS releases it when its owner dies, and no stale owner is ever reaped by age or PID. The database holds no rows. A command that waits longer than `FLEET_LIFECYCLE_WAIT_MS` (45 seconds by default, longer than one start) fails and changes nothing.
- `lanes.ts`: each host runs its own `fleet` for its lanes. Main reaches its host directly and the others over their transport. A non-interactive shell does not expand `~`, so a remote checkout path is given whole. A host that cannot be reached is named, never skipped, and reported once until it answers. Main checks its hosts at the same time, each with its own check every minute: the shared file, then `fleet up --maintenance`, then the disk use, in that order on that host. A host that is slow or hangs delays only its own lanes, and a check that is still running is skipped, not queued behind itself. `withLanes` is a lock for each host. A host's check holds only that host. A `lane` command and `/updatefleet` hold every host and wait for the checks that run, so supervision never starts or restarts a lane while a command changes it. Starting, stopping, restarting and recovering a lane find the host by the first host whose status lists it.
- A worker never takes its model from its folder. The fleet repo's `.pi/settings.json` puts the mates on the orchestrator tier, and every worktree of the repo has that file. So unless `workerArgs` name a model, dispatch starts workers on Pi's global default model from the agent folder's `settings.json`.
- Dispatch's optional `model` selects one worker's launch through Pi's existing `--model provider/id` flag. It removes both forms of the lane's `--provider` and `--model` flags first. The mate chooses the newest suitable `openai-codex` GPT from the live catalog for writing or reviewing non-English text. There is no language detector and no model version in fleet. Other work keeps its normal model. The chosen model is stored in the attempt's `model` column and returned by both begin and resume. Dispatch retries and ordinary or incident recovery therefore keep the same explicit model. A retry that asks for a different explicit model is refused. Only `restart_card(model)` from the card's own mate changes it, and it sets the worker's model whether or not the worker was dispatched with an explicit model. It applies only when a worker's process is replaced, and it leaves a note on the card's thread when the model changes. The restart runs in one `cardd` transaction. It plans the restart first and stores the model only for an accepted restart that is not a repeat of an earlier key, so a refused or repeated restart leaves the model as it was. The new model is stored before the process starts, so every later restart launches it too. A pin such as `tier/visual` hands the worker back to the router, which is how a worker leaves an account that cannot serve it. A restart whose `avoid` names the provider of the model it will launch (the new `model` when one is given, otherwise the card's stored model) is refused in `cardd` before the restart or its incident recovery records anything, since `PI_TIERS_AVOID` reaches only the tier router and the accounts of a `tiers.json` group, and the model flag would otherwise start any other excluded provider directly.
- Why an explicit dispatch option: lane-wide `workerArgs` would change unrelated work. Installed pi-tiers supports a `Model override:` task line, but only when its private config enables it, and the override joins a chain that can fall back to Claude. The currently configured tiers are not GPT-only. A worker cannot switch its own chat model through codemode. Pi's launch flag selects the provider directly without requiring a router change.
- An explicit model pins the model, not the account. `account-rotation.ts` runs in a worker's own process. At `session_start`, when the model Pi started on is a physical model whose provider is a member of a `tiers.json` `accounts` group, it registers the virtual model `fleet/pinned` and selects it, then restores the thinking level, because Pi picks the level again on a model switch. Its `route` serves the pinned model from the pinned account first, then from the group's other members in order, skipping a member that does not serve the model, has no credentials, is named in `PI_TIERS_AVOID`, or is cooling. It keeps the account that answered last, so a cache stays warm. A worker whose provider is in no group, a tier worker, and a mate are not touched.
- Why a virtual model and not a restart: the move happens inside the same turn, on the same card, conversation, and branch, without a mate. A `message_end` handler sees every failed turn of a pinned account. 429 or rate-limit text cools the account for `cooldowns.rateLimitSeconds` of `tiers.json` (600 if unset). Quota text (the `vendor-quota` pattern of `classify`) cools it for `usageLimitSeconds` (3600 if unset). The record is a custom session entry, so a replaced or restarted process, which resumes the same session file, restores the unexpired ones and does not start on the account that ran out.
- The move does not wait for Pi's retry. Pi never retries some of these texts (`insufficient_quota`, `billing`), and retries can be switched off or spent. When another account is usable, the handler rewrites the failed message to `fleet: <account> is <why> for <model>; continuing on another account.`, which Pi does not retry. `agent_before_settle` then appends a one line custom message and asks for one more request. `route` runs again for that request and picks the next usable account. A chain of limited accounts is walked in one turn, with no incident and no replacement. `Failures` reports a turn's error only at `agent_settled`, after the continuation, so a failure that continued never reaches `cardd`. An account that failed is not tried again until a turn goes through or a new run starts, even when its cooldown ran out meanwhile (`usageLimitSeconds` can be as short as one second, and a slow account can outlast it). So a chain of failures ends after the accounts the group has, and cannot circle back past a healthy one.
- When no account is usable, the failed message, or `route` when it is asked with every account blocked (a replaced process whose accounts are all cooling, or `PI_TIERS_AVOID`), carries `fleet: no usable account for <model>: <account> (<why>), ...`, which names the model and every account that cannot serve it with its reason (`throttled until <time>`, `out of quota until <time>`, `throttled in this run` and `out of quota in this run` for an account whose cooldown ran out but that already failed in this run, `does not serve it`, `no credentials`, `avoided by the restart`). It replaces the account's own error text, and Pi does not retry it. `classify` reads it as `router-cooldown`, and `accountResumeAt` hands cardd the earliest `until` as `resumeAt`, so the recovery waits for the first account to free instead of spending its retries. An account that is already free for a new run (`in this run`, or an `until` that has passed) counts as free now, so it gives no `resumeAt` and the recovery takes its ordinary delay instead of waiting for a later cooldown. This also covers a pin whose group has no other account serving the model: the first 429 or quota failure ends the turn with this text. The cooling is in memory and in the session only. It never writes pi-tiers' cooldown files, and a tier worker's cooldowns do not move a pinned worker.
- `titles.ts` owns the mates' names: `1stmate` for main, `2ndmate-<lane>` for a second mate. A mate gives its Pi session and its herdr workspace that name at start, so main gets it too, though the captain opens main's workspace by hand. Lane lifecycle prefers a workspace with the current title. Placement falls back to a legacy workspace when the current-title candidate is a stable single pane that is rooted in another home or has no foreground Pi (idle or busy with another command), and the other lifecycle commands fall back only when no current-title candidate exists. Two current-title workspaces make the lane unread, and two legacy workspaces do so only when both verify against the lane home; a legacy workspace that does not verify is excluded, never picked by Herdr order. A canonical title matches as before, and arrange never renames or hides a canonical mate workspace, even one that carries tags. A legacy `fleet-<lane>` title matches only if the workspace has no worker tags and its first pane is in the known lane home, even if idle. For sidebar grouping, a legacy title also needs foreground Pi. A mate renames the workspace in `HERDR_WORKSPACE_ID` only when its Pi holds a terminal. Every child process of a pane inherits that variable, so a mate-lane Pi that only inherited it, such as one an end-to-end test starts with piped stdio from a worker's shell, would rename the worker's workspace. A mate whose Pi starts in a workspace with another label, which includes the relaunch that `/updatefleet` does, renames that workspace to its own name, so a wrong label on a mate's workspace corrects itself.
- `provision` (`fleet home add`) converges. It makes the worktree only when the home's folder is missing, and adopts a folder that is already a worktree of the root (made ahead, or left by a crashed run), then links `node_modules`, makes `data/` and `state/`, writes `state/stopped` when `--hold` is given, and writes `config/lane.json` last, by rename. A home is invisible to `laneHomes`, and so to every pass, until that file exists, so a half-made home is never started, and a held one is held from the first moment. `launch.ts` returns early when the home's `config/lane.json` exists, without needing the token. `--token-file` reads the token from a file or from standard input (`-`) into memory, so it is in no argument list, and no message names it. `home add` has no `--token`: `launch.ts` exits with status 2 on `--token` or `--token=<value>` anywhere on a `fleet` command line, with a message that names `--token-file -`, `--token-file FILE`, and `--bws`, and that never repeats the value. `reconfigure` (`fleet home set`) merges `args` and `workerArgs`, the only settings that `home set` takes, into the file's own JSON, so the token, the `bws` block, `hosts`, `roots`, `tier`, and `cardd` stay, checks the result with `parseLaneConfig`, and replaces the file by rename. `home set` refuses every other option with a message, because the rest of a lane's settings are `home add`'s. `listSettings` in `launch.ts` turns `--args` and `--worker-args` into settings, for `home add` and `home set`, and `laneSettings` adds the options that only `home add` takes.
- `lane-config.ts` reads `<home>/config/lane.json`. It is private because it can hold the lane's token. A lane needs a `token`, a `bws` block, or both, and `bwsConfig` checks the block (Secrets from bws). `roots` defaults to `~/.fleet/app` for a remote host. `direnv` names a folder whose environment the mate runs in, while its home stays where it is.
- `update.ts` is one host's half of `/updatefleet`, run as `fleet update [--check]`. It prints one JSON line. `--check` fetches and finds every reason to refuse: a checkout off `main`, uncommitted changes, or commits that are not on `origin/main`, in the checkout or in any lane home. The update checks again, fast-forwards, runs `bun install --frozen-lockfile` when `bun.lock` changed or `node_modules` is missing, always builds the board, and moves each lane home to the new commit. The board build is cheap and makes a rerun converge after a failed build. A lane home moves only after the build, so a failed build leaves every mate on the code it runs. `fleet cardd` does the same for `cardd`'s checkout, and restarts `cardd` only when the commit that `cardd` reports running differs from the new one in `cardd`'s code, or is unknown. The running commit decides, not the pull, because a checkout can move without a restart, and a restart that failed must happen again on the next run. It backs up the database with `VACUUM INTO`, which copies a live WAL database consistently, just before the restart, since migrations run only when `cardd` starts. Pending migrations never run while the old `cardd` serves.
- `updating.ts` is main's half. It checks every host before it changes any, so a dirty home or an unreachable host stops the update with nothing pulled. Then it updates the hosts in turn, and stops at the first failure without restarting a mate. Then it updates `cardd`, and waits until `GET /api/version` answers with the new commit, which proves that the new process serves, not the old one. HTTP and not a session, because a second session with main's token would supersede main's own. Then it asks `requestAndAwait` for a reload batch (see [Updating the fleet](setup.md#7-updating-the-fleet)). Main restarts last. Pi cannot restart its own process, so a detached `relaunch.ts` waits for main's Pi to exit and its shell to be idle, then runs `pi --continue` in main's herdr pane with main's arguments. A mate's model flags are recomputed from its current `config/lane.json` (`mateRelaunchArgs`), so a changed `tier` applies. Main restarts when the turn that tells the captain ends. The command hands its report to main as a message that starts that turn, because Pi saves a conversation only once it has a reply, and `pi --continue` would otherwise start a new one.
- `migrate.ts` only copies, so a repeat never overwrites edits. Undoing renames the settings back and sets each home's `lane.json` aside.

### Memory

- `optchat.ts` loads OptChat from `packages/extension/vendor/optchat` with `FM_HOME` set to the home, when the home has `config/optchat.json`. The loader reads `FM_HOME` when its module is evaluated, so the variable is set around the import. The vendored folder is third-party code with its own style: lint, format, and knip skip it because their config files list it, and the typecheck skips it because `optchat.ts` imports it by URL, which the compiler does not follow. Fleet's own changes to it are listed in its `README.md`.

### Standing rules and stow

- `standing.ts` reads the three files in `data/` on every turn, in `before_agent_start`, so a mate's own edit takes effect on its next turn with no reload. A mate's own home `AGENTS.md` is the exception to Pi's context files: Fleet loads it at startup, reload, or /stow, so an edit applies only then, and before every turn and run start Fleet only checks that the file is still a readable regular file: a missing or rejected one blocks the run. Pi's other context files (global, ancestor, or project files) need Pi's reload, because Pi reads them once. A reload is still the only way for a mate to load new extension code.
- Main's `captain-shared.md` reaches second mates by copy, not by reading main's home, because a lane's home can be on another host. Main pushes the bytes as base64 on the command line of `fleet shared`, through the host's transport, so no host needs a shared file system. The push runs each minute before main starts the lanes of that host, so a lane that starts already holds the file. It also runs at the end of `/stow`. A failed push to a host that answers is told once, and never stops the lanes from being kept running. A copy is read-only and replaced by rename, so a mate never reads half a file. Like Firstmate, a copy that someone edited is kept aside before it is replaced or removed: the home's `state/captain-shared.published` holds the bytes main last put there, and a copy that matches neither that nor main's file was edited. The aside copy is a plain sibling that no loader reads, so it is never a second shared file. A copy with no record, such as one from before this existed, counts as edited. The mode is only a nudge: main's bytes always win.
- The stale flags in the stow report are computed, not judged, because the model gets date arithmetic wrong. The entry format is one bullet line with an optional trailing marker. Anything else in a file is prose that the report skips.
- `stow.ts` ends the command by waiting for `agent_settled`, then reloading. Pi allows `reload` only in a command handler. `sendMessage` returns before the turn starts, so `waitForIdle` right after it could return at once, which is why the command waits for the settle event it sets up first. A reload runs the extension factory again, so the link to cardd reconnects, and main checks the clones again on its first connection. The reload keeps the process id, because it is the same OS process.
- `e2e/extension/standing.test.ts` gives its mates Pi's context files and built-in tools, which the other tests turn off, because `AGENTS.md` and the model's `write` are what it checks. Its stow tests set `FLEET_SUPERVISE_MS` to ten minutes, so only the stow can have published the shared file. It does not wait a fixed time: it waits for the probe's `session_start` event with reason `reload`.

### Neglect

[neglect.md](neglect.md) owns what the states mean and when someone is told. Inside:

Everything about a dated wait stays in `datedWait`. `seenBy` in `board.ts` is the one place that makes a card fit a lane's eyes, for the `board` op and the `card` op alike: it hides what a dated wait watches in another lane, and it recounts `behind` with every step of a lane the viewer cannot see as open and not started.

The `watched` count in a list entry's `fields` counts the `watched` group, and is 0 in a list that was not due for them.
- `e2e/cardd/pulse.test.ts` ages cards by writing old times into the scratch database. It drops the `entries_no_update` trigger first, because entries are append-only. That is a fixture on a scratch database, never `cardd`'s own code.

### Calm

[calm.md](calm.md) owns what the captain sees. Inside:

- `layout.ts` patches the render of three Pi components. `ToolExecutionComponent` draws nothing, unless the row has an image, because an image is content. Without Pi's image list, a row counts as having images: showing a row is the safe error. `CustomMessageComponent` draws nothing for a `fleet` message. `AssistantMessageComponent` loses collapsed thinking and short pre-tool text from a shallow copy before layout. Pi's later refreshes read the full message back.
- Each patch probes the Pi member it replaces. `index.ts` skips a missing one with a diagnostic. A patch installs once per process. A reload evaluates the module again, so the flag lives in one process-wide object in `state.ts`.
- Calm drops thinking while it is on and Pi hides thinking (`hideThinkingBlock`). It does not read or set Pi's hidden-thinking label, because anything can reset the label, and a reset label shows `Thinking...`. Setting the label makes Pi lay out every assistant row again, so Calm sets it back to Pi's default on each toggle to apply the toggle to rows already on screen. Without a terminal (print and RPC modes), calm only records its state.
- `e2e/extension/calm.test.ts` navigates the fullscreen transcript before checking restored rows. Herdr's recent terminal output can contain only the current viewport after a redraw, not every retained message. Ctrl+Home reveals the earlier fleet, note, and tool rows; Ctrl+End reveals the later conversation. The test sends their standard terminal sequences because herdr 0.9.5 does not name those modified keys.
- One logical run lasts from `agent_start` to `agent_settled`, which also covers abort and failure, so the boat does not flicker between tool calls.
- `preference.ts` replaces `config/calm` atomically, so a crash never leaves half a value. The choice is saved before the screen changes, so a failed write changes nothing.
- `ship-sprite.ts` owns the geometry, the bounce track, and the two linked cadences. Every tick moves the water a quarter cell, and every fourth tick moves the boat one cell, so the trough stays under the boat. Ticks, not wall time, drive every change. Hiding freezes the sprite at its last painted frame, and the next run resumes there. A fresh session resets it. State never sits in a module-level singleton. The boat at an endpoint already carries the new direction. A resize recomputes and clamps the track before the next frame.
- `ship.ts` paints runs with standard ANSI codes only: one blue for water, so the swell reads through glyph height, and one yellow for the whole boat. It recomputes the track from the render width on every frame. The widget key `calm-working-ship` is shared with Firstmate's calm and the standalone Pi calm, so a session that loads more than one shows a single boat. Its timer never keeps Pi's process alive.

### Transcript

[transcript.md](transcript.md) owns what the captain sees. Inside:

- Pi has no hook around a whole message. Its Markdown transform sees one text block at a time and has no message identity, and `registerMessageRenderer` covers only custom messages. So `transcript/layout.ts` patches the `render` of `UserMessageComponent`, `AssistantMessageComponent`, and `CustomMessageComponent`, as Calm does, and each patch draws the rule around the lines Pi drew. A Markdown transformer would draw one rule for each text block.
- The patch keeps no state about earlier messages. Pi draws every message again at each frame, on a resize, and when a restart replays the history, so a rule that depended on the last message drawn would repeat or vanish. The rule depends only on the message and the width.
- Pi's assistant and custom rows start with their own blank line, and the rule goes under it. A user row has its blank line outside it, in a `Spacer` that Pi adds before the row, so the rule goes first. An empty row stays empty, which is why a silent reply has no rule.
- `state.ts` holds Pi's live theme, in one process-wide object like Calm's. `ctx.ui.theme` is a proxy for the current theme, so a theme change reaches rows already on screen. It never holds the extension context itself: after `/new`, the old context is stale, and reading it from a render crashes Pi. Without a terminal nothing sets it and nothing is drawn.
- The mate's own replies have a rule and no name. The one list of the fleet's own message types, `FLEET_ROW_TYPES` in `layout.ts`, decides both which rows are labelled `fleet` and which get the framed renderer. A type missing from it keeps Pi's raw `[type]` header.
- `patch.ts` is shared with Calm: install a patch once per process, probe the Pi member it replaces, and report a missing one with a line. Each patch loses only its own part if a Pi release moves the member.
- `window.ts` implements the [history window](transcript.md#what-it-does) with `DRAWN_ENTRIES` as its window size. Pi 1.4.0 draws every row of the chat at every frame: `Container.render` walks all of them, and the fullscreen layout needs the whole height to place the scroll position. A frame costs time in proportion to the rows, and the working spinner asks for about twelve frames a second, so one mate session of 28,000 entries kept the main thread at 100% CPU. Everything that shares that thread waits for a frame: `dispatch` makes about 25 awaited `herdr`, `git`, and `sh` calls, and each answer reached it only between frames (a dispatch took 5.4 s on that session, 17 s with the captain's footer and readable-row extensions, and 0.9 s on a new one). A mate cannot lean on compaction to bound the chat: OptChat cancels `session_before_compact` for every mate with memory, so those sessions never compact. `buildContextEntries` is not patched, because Pi also uses it for the model's context. The model, `/export`, the session file, and OptChat memory still see every entry, and nothing here rolls or writes the session file.
  - The patch is on `InteractiveMode.renderSessionEntries`, the one place where Pi turns session entries into chat rows at start, on `/reload`, and on every rebuild. It filters orphan tool results from the last `DRAWN_ENTRIES` entries, passes the remaining entries to Pi, and puts the notice row where the drawn history starts. There is one notice component. It lives in `state.ts` with the count of entries that are not drawn, and it reads that count each time it renders. The start and every rebuild set the count and put that same component back, so a rebuild never makes a second notice. Pi draws a tool result only inside the row of its call, so a result whose call is not among the drawn entries is left out with it, and the notice counts every entry that is not drawn.
  - Pi fills the editor's Up-arrow history only from the entries it draws. The patch adds the text of every older user entry first, so the captain's old prompts stay in the history after a restart.
  - The patch keeps the `InteractiveMode` that it is called on in `state.ts`, with the theme and the notice. On `agent_settled` the extension calls `trimDrawnHistory`. When the chat holds more than twice `DRAWN_ENTRIES` rows, it calls Pi's `rebuildChatFromMessages`, which clears the chat and renders every entry again through the same patch. The window, the notice, and its count are set in that one place. It rebuilds instead of removing the oldest rows because the rows of an entry are not tracked: an entry makes no row, one, or several, so only a render can say which rows belong to the last 500 entries. Rows that Pi made without an entry, such as a status line, go with the rebuild.
  - The trim waits while the captain is scrolled up, so the view does not jump under them. Pi exposes that as `renderer.isFollowingOutput` only in fullscreen mode. Without fullscreen there is nothing to read and the trim runs anyway. The next `agent_settled` that finds the transcript following its end trims.
  - The patch probes the Pi members it replaces or calls, `renderSessionEntries`, `getUserMessageText`, and `rebuildChatFromMessages`, and installs nothing when one is missing. Without the patch the extension never holds a mode, and the trim does nothing.
- `index.ts` registers a message renderer for the fleet's own rows. It draws the text in Pi's custom-message box without its `[fleet]` label. `@earendil-works/pi-tui` is a peer dependency of the extension, as `pi-coding-agent` is, because the renderer builds `Box` and `Text` at run time.

### Discord bridge

- The bridge starts from `start()` in `index.ts`, next to the other main-only parts, under `lane === "main"`. The lane comes from `config/lane.json` or `FLEET_LANE`, so the gate is the lane's own name and no path is involved. It starts there and not as a separate source in `.pi/extensions/fleet.ts`, because `start()` runs after `applyEnvSecrets`, so a token that `bws.env` maps into the environment is already set. It calls the bridge's start directly, not through a `session_start` handler of its own, because Pi snapshots the handlers before it runs an event, so a handler added while `session_start` runs misses that event.
- It reads the channel by polling Discord's HTTP API, so it needs no dependency and no gateway events. Discord's Message Content Intent still applies to the HTTP API, which is why the setup asks for it.
- A bot shows online only while a gateway session is open, and polling never opened one, so the bot always showed offline. `presence.ts` holds that session and does nothing else: it identifies with no intents and `status: "online"`, heartbeats, and ignores every event. A heartbeat that is not acknowledged before the next one means a dead connection, which it abandons for a new one. It does not resume. Each reconnect identifies afresh, which sets the presence again, and the wait before it starts at 5 seconds and doubles up to 2 minutes. It starts over at 5 seconds only when the connection that ended had been ready for a minute. Discord allows 1000 identifies a day and resets the bot's token past that, so a connection that keeps dropping right after `READY` must not retry quickly. The gateway address comes from `GET /gateway/bot` on the same base URL as every other call, so a proxy or a fake serves both.
- At `session_shutdown` the connection closes with code 1000, which ends the session and shows the bot offline at once. Pi awaits `session_shutdown` handlers, and a reload starts its new runtime only after them, so the old connection is gone before the new one opens and a reload never leaves two. The wait for the close is capped at two seconds, so a dead network cannot hold the shutdown. A process that is killed cannot close, and Discord keeps its session until it times out a few minutes later. A close with any other code does the same, which is why a dead connection is abandoned with 4000 and not 1000: Discord says to close a zombied connection that way. `e2e/support/fake-discord.ts` also serves a gateway, and `botStatus` answers as Discord shows the bot: online while an identified connection is open. It records each connection's Identify status and the code it closed with. `e2e/extension/discord-presence.test.ts` checks online, offline at shutdown with code 1000, one live connection after repeated reloads, and a new connection after a drop and after silence.
- `config.ts` is the only reader of settings. It returns `off` (none of the required settings), `refused` (some settings, or a bad value, with a message that never repeats a value), or `on`. The allowlist has no default and `BRIDGE_ALLOWED_USER_IDS` is required: an open channel would let anyone who can post there run main's tools. Every ID is checked to be digits before it goes into a URL path. `BRIDGE_GUILD_ID` is checked against the channel's own guild at start, and a failed lookup does not block, since the setting is a sanity check.
- Each request has a timeout. The earlier bridge had a watchdog that re-armed a stuck outbound loop, which only a request with no timeout could wedge. With every request bounded, `drain` always ends, and one interval retries a failed post, so the watchdog is gone. A 429 waits `retry_after` and retries up to five times. A post that still fails stays at the head of the queue, and the next tick retries it, so a message is never dropped. An upload that fails is dropped with a log line, so one bad file cannot block the queue.
- The inbound cursor is the id of the newest message seen. An empty channel is cursor `0`. A failed lookup leaves the cursor unset, and the next poll tries again, so a network error at start can never replay the channel's history as commands. Messages are sorted by id before they are handled, because the cursor must only move forward.
- Process-scoped state (`state.ts`) lives on `globalThis`, as the transcript state does: Pi replaces the extension runtime on `/new`, `/resume`, `/fork`, and reload, and the cursor, the bot's id, the queue, and the one-time online notice must outlive that. Timers belong to the runtime and stop at `session_shutdown`.
- `text.ts` refuses to upload anything under the home's `config/`, `data/`, or `state/`, and any dotenv file. The assistant picks the path, so an injected instruction could name a secret file. The rule is by real path, with the home and each folder resolved through `realpathSync` and compared with `path.relative`, so a symlink cannot get around it. A refused path stays in the reply text.
- Downloaded attachments and the log live in the home's private `state/`, not in a shared temporary folder, because their names would otherwise be predictable by other users of the host.
- Voice messages are transcribed by `transcribe.ts` in the bridge's own process, with `ffmpeg` and `whisper-cli` run without a shell. whisper-cli reads only wav, mp3, flac, and Ogg Vorbis, and Discord sends Ogg Opus, so `ffmpeg` converts first. The WAV goes to a file beside the saved attachment and is removed after, because `whisper-cli -f -` (standard input) printed no transcript with Homebrew's whisper.cpp 1.9.5. The language is `auto` unless set, which matches Groq's behavior and costs one more encoder pass. A failure never drops the message: `render` keeps the file reference, and the reason goes to the bridge log.
- The bridge does not drive OpenSuperWhisper, which was the first choice. Its bundle declares no URL scheme, no `OSAScriptingDefinition` (`sdef` fails with error -192), no App Intents, and no command-line handling, and it has no server code. The only entry is the open-document event (`application(_:openFile:)`). In the upstream source it shows the main window, queues the file, and writes the result to the app's own `recordings.sqlite`: it needs the app running in a logged-in session, it takes the focus, and its database layout is not an interface. The app's engine is whisper.cpp, and the largest model it offers, Turbo V3 large, is `ggml-large-v3-turbo.bin` from `ggerganov/whisper.cpp`, so the bridge runs that same model through `whisper-cli`.
- `e2e/support/fake-discord.ts` is a fake of the parts of Discord's and Groq's HTTP APIs that the bridge calls. It keeps the channel's messages, hands them out in Discord's order, rejects a request without the bot token, and can answer a post with a 429. `e2e/support/fake-whisper.ts` is a stand-in `ffmpeg` and `whisper-cli` (`fake-whisper-tool.ts`) that log their arguments, so the local transcription path runs in CI without a model. `e2e/extension/discord-bridge.test.ts` and `discord-voice.test.ts` start a real main Pi against them.

## Board

- `App.tsx` reloads the board on every change and every 30 seconds, because a card's notice depends on the clock. It keeps only the newest load. It keeps what the captain started to write on each card when he goes back to the board.

## End-to-end tests

- `e2e/run.ts` makes a private suite folder, `fe-<random>`, and gives it to every file as `FLEET_E2E_TMPDIR`. The suite base is the real path of `FLEET_E2E_TMPDIR` or the disk temp folder, normally `/var/tmp`. The runner rejects a base if it or any canonical ancestor can be replaced by another user. When the verified base is shared, the runner uses an owner-verified private subfolder named for the user ID. Runs under the same base share a private `fleet-e2e-cache` for downloads. Tests unpack them under unique names and rename them into place. Linux `/tmp` is often a tmpfs with a fixed number of inodes, so it is not the default.
- `e2e/support/run-root.ts` uses the short numbered folder assigned by the suite runner. A direct Node test or nested fixture gets its own `fr-<pid>-<random>` folder under the same base. macOS's own `TMPDIR` is a long folder under `/var`, which is a symlink to `/private/var`. A memory profile's lock socket under it goes over macOS's 103-byte limit, so the memory never loads. And a path through the symlink differs from the real path that a pane's cwd and Pi report, so a test that builds one from the other no longer matches. The real path keeps both the same on Linux and macOS. It also sets `FLEET_HOST_DIR` and `XDG_CONFIG_HOME` for every process that the file starts. `XDG_CONFIG_HOME` is where herdr keeps its sessions and sockets, so a file's herdr servers are invisible to every other file and every other suite, and to the captain's own herdr, and a leftover session goes with the run folder. `e2e/extension/tempdir-leak.test.ts` runs a nested suite in a folder it owns through `FLEET_E2E_TMPDIR`.
- `e2e/support/scratch.ts` makes a scratch copy of the repository with its own lane homes. A second mate's memory profile in a scratch home has a lock socket path longer than macOS's 103-byte limit, whatever `TMPDIR` is. So the tests that make one skip on macOS, and CI on Linux runs them.
- `e2e/support/fake-model.ts` is a Pi extension that posts each model call to the test's control server and returns the move the test chooses. Everything else in Pi stays real.
- `e2e/support/fake-anthropic.ts` registers a `tier` provider on Pi's real Anthropic Messages client, pointed at the control server, so the harness reads the actual request: its `cache_control` retention and whether it is a one-token warm. The harness answers with a server-sent-event stream. `harness.wire` lists the requests, with the role taken from the system prompt.
- `e2e/support/bws.ts` puts a fake `bws` first on a test's `PATH`. The fake keeps its secrets only in the environment of the test's processes (`FAKE_BWS_DATA`), never in a file, and logs each call's arguments. So `filesHolding` can scan the whole run folder for a secret, and a hit means the fleet wrote it. `bws-cli.test.ts` covers `fleet wake`, `fleet secrets`, and each fallback. `bws-session.test.ts` covers a mate, and a worker that its mate dispatched.
- `e2e/support/herdr.ts` runs an isolated herdr session whose name starts with `fleet-lab-`. The lab registers its initial and replacement server groups in a private lab directory, so identical session names in separate XDG folders do not select each other's processes. A Pi that points at a lab's session restarts that server whenever it finds it stopped (`host.ts`), so a test that stops the lab with such a Pi alive gets a new server back within milliseconds, either before `session delete`, which then fails with "is running", or after it, which leaks the server. The mate carries `lab.owned`, so a replacement it starts is registered in the lab or refused once the lab is closed, and a test stops the mate before the lab. `Pi.kill` in `e2e/support/harness.ts` signals the Pi's whole process group while its leader is alive. A child that a killed Pi leaves behind, such as the `herdr agent start --timeout 4000` of a dispatch that the test did not wait for, would keep the group in the lab's registry with no leader to verify it, and the lab's five-second sweep would fail with "could not stop owned Herdr lab". `e2e/support/operation-lab.ts` stops what it started in reverse order of starting, runs every stop even when one throws, and fails with the first error.
- `e2e/support/hermetic-env.ts` removes the fleet variables that a live mate exports, such as `FLEET_HOSTS`, `FLEET_ROOTS`, and `FLEET_ROOT`, as soon as a test loads its support. The extension and `fleet` read those variables before their lane config, so a run started from a mate's shell would otherwise send a scratch fleet's commands to the live hosts and checkouts. It also removes the herdr pane variables (`HERDR_WORKSPACE_ID`, `HERDR_PANE_ID`, `HERDR_TAB_ID`, `HERDR_SOCKET_PATH`, `HERDR_ENV`, and `HERDR_SESSION`), because the herdr CLI follows `HERDR_SOCKET_PATH`, so a run started from a worker's pane would otherwise reach that worker's live herdr and rename its workspace. Every module that spawns a fleet process imports it: `guarded.ts`, `herdr.ts` and `scratch.ts`. `e2e/extension/hermetic.test.ts` runs a two-host test from such an environment and fails if any command reaches the live host. It also runs a mate test from a worker pane's herdr variables and fails if the pane's workspace is renamed. It also sets `SHELL` to a wrapper that starts bash with `--noprofile --norc`, so the shell of every lab pane reads no rc file of its host. Lane mates and workers start with a bare `pi` typed into that shell, and a host rc that puts another `pi` first on the PATH (the usual `~/.local/bin` line) would otherwise start the host's Pi in place of the repo's Pi, so the lane never connects. The shell has to be one with line editing, because a Pi that is killed leaves the terminal in raw mode and a plain `sh` then never reads the Enter of the next command. `hermetic.test.ts` runs `launch.test.ts` from a host whose rc files in every shell put a decoy `pi` first, and fails if the decoy runs or the mate does not start. Production `fleet up`, relaunch and dispatch also type a bare `pi` and use the pane shell's PATH on purpose, so a lane runs the operator's own Pi.
- `Harness.stop` in `e2e/support/harness.ts` destroys every open connection before it waits for the control server to close. A Pi killed in the middle of a model request leaves that request half sent, and a plain `close` waits for it for the kernel's whole retry period. `process-containment.test.ts` gives its liveness probe a two-second connect timeout, because a closed loopback port on a loaded host can hang for minutes instead of refusing.
- `e2e/support/roomy-disk.ts` is a Node preload that every e2e process loads by default (via `hermetic-env.ts`) to report 10% disk use for local alarm probes, so a busy host does not trigger an unrelated model turn. The `disk-alarm*.test.ts` files share one lab in `e2e/support/disk-lab.ts` and are split so that no one file dominates a shard. They also script the far host's report through its own transport. `scratch-use.test.ts` invokes the CLI without the preload and checks each reported filesystem against live readings.
- `e2e/support/clock.ts` and `clock-preload.ts` move `Date` forward in the Node processes that a lab that opts in starts, through a skew file that the test writes. A test that waits out a cache lifetime (`cache-breaks.test.ts`, `memory-fold.test.ts`) moves the clock instead of sleeping. Pi's own timers still run on real time.
- `e2e/support/remote.ts` gives a clone a bare remote, `<clone>.git`, and lands commits on it from another clone, as a merged PR does. The dispatch lab names its GitHub repository with `--repo acme/site`, so its clone needs no origin on GitHub: dispatch fetches any origin first. With `remote` set, the lab registers its clone for host `local` only, because the other lab hosts reach the same folder and would refresh it once each.
- A mate `Session` from `e2e/support/cardd.ts` acknowledges each entry it gets, as a mate whose runs end cleanly does, so the timed check never sends it anything again. `connect(token, inFile, false)` makes a mate that never takes anything in. `connect` also sends a process id in its hello, the same one for every connection that uses a token, as the extension's `Link` does for one Pi process. A hello with no process id never clears a startup or lost incident (see Runtime incidents), so a helper that sent none would leave the incident of a worker that connected late, or that reconnected after a stall, open for good, and a live incident holds back that worker's idle finding. With `CARDD_TIMING_SCALE=0.001` a worker has 120 ms to connect after `begin` and 120 ms to reconnect before that incident opens.
- A `cardd` test that crosses a time window runs at the real scale with `CARDD_CHECK_EVERY_MS=50` and moves time by ageing rows: `ageCards`, `ageSession`, `ageDated`, `ageEntry`, `ageBatch`, and `ageDelivery` in `e2e/support/fleet.ts` shift stored times back. `CheckPasses.next()` returns after a timed check has read the database as it stands, so a test can assert that nothing was sent yet. A small `CARDD_TIMING_SCALE` with heartbeats sent at its heartbeat fails on a busy host for two reasons. Its windows (120 ms to connect, 90 ms without a job heartbeat) are shorter than the scheduling gaps of a loaded host. And a heartbeat every 20 to 40 ms is 25 to 150 writes a second, each commit is an fsync on the event loop of `cardd`, and an fsync took 40 to 820 ms on p620's busy ext4 disk, so every call queues behind the heartbeats until it times out. `stalled.test.ts`, `spinning.test.ts`, `action-cadence.test.ts`, `pause-watch.test.ts`, `decision-bundle.test.ts`, and `intake-repeat.test.ts` use this pattern. A test ages the rows of all cards a check must see together in one call (`ageCards`, `ageDated`), because two calls let a check pass between them list only some. When a test ages both a card and the last list, it ages the card first, then the list, so no pass can send a list that lacks the card.
- `e2e/support/fake-gh.ts` supports only worker-initiated PR merges and logs every invocation. Discovery and PR-state commands are rejected. Merge fixtures are atomically published through same-directory renames. Every `Cardd` in the tests runs this fake gh, so no test reaches GitHub. The trial runs the real one.
- Scratch puts a successful `gh --version` and `gh auth status` stand-in before the host's tools. FakeGitHub takes precedence for PR commands. The prerequisite tests supply explicit missing and failed-login cases instead of using the host's credentials.
- `e2e/extension/sync.test.ts` scripts lsof's ownership answer. A real host's unrelated inaccessible mounts can make lsof's negative result incomplete. The product keeps the lock in that case. The test covers a clean negative result, a holder, an inspection failure, an incomplete clone scan, and a recent lock without weakening the product's checks.
- The model harness accepts only `POST /model`. Closing its websocket server removes the upgrade listener, so a late probe handshake can arrive as an ordinary HTTP GET. It receives 404 rather than entering the JSON model parser. Node 26 resets a connection whose request ends after `server.close()`, so there the handshake gets a reset instead. `e2e/pi/harness.test.ts` accepts either, and checks that no model call came of it.
- `e2e/support/fake-ssh.ts` (put on the `PATH` as `ssh` by `mux-ssh.ts`) is an ssh whose master refuses file descriptors: in mode `wedged` it prints `mm_send_fd: sendmsg(0): Message too long` and exits 255 until it is run with `-o ControlMaster=no -o ControlPath=none`, in mode `down` it always times out, in mode `wedged-down` it refuses and then times out, and in mode `fell-back-then-dropped` it prints `muxclient: master hello exchange failed`, runs the command, and exits 255 anyway, as ssh does when it falls back by itself and the connection then drops. It logs every call. `e2e/extension/ssh-mux.test.ts` and `e2e/cardd/ssh-mux.test.ts` use it.
- `e2e/support/torn-transport.ts` behaves like herdr reading a process while it execs: for 2.5 s after the first process-info reply that shows Pi, every reply that shows Pi names it `node` and drops its arguments, and the transport writes a `.torn` file next to its marker for each one. `launch-watch.test.ts` dispatches through it.
- `e2e/support/flaky-transport.ts` behaves like ssh whose connection drops right after the worker started: the first `herdr agent start` that succeeds loses its output and exits 255. `switch-transport.ts` fails like an unreachable host once its marker file exists. A marker that starts with `hang` hangs instead, and one that starts with `flood` floods every command but herdr's.

- `e2e/extension/account-rotation.test.ts` starts a real worker Pi on `--provider anthropic-3 --model <id>:medium` against a real `cardd`, with Pi's retries switched off. `tiers.json` in the test's agent folder groups fake providers: some serve the model, one serves another. The fake model fails a request with the text of a 429 or of a quota error, and the test reads which `provider/model` each request reached. It covers the move to the other account on either text in one process with no failure on the card, the walk past two limited accounts to a third, the unchanged thinking level, the one failure that names the model and the accounts when none is left, accounts with a one second cooldown that a slow answer outlasts (never revisited in the same chain, revisited after a turn that went through and by a new run, and not held back from recovery by a later account's longer cooldown), a second process on the same session that skips the account that ran out, and an `avoid` that names the other account.
